Khi một nhánh công việc được đưa vào nhánh tích hợp, lựa chọn đầu tiên không nên là bấm merge theo thói quen mà phải đọc commit graph. Fast forward chỉ có thể xảy ra khi tip hiện tại của nhánh đích là ancestor của tip nhánh nguồn. Trong trường hợp đó git không cần tạo merge commit, nó chỉ di chuyển ref của nhánh đích tới commit đã tồn tại. Cách này giữ nguyên commit id và tạo lịch sử tuyến tính, nhưng không tạo một node riêng để ghi boundary của feature. Nếu hai nhánh đã cùng tiến lên từ một merge base, git cần three way merge. Nó so snapshot tại merge base với snapshot của mỗi tip rồi xây result tree. Nếu result được commit, merge commit thường có hai parent và giữ nguyên toàn bộ commit cũ. Developer nên dùng git merge base để chứng minh điểm chung tốt nhất thay vì đoán từ thời gian hoặc vị trí hiển thị trong log. Git log graph decorate oneline giúp nhìn divergence, parent và ref rõ hơn một danh sách phẳng. Policy fast forward only phù hợp khi nhánh đích chỉ được phép di chuyển đến một descendant đã kiểm chứng. Policy no fast forward phù hợp khi team muốn giữ feature boundary, nhưng nó không tự làm chất lượng tốt hơn. Một merge commit có message kém, không có test và không có issue evidence vẫn là release input yếu. Ngược lại, history tuyến tính cũng không có nghĩa mọi thay đổi đã được review. Trước operation, developer cần fetch remote refs, xác nhận current branch, source tip và target tip, ghi merge base, kiểm tra working tree sạch và hiểu branch có đang được môi trường cloud sử dụng hay không. Sau operation, cần xem parent của commit cuối, staged diff, test result và remote commit. Mục tiêu không phải tạo graph đẹp nhất theo sở thích cá nhân, mà là tạo graph phù hợp với mức chia sẻ, khả năng audit và quy trình promotion. Một quyết định merge tốt luôn giải thích được object nào được giữ, ref nào di chuyển, commit nào được tạo mới và evidence nào chứng minh result có thể phát hành.

Rebase không kéo các commit cũ sang chỗ mới như di chuyển file trong thư mục. Nó xác định chuỗi commit thuộc nhánh công việc, đặt nhánh lên base mới rồi áp lại từng patch để tạo commit object mới. Vì parent thay đổi, commit id cũng thay đổi ngay cả khi message và thay đổi nhìn giống nhau. Điều này làm history tuyến tính hơn nhưng đồng thời phá mọi tham chiếu dựa trên id cũ. Rebase phù hợp nhất với branch cá nhân hoặc branch chưa có collaborator phụ thuộc. Trước một rebase phức tạp, developer nên fetch remote, tạo backup ref và ghi tip cũ. Nếu conflict xảy ra, rebase dừng tại commit đang replay. Git rebase show current patch cho biết patch nào đang được áp, còn rebase head giúp xác định commit nguồn. Sau khi resolve và stage, git rebase continue tạo commit mới rồi chuyển sang patch tiếp theo. Git rebase abort đưa branch về trạng thái trước operation, trong khi quit dừng sequencer nhưng không có cùng hành vi reset. Git rebase skip bỏ patch hiện tại khỏi series mới, vì vậy nó không phải nút bỏ qua khó khăn. Chỉ skip khi change đã thật sự tồn tại ở base hoặc requirement chứng minh patch không còn cần. Sau rebase, range diff nên được dùng để so patch series cũ và mới. Kết quả vẫn cần test vì hai patch tương đương về text có thể chạy trong context khác sau khi base thay đổi. Khi push rewritten branch, force with lease an toàn hơn force vì nó kiểm tra remote ref chưa đổi ngoài dự kiến, nhưng nó không bảo vệ khỏi mọi sai policy. Shared integration, staging hoặc production history không nên bị rebase chỉ để đẹp. Trên adobe commerce cloud, environment branch có thể kích hoạt build và deploy, nên rewrite sai có thể làm mất trace giữa review, activity và artifact. Quy tắc senior là chỉ rewrite trong vùng có ownership rõ, giữ recovery ref, so patch intent, chạy verification đầy đủ và thông báo collaborator trước khi cập nhật remote.

Một conflict nên được đọc như trạng thái dữ liệu trong index, không chỉ như các marker trong editor. Khi three way merge không thể tự quyết, index có thể giữ stage một cho merge base, stage hai cho ours và stage ba cho theirs. Git ls files u hiển thị unmerged entries, còn git show với cú pháp stage và path cho phép đọc từng version. Content conflict xảy ra khi hai side sửa cùng region. Add add conflict xảy ra khi hai side cùng tạo một path khác nhau và thường không có base version. Modify delete conflict yêu cầu điều tra vì một side có thể đã chuyển behavior sang class mới trong khi side kia vẫn sửa file cũ. Rename rename hoặc rename delete conflict phức tạp hơn vì rename là suy luận similarity, không phải một object riêng được lưu trong commit. Directory file conflict có thể phá cấu trúc psr four, còn mode hoặc symlink conflict có thể tạo khác biệt deployment và security. Cấu hình conflict style diff three giúp marker hiển thị thêm base, nhưng base chỉ là evidence chứ không phải đáp án. Developer phải xác định contract cuối từ issue, design, test và behavior hiện tại. Sau khi sửa working file, git add chỉ ghi result vào index và đánh dấu path resolved. Nó không chứng minh result đúng. Trước khi continue, cần chạy git diff check, xem staged diff, xác nhận không còn unmerged path và kiểm tra mọi reference liên quan. Nếu một class được rename, phải tìm namespace, composer autoload, di xml, layout xml, test và factory reference. Nếu một file bị xóa, phải xác nhận feature đã được loại bỏ hay thay thế. Một resolution có thể khác cả ours và theirs vì requirement mới cần kết hợp hoặc tái thiết kế hai change. Evidence tốt ghi original tips, merge base, conflict type, base content, hai side, rationale, staged result và test. Cách làm này biến conflict resolution từ thao tác sửa text thành một quyết định kỹ thuật có thể review và audit.

Ours và theirs là các nhãn theo operation context, không phải hai lựa chọn mang ý nghĩa cố định là code của tôi và code của người khác. Trong merge bình thường, ours thường là current branch đang checkout, còn theirs là branch được merge vào. Trong rebase, git đặt result đang xây trên upstream làm side được checkout rồi replay commit của task branch. Vì vậy label mà developer quen từ merge có thể bị cảm nhận là đảo ngược. Trước khi chọn nguyên một side, cần xác định operation đang chạy bằng git status, merge head hoặc rebase head, sau đó đọc base và từng index stage. Checkout ours hoặc checkout theirs có thể đúng nếu toàn bộ file của một side là contract mong muốn, nhưng dùng máy móc thường làm mất change hợp lệ. Nguy hiểm còn lớn hơn với composer lock, generated config hoặc file chứa nhiều contract độc lập. Strategy option x ours cũng dễ bị hiểu sai. Nó ưu tiên ours ở conflicting hunks nhưng vẫn nhận non conflicting change từ side kia. Nó khác với merge strategy ours, vốn tạo result tree theo current branch và bỏ tree change từ head còn lại. Một team dùng x ours để hết conflict nhanh có thể vô tình phát hành code chưa từng được review theo file. Semantic conflict cũng không cần marker. Hai di xml ở dòng khác nhau có thể merge sạch nhưng tạo hai preference cho cùng interface. Hai plugin có thể dùng cùng sort order hoặc cùng thay đổi result mutable. Hai schema change có thể hợp lệ riêng nhưng kết hợp thành constraint hoặc migration không an toàn. Vì vậy câu hỏi đúng không phải side nào thắng, mà là final application contract là gì. Resolution phải được chứng minh bằng dependency validation, di compile, targeted integration test, smoke test và review generated artifact. Nếu requirement không rõ, abort operation và xin design evidence tốt hơn an toàn hơn chọn đại. Senior developer coi side selection là một công cụ hẹp, không phải chiến lược giải conflict.

Composer json và composer lock cần một quy trình conflict riêng vì lock file là kết quả của dependency solver. Hai branch có thể thêm các package khác nhau và mỗi branch đều có lock hợp lệ, nhưng ghép các block json bằng tay có thể tạo graph không thỏa constraint. Một package mới có thể yêu cầu dependency ở phiên bản cao hơn trong khi block lock được giữ từ side kia vẫn khóa phiên bản thấp. Syntax json vẫn hợp lệ nhưng composer install có thể fail hoặc package không xuất hiện đúng. Hướng an toàn là ghi dependency intent của cả hai branch, chọn một cặp composer json và composer lock hợp lệ làm baseline, rồi tái áp change còn lại bằng composer require, remove hoặc targeted update. Full composer update không nên được dùng chỉ để xóa conflict vì nó có thể đổi hàng loạt transitive package ngoài phạm vi release. Sau khi tạo result, composer validate strict kiểm tra metadata và quan hệ với lock, còn composer install dry run kiểm tra install plan trong điều kiện hiện tại. Composer show locked, composer why và composer prohibits giúp giải thích package graph. Developer cần review exact diff của composer json và lock để xác nhận package nào added, removed hoặc updated, content hash đã được tạo đúng và không có update bất ngờ. Private repository, authentication, platform extension và composer plugin policy cũng có thể làm local result khác cloud build, nên validation cần chạy trong ci hoặc integration environment tương ứng. Với adobe commerce, phải chú ý metapackage, cloud packages, quality patch tool và custom patch stack. Một lock conflict được giải sai có thể chỉ xuất hiện khi build phase cài dependency theo lock. Vì vậy merge pass ở git không có giá trị nếu dependency gate fail. Evidence nên ghi baseline đã chọn, command tái áp dependency, validation output, package delta, platform requirement và build result. Lock file không phải prose để người resolve chọn từng đoạn theo cảm giác, mà là artifact cần được solver tạo lại từ dependency intent có kiểm soát.

Adobe commerce có nhiều semantic conflict mà git không thể phát hiện. Hai module có thể thêm preference khác nhau cho cùng interface ở hai file riêng nên merge hoàn toàn sạch, nhưng merged dependency injection configuration chỉ chọn một implementation hiệu lực theo cấu hình và module load order. Hai plugin có thể cùng intercept một method, dùng sort order xung đột hoặc giả định result khác nhau. Module xml sequence có thể đổi thứ tự merge configuration. Declarative schema từ hai branch có thể thêm column, index hoặc constraint hợp lệ riêng nhưng không tương thích khi upgrade database thật. Layout, ui component, web api, graphql, acl, queue topology và cron cũng có thể merge text nhưng hỏng contract. Verification cần đi theo ladder. Đầu tiên phải hết unmerged entry và staged diff sạch. Tiếp theo chạy php lint, xml parser và composer validate. Sau đó chạy module status, dependency injection compile và inspection như dev di info cho type quan trọng. Schema change cần được test trên fresh database và database upgrade từ state đại diện production. Generated code, static content và cache phải được tái tạo từ final commit, không lấy artifact cũ của một side. Unit test kiểm tra logic hẹp, integration test kiểm tra framework wiring, api hoặc functional test kiểm tra contract, còn smoke test kiểm tra flow quan trọng trên environment đã deploy. Performance và security cũng cần review vì merge có thể thêm hai observer trên hot path, bỏ authorization check hoặc làm mất security patch. Một auto merge clean chỉ chứng minh git tạo được tree. Adobe commerce correctness chỉ được chấp nhận khi dependency, configuration, compile, data, behavior và deployment evidence cùng pass.

Workflow cloud nên giải conflict ở tầng thấp trước khi promotion, không giải mới trong lúc đưa code lên production. Task branch được tạo từ parent development environment đúng và được cập nhật bằng merge hoặc rebase theo policy của team. Nếu task branch là private, rebase có thể giúp đưa patch lên latest integration. Nếu branch đã chia sẻ, merge thường an toàn hơn vì giữ commit id mà collaborator đang dùng. Pull request cần chứa source tip, target tip, merge base, conflict list, rationale, composer result và test evidence. Sau review, final commit được merge vào integration và kích hoạt build deploy theo project. Integration là nơi kiểm tra build log, dependency install, compile, service connection và targeted flow. Khi result ổn định, code được promote lên staging theo hierarchy thật của starter hoặc pro project. Staging cung cấp môi trường gần production hơn để uat, kiểm tra fastly, new relic và third party integration. Production chỉ nhận lineage đã qua staging, cùng backup, activity monitoring và smoke plan. Branch name không nên được hardcode từ một tài liệu nếu project có cấu trúc khác hoặc external repository integration. Developer phải đọc cloud console, environment id, parent relationship và protected branch policy thực tế. Một anti pattern nguy hiểm là khi staging diverged, team chọn ours hoặc theirs ngay trên promotion branch để merge button chạy. Result mới đó chưa được integration test và có thể tạo artifact khác. Đúng hơn là dừng promotion, đưa conflict về task hoặc integration, resolve, build, test lại rồi promote cùng commit lineage. Release evidence cần nối final git commit với cloud activity, build log, staging test và production smoke. Khi có incident, chuỗi này cho biết lỗi đến từ graph integration, dependency resolution, generated artifact hay environment configuration. Workflow tốt không chỉ di chuyển code qua các nhánh, mà bảo đảm mỗi bước thêm evidence thay vì tạo một result mới chưa kiểm chứng.

Senior review của merge hoặc rebase bắt đầu bằng câu hỏi về graph và kết thúc bằng behavior đã deploy. Reviewer xác nhận working tree sạch trước operation, remote refs đã fetch, current branch và target đúng, merge base được ghi và policy rewrite phù hợp. Với rebase, backup ref phải tồn tại và range diff phải cho thấy patch intent không bị mất. Với conflict, reviewer cần thấy classification, base, ours, theirs và lý do final result có thể khác cả hai side. Staged diff được đọc như một release candidate, không như phần còn lại sau khi xóa marker. Conflict marker scan, secret scan và security review phải chạy trước commit. Composer metadata, lock consistency, php, xml, di compile, schema path và targeted tests tạo các lớp evidence khác nhau. Sau integration, reviewer kiểm tra final commit parent, remote ref, cloud activity và build artifact. Promotion lên staging và production chỉ tiếp tục khi test matrix, uat, backup, rollback owner và monitoring plan rõ. Nếu một gate không chạy, residual risk phải được ghi thay vì im lặng coi là pass.
