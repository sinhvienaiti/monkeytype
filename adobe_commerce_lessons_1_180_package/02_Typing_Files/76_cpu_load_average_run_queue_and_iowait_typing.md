Cpu utilization và load average trả lời hai câu hỏi khác nhau nên không được thay thế cho nhau. Cpu utilization mô tả tỷ lệ thời gian processor chạy user code, kernel code, interrupt hoặc ở trạng thái idle trong một interval. Load average mô tả lượng scheduling entity đang runnable hoặc ở trạng thái chờ không ngắt được theo cách linux tính load. Một server có cpu bận nhưng load vừa phải khi số task runnable gần capacity. Một server khác có cpu idle cao nhưng load lớn vì nhiều task ở trạng thái d đang chờ storage hoặc kernel resource. Ba con số load một, năm và mười lăm phút là moving average có trọng số, không phải phần trăm và không giảm ngay sau burst. Load một phút cao hơn load dài hơn thường cho thấy pressure đang tăng, còn load một phút thấp hơn cho thấy hệ thống đang hồi phục. Số cpu khả dụng tạo context, nhưng phép chia load cho cpu không phải ngưỡng tuyệt đối. Container có thể nhìn thấy nhiều cpu online nhưng chỉ được cấp quota nhỏ, hoặc affinity chỉ cho phép task chạy trên vài core. Workload web nhạy latency có thể xấu trước khi load bằng số core, trong khi batch có thể chấp nhận queue dài hơn. Engineer cần xem run queue, task blocked, cpu pressure, quota, per core utilization và request latency trong cùng timeline. Dòng cpu tổng trong proc stat là counter tích lũy từ boot, nên phải lấy delta giữa hai thời điểm. Dòng đầu của vmstat cũng thường là average dài hạn và không đại diện interval tiếp theo. Một ảnh top giúp định hướng nhưng có thể bỏ burst, process ngắn hoặc mode normalization khác. Evidence tốt phải ghi tool, version, interval, số cpu, timezone và node. Khi các metric được đặt đúng nghĩa, team không còn nói load tám nghĩa cpu tám mươi phần trăm. Team có thể phân biệt processor đang bận, task đang chờ scheduler và task đang bị block, rồi mới tìm producer thực sự.

Per core observation là bắt buộc vì aggregate có thể che single thread bottleneck. Trên máy tám logical cpu, một php process dùng trọn một core có thể chỉ tạo khoảng mười hai phần trăm aggregate. Command vẫn chậm dù tổng cpu có vẻ thấp, bởi một task single thread không tự chia công việc cho các core còn lại. Thêm core giúp chạy nhiều request hoặc process đồng thời, nhưng không tự làm một request php đơn lẻ nhanh hơn. Engineer cần xem process cpu, thread view, core gần nhất, affinity và cpu quota. Nếu một core liên tục bão hòa còn các core khác idle, nguyên nhân có thể là algorithm serial, lock serialization, một shard hot hoặc phase compile không parallel. Nếu nhiều task runnable cùng tranh core, run queue và cpu pressure tăng. Oversubscription có thể xuất hiện khi php fpm child, cron, consumer và reindex cùng chạy. Tăng thêm worker khi cpu đã saturation thường làm scheduler delay, context switch và memory tăng mà throughput không tăng. Context switch cao không tự động là lỗi vì server request vốn switch nhiều, nhưng nó đáng chú ý khi tăng mạnh cùng system time, queue và latency. Wall time cần được so với cpu time. Nếu wall time hai giây và cpu time gần hai giây, code có thể cpu bound. Nếu cpu time rất nhỏ, process chủ yếu chờ dependency, lock hoặc scheduler. Một benchmark phải dùng dữ liệu và concurrency giống production, vì micro benchmark một process có thể bỏ cache, lock và service contention. Per core metric cũng phải được đọc với simultaneous multithreading, bởi hai logical cpu trên một physical core không luôn có throughput như hai core độc lập. Quyết định tốt là tối ưu algorithm, chia work hợp lý hoặc scale concurrency theo headroom, thay vì chỉ nhìn aggregate và mua thêm core không kiểm chứng.

Iowait là metric hữu ích để đặt câu hỏi nhưng nguy hiểm nếu dùng làm kết luận. Kernel ghi iowait trong cpu accounting, song cpu không ngồi chờ một request cụ thể. Khi một task chờ i o, scheduler có thể chạy task khác trên cpu đó. Trên máy nhiều core, task chờ không gắn ổn định với một core, và kernel documentation còn cảnh báo counter iowait có thể giảm trong một số điều kiện. Vì vậy iowait cao có thể gợi ý storage pressure, nhưng iowait thấp không loại bỏ disk, database hoặc network latency. Vmstat cung cấp cột r cho runnable process, b cho process blocked, bi và bo cho block traffic, cùng wa cho iowait. Những field này cần được xem qua nhiều interval. Task ở state d thường chờ không ngắt được và được tính vào load average. Nếu load cao, cpu idle và nhiều task d xuất hiện, engineer nên xem wait channel, i o pressure và device latency thay vì tăng cpu. External api, redis hoặc opensearch cũng có thể làm request chậm với load thấp. Evidence phải thuộc đúng node và service. Một transaction trace cho biết thời gian ở application, database, search và external span, còn host metric cho biết scheduler hoặc device pressure. Khi hai lớp được nối bằng absolute time, team có thể phân biệt cpu bound, disk bound, lock bound và network wait. Không nên kill task d mù, vì signal thường chỉ được xử lý khi task rời uninterruptible wait. Root cause cần sửa storage, filesystem, query hoặc dependency tương ứng.

Steal time và cpu throttling đều làm workload thiếu thời gian chạy nhưng đến từ boundary khác nhau. Steal là thời gian virtual cpu sẵn sàng nhưng hypervisor đang chạy guest khác. Cpu throttling xảy ra khi cgroup đã dùng hết quota trong period và scheduler tạm dừng workload theo policy. Một container có host cpu idle và steal gần không nhưng vẫn chậm vì cpu stat cho thấy throttled time tăng. Ngược lại quota không chạm mà steal tăng kéo dài có thể tạo hypothesis về host contention. Noisy neighbor chỉ nên được dùng sau khi đã loại cron nội bộ, retry storm, affinity, single thread hotspot và service dependency. Engineer cần đọc cpu max, cpu stat, affinity và per cpu steal theo interval. Số cpu online không luôn là capacity thực, vì quota có thể tương đương một phần của cpu dù process nhìn thấy nhiều logical cpu. Throttling counter là tích lũy, nên cần snapshot trước và sau incident hoặc metric rate. Một spike steal đơn lẻ không đủ để escalation. Evidence nên có timestamp, environment, release, traffic, processor count, quota, steal và transaction impact. Trên cloud được quản lý, support có thể đối chiếu hạ tầng mà application engineer không thấy. Affinity cũng có thể tạo hot core khi process bị pin vào tập cpu nhỏ. Thay affinity hoặc priority không phải phản xạ an toàn, vì supervisor, numa và platform policy có thể phụ thuộc cấu hình hiện tại. Nice chỉ điều chỉnh priority tương đối của normal task và không cô lập database lock hoặc i o. Real time scheduling không phù hợp cho commerce process thông thường vì có thể làm task khác starve.
