Data Connection là extension kết nối dữ liệu Adobe Commerce với Adobe Experience Platform và Edge Network. Tên cũ của sản phẩm là Experience Platform connector, nhưng package composer vẫn có thể giữ tên cũ để tương thích ngược. Điều này dễ gây nhầm khi developer nhìn thấy package và nghĩ hệ thống chưa được nâng cấp. Data Connection không sao chép toàn bộ database Commerce sang Platform. Nó gửi các event và profile field đã được định nghĩa trong schema. Mục tiêu là phá vỡ data silo, giúp dữ liệu browsing, cart, checkout, order và customer profile có thể được dùng trong Real Time CDP, Journey Optimizer hoặc các sản phẩm Adobe khác. Với web storefront, dữ liệu thường đi qua Adobe Client Data Layer, event sdk, collector hoặc tags, rồi đến Edge Network. Với mobile app, Adobe hướng dẫn dùng Experience Platform Mobile SDK. Cài extension chỉ là bước đầu. Dự án vẫn cần organization, permission, schema, dataset, datastream, consent policy và monitoring. Nếu một trong các phần này sai, browser có thể gửi request thành công nhưng dữ liệu vẫn không xuất hiện đúng trong Platform.

Kiến trúc Data Connection có hai nguồn dữ liệu chính. Storefront phát behavioral event khi shopper xem trang, xem sản phẩm, thêm vào giỏ, bắt đầu checkout hoặc đăng nhập. Commerce backend phát back office event khi order được đặt, hủy, refund, ship hoặc hoàn tất. Backend cũng có thể gửi profile record mô tả thuộc tính customer. Behavioral và back office event là time series data, vì chúng ghi lại một hành động tại một thời điểm. Profile record là record data, vì nó mô tả trạng thái tương đối bền của một subject. Hai loại data này dùng class XDM khác nhau. Time series dùng ExperienceEvent, còn profile record dùng Individual Profile. Nếu schema chọn sai class, ingestion có thể fail hoặc data không đi vào đúng service. Người học cần tách rõ action và state. Một event sign in nói rằng hành động đăng nhập vừa xảy ra. Một profile record loyalty tier nói rằng customer hiện thuộc cấp thành viên nào. Cả hai có thể dùng cùng identity nhưng phục vụ consumer khác nhau. Việc phân loại đúng ngay từ đầu giúp downstream dùng data đúng mục đích.

Schema, field group, dataset và datastream là bốn khái niệm phải học cùng nhau. Schema định nghĩa cấu trúc data theo XDM. Field group bổ sung nhóm field chuẩn cho commerce, web, order hoặc identity. Dataset lưu data tuân theo schema. Datastream route event từ Edge Network đến dataset và Adobe service đã bật. Một event có payload đúng nhưng datastream sai có thể đi vào sandbox khác. Một datastream đúng nhưng schema thiếu Commerce field group có thể tạo validation error. Dataset không phải nơi quyết định browser gửi gì, nó chỉ nhận data theo contract. Khi onboarding, đội data nên tạo ExperienceEvent schema cho behavioral và back office event, Profile schema cho record data, rồi tạo dataset tương ứng. Mọi environment cần map rõ organization, sandbox, schema, dataset và datastream. Staging không được dùng production datastream. Nếu test data đi vào production profile, audience và journey có thể bị ô nhiễm. Cần thêm deployment validation để kiểm tra id trước khi release. Mỗi thay đổi schema cần được review như thay đổi api vì nhiều consumer có thể phụ thuộc vào field path hiện tại.

Commerce Services Connector và Data Connection configuration có vai trò khác nhau. Commerce Services Connector quản lý organization và credential cho các Commerce service. Data Connection quản lý kết nối đến Experience Platform, datastream và collection setting. Adobe hướng dẫn cấu hình connector trước, rồi mới cấu hình Data Connection. Organization id phải thuộc đúng Experience Cloud organization và có format theo Adobe quy định. Datastream id phải thuộc đúng sandbox và schema. Một user có thể switch nhiều organization, vì vậy copy organization id từ giao diện không được kiểm tra dễ dẫn đến kết nối nhầm. Production và sandbox key cũng cần được quản lý riêng. Không nên hardcode id vào source code frontend nếu config có cơ chế quản lý environment. Khi clone database production sang staging, phải kiểm tra lại các id trước khi bật cron hoặc event collection. Đây là bước thường bị bỏ qua và có thể làm staging gửi dữ liệu thật hoặc dữ liệu test vào nơi sai. Một checklist environment trước deploy giúp ngăn lỗi cấu hình lan sang nhiều dataset và journey.

Adobe Client Data Layer là lớp dữ liệu phía browser giúp component và collector trao đổi theo contract ổn định. Data layer có thể lưu state như product, cart hoặc customer context, đồng thời phát event khi action xảy ra. Tuy nhiên đẩy data vào layer không tự động gửi data tới Platform. Cần event sdk, collector, Web SDK hoặc tags rule lắng nghe và gửi request. State và event cũng không giống nhau. State cho biết context hiện tại, còn event cho biết điều gì vừa xảy ra. Nếu component publish add to cart trước khi state product và quantity được cập nhật, payload có thể thiếu sku hoặc price. Nếu SPA route thay đổi nhưng listener không được reset đúng, event page view có thể bị phát hai lần. Vì vậy test cần quan sát cả data layer và network. Chỉ nhìn request cuối không cho biết lỗi xuất phát từ component, state, mapping hay collector. Component cũng nên publish event sau khi action thật sự hoàn tất để tránh ghi nhận hành vi chưa xảy ra. Điều này giúp dữ liệu phản ánh kết quả thật thay vì chỉ phản ánh ý định click.

Commerce Events SDK cung cấp publish và subscribe cho event Commerce. Collector lắng nghe event, map sang XDM và gửi đến Edge Network. Một merchant đã dùng Adobe Experience Platform tags có thể chọn publishing only mode. Trong flow này, Commerce Events SDK chỉ publish event, còn tags với Adobe Client Data Layer và Web SDK chịu trách nhiệm mapping cùng send. Điều quan trọng là chỉ có một send path cho mỗi event. Nếu Data Connection collector và tags cùng gửi, dataset nhận duplicate. Journey có thể gửi email hai lần, event count bị phóng đại và attribution sai. Adobe hướng dẫn trong publishing only flow không cấu hình organization và datastream theo cách làm collector Data Connection gửi thêm một lần. Khi debug duplicate, kiểm tra network request, tags rule, collector config và số lần component publish. Một lỗi khác là SPA bind listener sau mỗi route, làm mỗi navigation tăng số subscriber. Idempotency phải được thiết kế cả ở source và downstream. Khi một event được đổi owner, configuration cũ cần được gỡ bỏ rõ ràng để không còn đường gửi ẩn.

Experience Platform Web SDK là lớp gửi dữ liệu từ web đến Edge Network. SDK có thể được deploy bằng tags hoặc raw code, nhưng tags thường giúp quản trị version, rule và environment dễ hơn. Mobile application dùng Mobile SDK vì không có browser data layer giống Luma. Web và mobile phải dùng identity strategy thống nhất. Nếu web gửi email đã trim và lowercase nhưng mobile gửi email nguyên dạng, Platform có thể tạo profile fragment. Nếu mobile dùng customer id trong namespace riêng mà web chỉ dùng email, identity graph cần policy rõ để stitch. Shared device cũng tạo rủi ro, vì ECID thuộc browser có thể liên hệ nhiều account theo thời gian. Đội data cần xác định cách login transition, logout và account switch được xử lý. Không nên coi identity stitching là tự động đúng chỉ vì event có identity map. Test cross channel nên dùng cùng một account và kiểm tra profile viewer để xác nhận hành vi từ hai thiết bị được nối đúng. Nếu không có test này, lỗi identity chỉ xuất hiện khi campaign đã chạy.

Identity map thường chứa ECID và email khi email khả dụng. ECID là identity pseudonymous giúp theo dõi hành vi guest trên browser. Khi shopper đăng nhập hoặc cung cấp email, event có thể thêm email identity để Platform liên kết hành vi với profile. Tài liệu đôi khi mô tả behavioral data là anonymized, nhưng việc identity map chứa email khi available cho thấy team không nên hiểu anonymous theo nghĩa không thể liên hệ tới người dùng. Cách diễn đạt chính xác hơn là guest data có pseudonymous identity và known customer data có thể được stitch theo policy. Identity governance cần định nghĩa primary identity, namespace, normalization, shared device, deletion và consent withdrawal. Không tự gửi internal customer id vào namespace tùy ý. Nếu namespace không được thiết kế, profile có thể fragment hoặc merge sai. Identity error rất khó sửa sau khi data đã đi vào nhiều dataset và audience. Identity policy cũng cần được review với đội privacy vì cách merge có thể ảnh hưởng quyền truy cập, xóa dữ liệu và phân tích customer.

Consent và privacy phải được thiết kế trước khi bật collection. Một flow phổ biến là chỉ load chức năng thiết yếu khi chưa có consent, sau đó bật analytics hoặc personalization send khi shopper đồng ý theo chính sách. Collector hoặc tags rule cần kiểm consent, không chỉ giao diện cookie banner. Nếu banner nói từ chối nhưng event vẫn gửi, đó là lỗi compliance nghiêm trọng. Data minimization yêu cầu chỉ gửi field cần cho use case. Không gửi password, token, payment card, internal note hoặc free text nhạy cảm. Data Connection có tài liệu về HIPAA readiness cho back office data, nhưng điều đó không làm merchant compliant tự động. Compliance còn phụ thuộc contract, entitlement, schema, access control, retention, audit và legal approval. Dự án cũng cần quy trình cho data subject request trên cả Commerce và Experience Platform. Xóa account trong Commerce không tự đảm bảo mọi profile fragment trong Platform đã được xử lý. Consent state nên được ghi nhận theo contract rõ ràng để downstream hiểu event nào được thu thập theo quyền nào của shopper.

Behavioral events mô tả shopper interaction như page view, product view, add to cart, remove from cart, start checkout, complete checkout, sign in và create account. Search event có thể xuất hiện khi Live Search được cài và giúp nối search request với response cùng click. Event doanh nghiệp có thể yêu cầu extension bổ sung. Không nên giả định custom product type tự động có payload giống simple hoặc configurable. Cần kiểm tra event contract và product context thật. Browser event hữu ích cho intent, nhưng không phải mọi event đều là business truth. Complete checkout ở browser có thể bị mất nếu shopper đóng tab hoặc network lỗi. Nó cũng có thể phát lại khi page refresh nếu implementation sai. Vì vậy order lifecycle quan trọng nên được xác nhận bằng back office event. Behavioral event phù hợp để hiểu journey và interaction, còn backend event phù hợp để ghi trạng thái transaction. Event name và payload cần ổn định để dashboard, audience và journey không bị hỏng khi frontend thay component. Khi Live Search hoặc extension doanh nghiệp thay đổi version, event reference cần được kiểm tra lại để tránh field cũ vẫn được gửi nhưng downstream không còn hiểu.

Back office event phát từ server và bao gồm order placed, canceled, refunded, shipped hoặc completed cùng các profile lifecycle event. Ưu điểm là không phụ thuộc browser còn mở. Nếu payment redirect thành công nhưng shopper không quay lại success page, backend vẫn có thể phát order event. Tuy nhiên server event cũng cần idempotency. Retry không nên làm journey gửi thông báo hai lần. Downstream cần event id, business key hoặc suppression rule. Event cũng có thể đến không đúng thứ tự tuyệt đối do network và retry. Journey không nên giả định shipment luôn đến sau một event khác chỉ dựa vào thời điểm ingestion. Cần dùng business timestamp và current order state khi quyết định action. Khi order completed event thiếu, kiểm tra module, queue, cron, network và Platform ingestion, không chỉ kiểm browser. Back office pipeline và storefront pipeline là hai đường độc lập có failure mode khác nhau. Status transition cũng nên được chuẩn hóa để cùng một order không phát nhiều event có ý nghĩa trùng nhau. Downstream nên kiểm tra trạng thái cuối cùng của order trước khi gửi thông báo quan trọng cho customer.

Profile record data dùng Individual Profile schema để gửi thuộc tính customer như loyalty tier, preferred store hoặc custom profile field được hỗ trợ. Record update có thể ghi đè state, vì vậy timestamp và merge policy rất quan trọng. Một source chậm không nên ghi giá trị cũ đè lên source mới. Custom profile attribute cần được thêm vào schema trước khi send. Không biến profile schema thành data dump của customer entity. Chỉ gửi field có consumer rõ như segmentation hoặc personalization. Mỗi field cần owner, source of truth, update frequency và retention. Nếu field được dùng trong audience, cần test case khi giá trị đổi, bị xóa hoặc null. Profile data cũng phải tuân thủ access control nghiêm ngặt hơn vì liên hệ trực tiếp identity. Việc field xuất hiện trong Commerce không có nghĩa Platform nên nhận nó. Profile field thay đổi chậm có thể dùng record update, còn hành động theo thời điểm nên giữ ở event để lịch sử không bị mất. Team data cần định nghĩa source priority khi cùng một field được cập nhật từ Commerce, crm và ứng dụng khác.

Custom event cho phép merchant thu thập hành vi riêng của ngành. Adobe nêu collector sẽ bao event trong xdm, thêm ECID primary identity và có thể thêm email secondary identity nếu event chứa personal email. Custom event được gửi đến Adobe Experience Platform, nhưng không tự xuất hiện trong Commerce dashboard hoặc metrics tracker. Đây là giới hạn dễ bị hiểu sai. Custom event vẫn cần schema, naming và versioning. Ví dụ merchant chăm sóc thú cưng muốn ghi subscription paused. Event chỉ nên phát sau khi pause thành công, không phải khi user mở modal. Payload có thể chứa category và reason code đã whitelist, nhưng không nên chứa free text ghi chú sức khỏe. Event cần business owner, trigger definition, duplicate rule, consent category và consumer. Nếu không có consumer, collection chỉ tạo data cost và privacy risk. Trước khi thêm custom event, team nên chứng minh event chuẩn chưa đáp ứng use case và xác định ai sẽ sử dụng data. Event không consumer nên bị loại bỏ. Schema custom cũng cần tài liệu ví dụ hợp lệ và trường hợp bị từ chối để developer hiểu contract.

Data Connection xử lý chiều dữ liệu từ Commerce lên Platform. Audience Activation là extension riêng xử lý audience từ Real Time CDP quay về Commerce. Không có Audience Activation, việc tạo audience trong Platform không làm cart price rule hoặc dynamic block tự thay đổi. Khi extension chiều ngược được cấu hình, audience membership có thể được dùng cho cart price rule, related product rule hoặc dynamic block. Tuy nhiên audience evaluation và activation có latency. Không dùng audience membership cho authorization hoặc quyền truy cập nhạy cảm. Nếu service lỗi, storefront cần default experience an toàn. Test phải bao gồm customer đủ điều kiện, customer không đủ điều kiện và thời gian chờ activation. Đội marketing và Commerce cần thống nhất audience id, expiry và fallback. Đây là vòng dữ liệu khép kín chỉ khi cả hai chiều được cấu hình. Audience id và rule mapping cần được source control hoặc ghi trong deployment record để staging và production không dùng nhầm audience. Khi audience hết hạn hoặc bị đổi logic, Commerce rule liên quan cũng phải được review để tránh personalization cũ tiếp tục chạy.

Event forwarding là capability của Adobe Experience Platform Data Collection, không phải chính Data Connection. Data Connection thu event Commerce và gửi đến Edge hoặc Platform. Event forwarding nhận data đã vào Edge, transform và gửi server side đến destination khác. Lợi ích là giảm script client và tập trung governance. Tuy nhiên event forwarding cần entitlement riêng trong các gói Adobe phù hợp. Nó có rule, data element và property riêng. Không nhầm event forwarding với Commerce webhook. Event forwarding xử lý data tại Edge sau collection. Webhook có thể gọi external endpoint đồng bộ trong Commerce action và ảnh hưởng transaction. Hai cơ chế có timing, reliability và use case khác. Một đội muốn gửi add to cart sang vendor marketing có thể dùng event forwarding nếu data đã ở Edge, thay vì thêm script vendor trực tiếp vào browser. Event forwarding rule cũng cần versioning, test environment và secret management như một integration server side thông thường. Destination bên thứ ba cần được kiểm tra data residency, retention và quyền xử lý trước khi event được forward.

Onboarding Data Connection gồm cài extension, xác nhận organization, permission, review data, tạo schema, dataset, datastream, cấu hình Commerce Services Connector và kết nối Platform. Trước production, phải test browser event, back office event và profile record. Browser network chỉ là bước đầu. Cần xác nhận dataset nhận event, schema không lỗi và identity được stitch đúng. Với back office, tạo order test rồi cancel, ship hoặc refund theo scope. Với profile, cập nhật attribute và xem merge. Nếu dùng Audience Activation, tạo test audience và xác nhận Commerce nhận membership. Mọi environment cần config riêng. Deployment pipeline nên kiểm tra datastream và organization trước khi bật event. Monitoring nên theo dõi event volume, duplicate rate, schema failure, ingestion latency, identity fragment và activation lag. Data pipeline không có monitoring sẽ chỉ được phát hiện khi campaign sai. Mỗi bước onboarding nên có owner giữa Commerce, data và marketing team. Nếu trách nhiệm không rõ, lỗi thường bị phát hiện muộn khi campaign bắt đầu. Một buổi dry run với dữ liệu test giúp phát hiện lỗi permission, field group và datastream trước khi storefront production phát event thật.

Debug event nên đi theo từng tầng. Nếu browser không gửi, kiểm tra data layer, SDK, collector, tags, consent, JavaScript error và ad blocker. Nếu Edge request thành công nhưng dataset trống, kiểm tra datastream, schema class, field group, dataset và sandbox. Nếu event duplicate, tìm hai send path, publish lặp hoặc listener SPA. Nếu profile fragment, kiểm tra email normalization, namespace, ECID continuity và merge policy. Nếu production data vào sandbox sai, kiểm tra deployment variable và config import. Nếu audience không về Commerce, xác nhận Audience Activation, destination, qualification và identity mapping. Không chạy thay đổi ở nhiều tầng cùng lúc vì sẽ mất bằng chứng. Ghi timestamp, event id và environment giúp đối chiếu browser, Edge, dataset và profile. Nên lưu sample event hợp lệ cho từng type để regression test sau mỗi upgrade. Sample này phải được làm sạch dữ liệu nhạy cảm và dùng trong môi trường test. Test cũng nên bao gồm consent từ chối, ad blocker, network retry và account switch để thấy event có bị mất hoặc duplicate không. Kết quả cần được lưu lại.

Data governance cần một data dictionary cho mỗi event và profile field. Dictionary nên có name, owner, trigger, source, schema path, identity, consent category, consumer, retention, test case và version. Event là public contract giữa Commerce, data và marketing team. Đổi tên field hoặc semantics mà không coordination có thể làm audience và journey sai nhưng không tạo technical error rõ ràng. Schema change cần review compatibility. Event volume cũng cần budget, vì duplicate hoặc event quá chi tiết tăng cost và noise. Mỗi custom event phải có lý do business. Khi use case kết thúc, event có thể được retire. Access vào dataset và profile phải theo least privilege. Data quality review nên kiểm tra null rate, unexpected value, timestamp và identity coverage, không chỉ số lượng event. Một correlation id hoặc event id nhất quán giúp tìm cùng event ở nhiều tầng. Không có id này, việc đối chiếu log thường dựa vào timestamp gần đúng và dễ nhầm. Runbook cần chỉ rõ nơi xem error ở Edge, Platform và Commerce để on call không mất thời gian tìm dashboard.

Guest và logged in không merge vì identity policy khác. Staging làm bẩn production vì datastream bị copy theo database. Audience không về Commerce vì thiếu extension chiều ngược. Consent từ chối nhưng event vẫn gửi vì collector load trước banner. Profile attribute cũ ghi đè mới vì merge policy. Mobile và web tạo hai profile vì namespace khác. Mỗi sự cố cần owner xuyên suốt pipeline, không thể đẩy hoàn toàn cho frontend hoặc data team. Runbook chung và event contract giúp giảm thời gian tranh luận. Data Connection thành công khi dữ liệu đúng, có consent, được stitch đúng và phục vụ use case, không chỉ khi extension cài thành công. Review định kỳ cũng nên loại event không còn consumer, cập nhật retention và kiểm tra field mới có làm tăng privacy risk hay không. Data quality metric nên có ngưỡng cảnh báo để team biết khi null rate hoặc duplicate rate tăng bất thường.

Điểm cần nhớ là Data Connection tạo một data pipeline, không phải một nút bật personalization. Commerce event phải được publish đúng, gửi qua một collection path, map vào XDM schema, route qua datastream, lưu trong dataset và stitch vào identity. Audience cần được tạo và nếu muốn dùng trong Commerce thì phải kích hoạt qua extension riêng. Event forwarding có thể gửi data từ Edge tới destination khác nhưng không thay Data Connection. Consent, privacy và data minimization đi cùng mọi bước. Test phải theo dõi từ source đến Platform, không dừng ở network success. Khi schema, identity và environment được quản trị tốt, Commerce data có thể hỗ trợ journey và personalization đa kênh. Khi quản trị kém, hệ thống tạo duplicate, profile fragment, dữ liệu nhầm sandbox và campaign sai đối tượng. Mỗi đội cần thống nhất định nghĩa thành công, gồm data đúng schema, đúng identity, đúng consent, đúng environment và tới đúng consumer. Chỉ đo số request là chưa đủ. Governance tốt biến event pipeline thành sản phẩm dữ liệu có lifecycle, không phải tập hợp script được thêm dần theo từng campaign.
