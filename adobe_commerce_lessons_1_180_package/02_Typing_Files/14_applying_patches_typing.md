Patch là một tập thay đổi dạng diff được áp lên code của Adobe Commerce hoặc package bên thứ ba mà project không trực tiếp sở hữu. Nó mô tả file, dòng cũ, dòng mới và context để công cụ tìm đúng vị trí. Patch khác custom module. Module mở rộng hệ thống qua contract và extension point, còn patch sửa trực tiếp source upstream trong quá trình build. Patch phù hợp với bug nhỏ, khẩn cấp hoặc fix được Adobe hay vendor cung cấp khi release hiện tại chưa tích hợp. Nó không nên trở thành cách xây business feature lớn. Mỗi patch cần có source, package, version, issue, owner, test và điều kiện remove. Nếu chỉ copy patch vào project rồi quên, team tạo một khoản nợ khó thấy cho lần upgrade sau. Trong hệ sinh thái Adobe Commerce có nhiều loại fix. Security hoặc functional fix có thể đã nằm trong patch release chính thức. Cloud Patches for Commerce cung cấp required patch cho môi trường cloud. Quality Patches Tool cung cấp quality patch riêng lẻ và cho phép xem status, detail, dependency, apply cùng revert.

Adobe Support có thể cung cấp patch theo ticket. Project cũng có thể tạo custom patch. Lựa chọn dài hạn ưu tiên upgrade khi fix đã có trong release được hỗ trợ. Nếu quality patch phù hợp exact version, Quality Patches Tool thường dễ quản lý hơn custom diff. Trên cloud, patch phải đi qua ECE Tools và deployment pipeline, không sửa trực tiếp remote node. Patch lifecycle bắt đầu bằng tái hiện issue trên source sạch. Sau đó tìm release note, quality patch hoặc support fix, kiểm tra compatibility, dependency và replacement. Patch được áp trên branch riêng, diff được review, test được chạy rồi mới deploy integration và staging. Production cần backup, rollback plan và monitoring. Sau mỗi upgrade, team phải kiểm tra patch đã được tích hợp vào core chưa, còn cần không và còn apply đúng không. Một patch không có bước retirement là patch chưa được quản trị đầy đủ. Inventory nên ghi patch identifier, package, version, ticket, owner, ngày thêm, test scope, rollback và remove condition. Quality Patches Tool giúp xem patch có sẵn, status, affected component, required patch và recommended replacement.

Apply từng patch riêng giúp dễ xác định nguyên nhân khi test fail. Revert tool loại thay đổi code của patch, nhưng không tự phục hồi dữ liệu đã được code mới ghi sai. Tool có patch log để hỗ trợ debug. Sau upgrade, không nên reapply mọi patch cũ theo thói quen. Hãy cập nhật tool, xem patch nào đã nằm trong release, patch nào được thay thế và patch nào vẫn cần. Adobe lưu ý không nên dùng số lượng lớn quality patch như một phương án bảo trì lâu dài vì upgrade sẽ phức tạp hơn. Trong Adobe Commerce on cloud infrastructure, required patch được áp trước, quality patch được chọn áp tiếp theo và custom patch trong thư mục hotfix được áp sau theo thứ tự tên file. Vì vậy filename là một phần của dependency order. Tên như fix patch không đủ rõ. Tên nên phản ánh thứ tự và mục tiêu. Custom patch phải được commit vào repository, có phần mở rộng phù hợp và được tái hiện local theo đúng order của cloud build.

Nếu patch local áp trên source chưa có required patch nhưng cloud áp sau required patch, context có thể khác và deployment fail. Không nên sửa file trực tiếp trên staging hoặc production vì build artifact sau có thể ghi đè và nhiều node trở nên không nhất quán. Với on premises, Quality Patches Tool vẫn là lựa chọn tốt khi patch có trong catalog. Custom diff có thể được quản lý bằng Composer patch plugin hoặc pipeline riêng. Tài liệu Adobe hiện hành lưu ý official Adobe provided patch nên dùng phương pháp Adobe hỗ trợ, thay vì tự đưa vào Composer patch plugin khi có Quality Patches Tool hoặc flow chính thức. Manual patch command hữu ích cho dry run và thử nghiệm, nhưng kết quả phải được đưa vào source control và build reproducible. Dry run giúp kiểm tra context mà không ghi file. Nếu công cụ hỏi file cần patch, hãy kiểm tra path header, working directory và strip level, không nhập ngẫu nhiên cho qua. Patch apply sạch không có nghĩa logic chắc chắn đúng. Context có thể vẫn khớp ở version khác nhưng surrounding behavior đã thay đổi.

Patch có thể gọi method deprecated, lặp fix đã có hoặc bỏ qua behavior mới. Compatibility cần exact package version, edition, dependency và patch order. Một patch có thể yêu cầu patch khác hoặc đã có replacement. Hai patch cùng sửa một method có thể conflict. Không nên giảm context hoặc ép apply chỉ để công cụ báo success. Hãy hiểu mục tiêu của cả hai diff, merge logic thành patch mới nếu cần và giữ test cho cả hai issue. Custom patch nên được tạo từ clean source cài theo lock file. Áp trước các patch đứng trước trong pipeline, thực hiện thay đổi nhỏ nhất rồi tạo diff chỉ cho file cần thiết. Không trộn refactor lớn với fix khẩn cấp. Không patch generated code vì artifact sẽ được tái tạo. Không đưa secret hoặc production value vào patch. Review diff phải nhìn cả dòng xóa, dòng thêm và context. Với lỗi làm tròn thuế, một thay đổi chỉ một dòng vẫn có thể ảnh hưởng quote, order, invoice, credit memo, api và export. Kích thước diff nhỏ không đồng nghĩa blast radius nhỏ.

Testing bắt đầu bằng reproduction fail trước patch. Sau patch, test direct behavior và regression xung quanh. Với rounding cần kiểm tra refund toàn phần, refund một phần, nhiều tax rate, discount, currency precision và consistency giữa order, invoice cùng credit memo. Chạy php lint, dependency injection compile và test integration liên quan. Deployment staging cần dữ liệu gần production. Patch có thể sửa code nhưng dữ liệu đã tạo trong thời gian bug tồn tại vẫn sai. Khi đó cần data audit và repair plan. Revert code không thay thế restore hoặc correction dữ liệu. Backup và rollback phải được chuẩn bị trước production. Code rollback có thể là revert deployment commit, revert quality patch, remove custom patch rồi rebuild artifact. Nếu patch có side effect dữ liệu, cần rollback hoặc repair riêng. Không chỉnh từng production node để khôi phục. Mọi node phải nhận cùng artifact qua pipeline. Sau deploy, xác nhận patch status, source runtime, behavior và metric. Một patch báo applied nhưng bug còn có thể do runtime dùng implementation khác bởi preference hoặc plugin. Debug phải kiểm tra execution path thật, không chỉ file diff.

Patch debt xuất hiện khi project có nhiều patch không owner, tên không rõ, không test, chồng cùng package và luôn phải merge thủ công khi upgrade. Cách giảm debt là ưu tiên release mới, giữ patch inventory, review từng patch trong upgrade và loại bỏ patch đã obsolete. Centralized patching hữu ích với nhiều project, nhưng vẫn cần mapping version chính xác và project specific exception. Một package patch dùng cho version này không được mặc định áp cho version khác. Deterministic build yêu cầu lock file, patch artifact và tool version nhất quán giữa local, ci và production. Best practice là dùng phương pháp chính thức phù hợp, test ở development và staging, giữ custom diff nhỏ, áp từng patch khi có thể, review dependency và order, có backup cùng rollback, ghi owner và remove condition, rồi kiểm tra lại sau mỗi upgrade. Anti pattern gồm patch business feature lớn, sửa production bằng tay, ép patch khi context không khớp, chỉ test trang lỗi, quên data side effect và reapply mọi patch cũ. Patch là công cụ hữu ích khi có kỷ luật. Không có lifecycle và test, nó trở thành một fork âm thầm của upstream code.
