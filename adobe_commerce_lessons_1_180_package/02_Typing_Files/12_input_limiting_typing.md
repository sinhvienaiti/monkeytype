Input limiting là việc đặt ranh giới rõ ràng cho kích thước, số lượng, độ sâu và độ phức tạp của dữ liệu mà một api được phép nhận. Validation thông thường kiểm tra dữ liệu có đúng kiểu, đúng format hoặc đúng business rule hay không. Tuy nhiên, một request có thể hoàn toàn đúng schema nhưng vẫn gây quá tải nếu chứa quá nhiều phần tử hoặc yêu cầu hệ thống thực hiện quá nhiều công việc. Giả sử một api nhận hồ sơ tuân thủ của nhà cung cấp. Mỗi hồ sơ có thể có mã nhà cung cấp, metadata, tài liệu và đơn vị kinh doanh được áp dụng. Nếu request chứa hàng nghìn hồ sơ, hệ thống có thể tạo rất nhiều database query, upload, message và audit record. Vì vậy developer cần hỏi không chỉ dữ liệu có hợp lệ không, mà còn một request hợp lệ tối đa được phép tốn bao nhiêu resource. Input limiting giúp từ chối request vượt ranh giới trước khi php, database, queue hoặc external service phải xử lý phần việc nặng. Input limit, output limit và rate limit giải quyết ba vấn đề khác nhau. Input limit kiểm soát một request được phép lớn hoặc phức tạp đến đâu.

Output limit kiểm soát server được phép trả về bao nhiêu dữ liệu. Rate limit kiểm soát một actor được gửi bao nhiêu request trong một khoảng thời gian. Chỉ dùng một lớp là chưa đủ. Một attacker có thể gửi rất nhiều request nhỏ để vượt qua input limit, hoặc gửi một request cực nặng nhưng vẫn nằm trong rate quota. Một list endpoint có input ngắn nhưng trả hàng trăm nghìn record cũng gây memory và network lớn. Thiết kế an toàn thường kết hợp giới hạn body, item count, page size, query depth, response size và request rate. Mỗi lớp cần được đặt ở vị trí phù hợp. Gateway và web server chặn payload quá lớn sớm. Application hiểu business cardinality. Repository và database cần pagination. Queue cần producer quota. Monitoring cần quan sát rejection và chi phí thực tế. Giới hạn không nên được chọn tùy ý. Trước hết cần lập cost model cho operation. Với mỗi item đầu vào, hãy xác định số database query, entity load, row write, external call, queue message và lượng memory có thể phát sinh. Một dòng hồ sơ có thể yêu cầu kiểm tra quyền, load hợp đồng, lưu metadata, upload tệp, gọi dịch vụ quét, tạo audit và gửi message.

Khi request chứa nhiều dòng, chi phí được khuếch đại. Dữ liệu production giúp chọn ranh giới hợp lý. Hãy xem số item thông thường, trường hợp hợp lệ lớn nhất, latency ở percentile cao, memory peak và transaction time. Limit phải đủ cho business thực tế nhưng không để operation trở thành vô hạn. Cũng cần kiểm tra request đồng thời gần limit, vì một request đơn lẻ có thể chạy được nhưng nhiều request cùng lúc vẫn làm cạn worker hoặc database connection. REST search criteria cần được review đặc biệt. Tài liệu Adobe nêu rằng page size xác định số item tối đa được trả về và nếu client không truyền page size, hệ thống có thể trả toàn bộ kết quả khớp. Với bảng nhỏ, lỗi này khó nhận ra. Khi dữ liệu tăng, collection có thể load rất nhiều row, extension attribute tạo thêm query và serialization làm memory tăng mạnh. Không nên chỉ ghi trong tài liệu rằng client phải phân trang. Server cần default an toàn, maximum rõ ràng hoặc custom facade bắt buộc pagination. Page hiện tại quá lớn cũng có thể làm offset query đắt vì database phải bỏ qua nhiều row.

Với export hoặc đồng bộ dài, pagination theo khóa ổn định và checkpoint thường an toàn hơn. Search endpoint còn cần giới hạn số filter, số value trong điều kiện in, độ dài value, field được filter và condition type được phép. Graphql có nhiều chiều cần giới hạn. Page size giới hạn số item một field list trả về. Query depth giới hạn độ sâu của cây dữ liệu, đặc biệt quan trọng với category tree hoặc hierarchy tùy biến. Query complexity giới hạn số field, object và fragment contribution trong query. Tài liệu Adobe hiện hành mô tả các giá trị mặc định, nhưng project không nên chỉ ghi nhớ con số. Threshold cần được kiểm tra với query thật và dữ liệu thật. Complexity không phải cost model hoàn hảo. Một field tùy biến có thể gọi dịch vụ bên ngoài cho từng sản phẩm dù cấu trúc query nhìn qua khá nhỏ. Một resolver có thể gây n cộng một query. Vì vậy developer vẫn phải dùng batching, caching, timeout, authorization sớm và page size. Mutation cũng cần giới hạn số phần tử trong input array, vì complexity của selection set không tự động phản ánh số item được ghi. Request body, string, array và nested object đều cần ranh giới riêng.

Body size nên được giới hạn ở cdn, gateway, web server, php và application. Lớp hạ tầng chặn payload lớn trước khi parse, còn application đưa ra lỗi theo business semantics. String quá dài có thể làm log phình, regex đắt, database lỗi hoặc search query nặng. Array cần maximum item và cần loại duplicate trước khi xử lý. Một danh sách lặp cùng identifier nhiều lần vẫn có thể tạo công việc dư thừa. Với cây nested, chỉ giới hạn số child mỗi node là chưa đủ. Cần giới hạn cả depth, tổng node và tổng kích thước chuỗi. Một cây có ít child nhưng rất nhiều tầng vẫn có thể gây recursion sâu và memory lớn. File upload cần kiểm soát nhiều hơn kích thước mỗi file. Hệ thống cần giới hạn số file, tổng request size, loại tệp, mime thực, kích thước sau giải nén, kích thước ảnh, thời gian scan và storage quota. Custom api nhận file dưới dạng dữ liệu mã hóa dạng văn bản cần nhớ rằng dữ liệu encoded lớn hơn binary gốc. Trong một số flow, memory còn giữ đồng thời chuỗi encoded và decoded. Không nên giữ database transaction mở trong lúc upload tới remote storage hoặc chờ malware scanner.

Có thể tạo record trạng thái pending, commit transaction ngắn rồi xử lý tệp bằng job nếu business cho phép. Lỗi phải được trả trước khi một phần lớn dữ liệu đã được lưu hoặc external service đã bị gọi nhiều lần. Bulk operation cần ranh giới về batch size và transaction. Synchronous request phù hợp khi số item nhỏ, thời gian xử lý nằm trong request budget và client cần kết quả ngay. Khi dữ liệu lớn hơn, client có thể chia thành chunk. Mỗi chunk cần identifier ổn định, duplicate policy, idempotency và kết quả cho từng item. Export, import hoặc file processing lớn thường phù hợp với asynchronous job. Api trả job identifier, trạng thái ban đầu và cách lấy kết quả sau đó. Queue không tự loại bỏ rủi ro quá tải. Nếu producer tạo message nhanh hơn consumer, backlog vẫn tăng vô hạn. Vì vậy route tạo job cần quota, maximum item và monitoring queue depth. Chuyển toàn bộ sang queue mà không giới hạn producer chỉ chuyển nơi xảy ra outage. Authorization và limit validation phải chạy trước heavy work. Một flow tốt thường xác thực actor, kiểm tra quyền, validate shape, kiểm tra count, size, depth và page size, loại duplicate rồi mới load repository hoặc gọi external service.

Nếu code load hàng nghìn entity rồi mới phát hiện actor không có quyền, attacker vẫn tiêu thụ resource dù cuối cùng nhận access denied. Nếu validator nằm sâu trong service sau khi collection đã load, limit tồn tại về mặt chức năng nhưng không bảo vệ availability. Trace thứ tự method và database query giúp phát hiện lỗi này. Test cần bao gồm ngay dưới limit, đúng limit, vượt limit một đơn vị, input trùng, input rỗng, nested sâu và nhiều request đồng thời gần limit. Không nên rải magic number trong controller, resolver và service. Một policy object giúp tập trung maximum page size, maximum item và maximum filter. Validator dùng policy trước khi bắt đầu xử lý. Limit có thể khác giữa guest, customer, admin và trusted integration, nhưng mọi actor vẫn cần hard ceiling. Configurable limit giúp vận hành linh hoạt nhưng có thể bị đặt quá cao. Vì vậy configuration cần safe default, validation range, audit log và giới hạn tuyệt đối trong code hoặc hạ tầng. Khi thay đổi limit, cần theo dõi rejection theo route và identity. Một con số phù hợp hôm nay có thể cần điều chỉnh khi business flow, dữ liệu hoặc hạ tầng thay đổi.

Error contract cần rõ ràng và nhất quán. Client nên biết loại giới hạn bị vượt, maximum được phép và có thể chia request hay dùng job thay thế không. Không cần trả stack trace hoặc chi tiết capacity nhạy cảm. Với custom rest api, lỗi validation, payload quá lớn và rate limit có thể thuộc các nhóm status khác nhau, nhưng mapping phải thống nhất với framework và contract của project. Graphql thường trả lỗi trong phần errors, vì vậy client không nên chỉ nhìn http status. Nếu server âm thầm giảm page size, response phải cho biết page size thực tế và thông tin page. Nếu không, client có thể tưởng dữ liệu bị mất. Trong nhiều trường hợp, reject rõ ràng dễ hiểu hơn clamp âm thầm. Thêm limit vào api đang hoạt động có thể làm integration cũ lỗi. Một client có thể đã gửi batch rất lớn trong nhiều năm vì server trước đây không chặn. Rollout an toàn bắt đầu bằng đo input hiện tại, xác định client vượt ranh giới dự kiến và cung cấp cách chia batch hoặc asynchronous alternative. Có thể ghi warning và metric trước khi enforce, sau đó bật limit theo giai đoạn.

Compatibility không có nghĩa là giữ endpoint vô hạn mãi mãi. Nếu contract cũ không thể sửa an toàn, cần version mới hoặc migration plan. Monitoring sau rollout phải phân biệt request abuse với business flow hợp lệ để tránh chặn hoạt động quan trọng. Khi debug endpoint chậm, hãy ghi nhận body size, item count, filter count, page size, depth, complexity và response bytes mà không log secret hoặc toàn bộ tài liệu nhạy cảm. Sau đó dùng profiler hoặc tracing để tìm amplification. Đếm database query, external call, queue message, loop iteration và serialization time. Một input nhỏ vẫn có thể tạo output lớn hoặc resolver đắt. Kiểm tra validator có chạy trước repository không. Test trên dữ liệu production like, vì limit tưởng an toàn trên database nhỏ có thể không an toàn khi bảng có hàng triệu row. Theo dõi percentile latency, memory, rejection rate và client identity giúp chọn threshold chính xác hơn. Một số anti pattern phổ biến là chỉ validate kiểu dữ liệu, tin client luôn phân trang, chỉ giới hạn request body, chỉ dựa vào graphql complexity, rải magic number và chuyển mọi việc sang queue. Payload nhỏ vẫn có thể yêu cầu cây sâu hoặc response lớn.

Query ít field vẫn có thể gọi external service nhiều lần. Queue không quota vẫn bị backlog. Clamp page size mà không trả metadata làm client hiểu sai. Một maximum giống nhau cho mọi actor có thể không phù hợp, nhưng bỏ hard ceiling cho integration tin cậy cũng nguy hiểm. Security review nên hỏi một request hợp lệ tối đa tạo bao nhiêu query, ghi bao nhiêu row, gọi bao nhiêu service và giữ resource bao lâu. Nếu chưa trả lời được, endpoint chưa có ranh giới vận hành rõ. Best practice là giới hạn body ở hạ tầng, giới hạn cardinality trong application, bắt buộc pagination cho list lớn, review graphql depth và complexity cùng resolver cost, giới hạn input array của mutation, loại duplicate, giữ transaction ngắn và dùng async cho công việc dài. Authorization và limit validation phải diễn ra trước heavy work. External call cần timeout. Luồng tạo message vẫn phải có quota rõ ràng. Limit cần safe default, hard ceiling, test ở ranh giới và migration plan cho client cũ. Input limiting không chỉ là một control security. Nó còn làm api contract rõ ràng, latency dễ dự đoán, capacity planning thực tế hơn và failure có kiểm soát hơn.
