Một release đáng tin không bắt đầu từ tên phiên bản mà bắt đầu từ chuỗi bằng chứng nối source với thứ đang chạy. Commit nhận dạng snapshot đã được review. Tag đặt tên cho một object trong git. Package version là giá trị mà composer dùng khi giải dependency. Lock entry ghi version và reference chính xác mà project đã chọn. Archive hoặc build artifact chứa byte được phân phối. Deployment record nối artifact đó với môi trường. Nếu đội chỉ ghi rằng production dùng phiên bản một chấm bốn chấm hai, họ vẫn chưa biết tag có trỏ đúng commit hay không, archive có được tạo từ working tree sạch hay không, lock có đổi thêm package nào hay không và artifact được test có phải artifact được deploy hay không. Lightweight tag chỉ là một ref trực tiếp tới object, nên phù hợp với marker tạm. Annotated tag tạo tag object có tagger, thời gian, message và có thể chứa signature, nên phù hợp hơn với public release. Phép peel giúp đi qua tag object để lấy commit đích. Signature hợp lệ chứng minh tag object khớp chữ ký của key mong đợi, nhưng không chứng minh code không có lỗi, test đã pass hoặc archive không bị thay. Reviewer cần tách cryptographic identity khỏi quality evidence. Quy trình release nên lưu commit sha, tag object id, peeled commit, kết quả verify, lock hash, artifact hash, pipeline và deployment activity. Chuỗi này cho phép điều tra một incident bằng object cụ thể thay vì dựa vào nhãn. Khi thiếu một mắt xích, cùng tên version có thể che nhiều trạng thái khác nhau. Nguyên tắc quan trọng nhất là tag và artifact đã công bố phải bất biến. Nếu release có lỗi, publisher phải phát hành version mới thay vì sửa ý nghĩa của version cũ.

Semantic versioning dùng ba thành phần major, minor và patch để công bố ý định compatibility của public api. Major tăng khi contract không còn tương thích ngược. Minor tăng khi có chức năng mới nhưng vẫn giữ compatibility. Patch tăng cho sửa lỗi tương thích. Mô hình chỉ có ý nghĩa khi publisher định nghĩa public contract đủ rõ. Trong adobe commerce, contract có thể là service contract, graphql schema, event, message payload, configuration path hoặc hành vi dữ liệu mà hệ thống ngoài dựa vào. Một method public không tự động là api ổn định, và một thay đổi xml không đổi chữ ký php vẫn có thể phá extension khác. Pre release đứng sau dấu gạch ngang và có precedence thấp hơn final version tương ứng. Build metadata đứng sau dấu cộng và không thay đổi precedence, nên không thể dùng metadata để buộc dependency solver coi một build là release mới hơn. Version trước một chấm không được xem là stable theo cùng nghĩa với major một, vì vậy consumer phải thận trọng hơn. Giới hạn lớn nhất của semantic versioning là con người phải phân loại thay đổi. Version number không tự chạy compatibility test và không phát hiện hidden contract. Một patch release vẫn có thể gây lỗi do publisher vi phạm quy ước, do consumer dùng private implementation, do data migration hoặc do behavior thay đổi ở tầng không được mô tả. Senior developer đọc semantic version như claim của publisher rồi yêu cầu evidence tại consumer. Evidence gồm changelog, api diff, dependency matrix, setup upgrade, compile, regression và quan sát staging. Semantic versioning giúp giao tiếp và giúp constraint có ý nghĩa, nhưng không thay thế review hay test. Khi một nhóm tranh luận nên tăng minor hay major, họ cần liệt kê consumer contract bị tác động và bằng chứng compatibility thay vì chọn số theo cảm giác. Một version policy tốt nêu rõ phạm vi api, cách xử lý deprecation, thời gian hỗ trợ và quy tắc cho security fix. Nếu policy không tồn tại, constraint của consumer dựa trên một lời hứa mơ hồ.

Composer constraint phải được đọc như một tập version được phép chứ không phải một chuỗi trang trí trong file cấu hình. Exact constraint chỉ cho một version. Range dùng toán tử so sánh và có thể kết hợp điều kiện and hoặc or. Wildcard một chấm bốn sao cho phép các patch trong minor một chấm bốn. Tilde một chấm bốn chấm hai giữ major và minor rồi cho patch tăng tới trước một chấm năm. Caret một chấm bốn chấm hai cho phép update tương thích tới trước hai chấm không theo giả định semantic versioning. Điểm dễ sai nằm ở package trước một chấm. Caret không chấm ba chỉ cho dải không chấm ba và loại không chấm bốn, còn caret không chấm không chấm ba chỉ cho patch rất hẹp. Solver xét constraint của toàn graph, repository priority, platform requirement và stability. Resolution thành công chỉ nói metadata giao nhau, không nói runtime chắc chắn tương thích. Minimum stability là admission boundary ở root project. Candidate kém ổn định hơn mức đó bị loại trừ trừ khi requirement cụ thể mở bằng stability flag. Prefer stable chỉ ưu tiên candidate stable khi có lựa chọn tương thích, nó không cấm dev package. Hạ minimum stability của toàn project xuống dev để cài một package là thay đổi rộng có thể đưa nhiều transitive dev version vào lock. Lựa chọn an toàn hơn là ngoại lệ hẹp, fixed reference, test bổ sung và exit plan. Reviewer phải mở rộng constraint thành boundary cụ thể, đọc stability flag, kiểm tra package nào đổi trực tiếp và package nào đổi theo dependency. Constraint tốt cân bằng khả năng nhận fix với giới hạn compatibility thực tế của publisher và dự án. Một cách review hữu ích là ghi lower bound, upper bound và các boundary version ngay trong pull request. Sau đó chạy lệnh giải thích dependency để biết package nào ngăn candidate mong muốn. Cách này phân biệt lỗi do constraint trực tiếp, lỗi do transitive dependency và lỗi do platform. Không nên mở range rộng chỉ để solver hết báo đỏ.

Composer json mô tả dependency intent của root project, gồm package trực tiếp, constraint, repository, autoload, script, plugin policy và platform configuration. Cùng application commit có thể nhận graph khác vào hai ngày khác nhau nếu repository có release mới. Workflow tốt thực hiện update trong branch riêng, giới hạn package mục tiêu, review toàn bộ lock diff, chạy validation, clean install và test, sau đó commit cả composer json và lock. Partial update vẫn có thể thay transitive dependency nên không được chỉ nhìn package trực tiếp. Lock content hash giúp phát hiện intent và resolution lệch, nhưng không nên sửa hash thủ công để tắt cảnh báo. Application adobe commerce cần commit root lock để local, ci, staging và production dùng cùng package set. Reusable library có thể không commit lock vì cần test nhiều combination, nhưng consumer application vẫn phải lock. Platform requirement cũng là một phần graph. Config platform có thể làm resolution ổn định nhưng có thể che runtime thật thiếu extension. Lệnh kiểm tra platform phải chạy trên runtime build hoặc deploy thật. Bỏ qua platform requirement chỉ bỏ guard, không tạo extension và không sửa incompatibility. Khi incident xảy ra, đội cần ghi application commit, lock hash, composer version và package inventory trước khi thử thay đổi, vì đó là baseline để so sánh và rollback. Source và dist là hai cách phân phối package khác nhau. Source thường lấy working copy từ hệ thống quản lý phiên bản và hữu ích khi debug hoặc đóng góp sửa lỗi. Dist là archive đã đóng gói, thường nhanh hơn và là lựa chọn phù hợp cho stable production install. Cả hai phải đại diện cho cùng release, nhưng version label một mình không chứng minh điều đó. Reproducible build cũng không nên bị rút gọn thành câu có lock là đủ.
