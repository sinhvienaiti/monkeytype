Graphql trong Adobe Commerce là một public contract mô tả client được gọi operation nào, truyền input gì và nhận output theo type nào. Nó không phải database schema. Database schema mô tả bảng, cột, index và constraint, còn graphql schema mô tả query, mutation, argument, field, resolver, cache policy và deprecation. Một field graphql có thể lấy dữ liệu từ cột thường, eav attribute, extension attribute, configuration, repository, bảng riêng hoặc dịch vụ ngoài. Vì vậy thêm cột không làm api tự có field, còn thêm field không nhất thiết phải tạo cột. Khi mở rộng schema hiện có, developer cần bắt đầu từ nhu cầu business và response tree, không bắt đầu từ việc sao chép một resolver mẫu. Ví dụ storefront cần hiển thị lựa chọn bảo hành và sửa chữa cho từng sản phẩm. Dữ liệu có thể phụ thuộc product, store, website và vùng phục vụ. Thiết kế phải xác định field thuộc product interface hay một query riêng, dữ liệu public hay private, có cache được không và cách invalid khi chính sách thay đổi. Mục tiêu cuối cùng là contract ổn định, an toàn và đủ nhanh cho storefront, không chỉ là làm field xuất hiện trong công cụ introspection.

Adobe Commerce cho phép mỗi module đóng góp một file schema và stitch tất cả thành một schema thống nhất. Khi hai module khai báo cùng loại node và cùng tên, framework hợp nhất các phần tương ứng. Nhờ vậy module tùy chỉnh có thể thêm field vào product interface, store config hoặc enum mà không sửa file lõi. Tuy nhiên schema stitching cũng tạo rủi ro collision. Hai extension có thể cùng dùng một field name nhưng định nghĩa type, nullability, resolver hoặc ý nghĩa khác nhau. Đây là conflict public api chứ không chỉ là lỗi cấu hình. Pull request cần tìm field name trên toàn codebase, kiểm tra module dependency và build schema trong pipeline. Nếu field đã tồn tại, khai báo lại có thể thay description hoặc resolver. Thay resolver lõi ảnh hưởng mọi storefront đang dùng field đó nên cần review behavior, authorization, cache và performance. Thêm field mới thường an toàn hơn thay âm thầm semantics cũ. Client cũ không yêu cầu field mới nên vẫn chạy, còn client mới chủ động thêm field vào selection set. Schema evolution vẫn cần compatibility plan vì endpoint graphql không có version trong url để tự cô lập thay đổi.

Để mở rộng đúng node, developer phải lần theo response tree. Query products trả một result object, result có items và mỗi item triển khai product interface. Nếu dữ liệu thuộc từng sản phẩm, field thường nằm trên product interface. Nếu dữ liệu mô tả cả danh sách, field có thể thuộc result object. Nếu cần operation mới, mới mở rộng Query hoặc Mutation. Nếu dữ liệu chỉ có ý nghĩa với một product type, concrete type có thể phù hợp hơn interface chung. Đưa field riêng của gift card lên mọi product khiến hầu hết item trả null và làm contract khó hiểu. Input và output cũng là hai contract riêng. Thêm output field không làm field đó tự trở thành filter, sort hoặc mutation input. Muốn filter theo custom attribute còn phải kiểm tra metadata, input type và query implementation. Nullability là quyết định quan trọng. Field non null hứa rằng resolver luôn có dữ liệu. Nếu external service lỗi hoặc một product type thiếu key, null bubbling có thể làm parent branch biến thành null. Không nên dùng dấu bắt buộc chỉ vì dữ liệu thường tồn tại trong happy path.

Resolver nhận field metadata, request context, resolve info, parent value và argument. Context cung cấp thông tin như user, store và các extension data của request. Resolve info mô tả selection tree và có thể hỗ trợ tối ưu load. Parent value là dữ liệu resolver cha đã chuẩn bị. Đây là đầu vào thường bị bỏ phí. Nếu product parent đã có sku, id, model hoặc service group, resolver con nên dùng lại thay vì gọi product repository thêm một lần. Args chứa input client truyền và vẫn cần business validation dù schema đã kiểm tra scalar type. Resolver nên mỏng. Nó đọc context, validate argument, gọi application service và chuyển kết quả sang output shape. Transaction phức tạp, query nhiều bảng và external call policy nên nằm ở service phù hợp. Resolver cũng phải chuyển exception sang error contract an toàn, không để production lộ sql, path hoặc stack trace. Khi một resolver phụ thuộc key nội bộ như model, cần kiểm tra mọi concrete product type và test upgrade vì key đó có thể là implementation detail chứ không phải public schema contract.

Lỗi n cộng một xuất hiện khi field trên mỗi item thực hiện một query riêng. Một product list có nhiều item và resolver service option gọi database theo từng sku sẽ tạo một query danh sách cộng nhiều query con. Khi client lồng thêm branch, số lần load tăng nhanh. Adobe khuyến nghị batch resolver cho query vì framework có thể gom request của cùng field, lấy danh sách parent key, load dữ liệu một lần và phân phối result về từng branch. Batch service contract resolver còn tách việc chuyển request thành criteria và gọi service nhận danh sách criteria. Tư duy quan trọng không chỉ là chọn đúng interface. Dữ liệu phải được gom theo key ổn định, query có index phù hợp, result được group chính xác và batch vẫn có giới hạn memory. Nếu external api chỉ nhận một số lượng item nhất định, service cần chia chunk. Page size lớn không được biến một batch thành tải vô hạn. Performance test nên đo query count và external call count khi tăng số item, thay vì chỉ đo một query nhỏ trên máy local.

Graphql schema không tự bảo vệ field nhạy cảm. Token cho biết caller là ai, còn authorization quyết định caller được xem entity hoặc field nào. Resolver order, cart, customer hoặc company phải kiểm tra ownership và scope. Không được nhận customer id từ args rồi trả dữ liệu chỉ vì token hợp lệ. Store và website boundary cũng là authorization và visibility concern. Một sku tồn tại trong catalog không có nghĩa nó được assign hoặc visible ở store hiện tại. Resolver dùng admin scope để lấy đủ data có thể vô tình bỏ qua website assignment hoặc rule storefront. Với field bảo hành, public label có thể cho guest xem, nhưng internal repair cost, supplier contract và company entitlement không được expose. Service layer nên thực thi policy để cùng logic được dùng ở graphql, rest và process nội bộ. Error strategy cần nhất quán. Có trường hợp authorization failure nên trả error rõ, có trường hợp field nullable theo product type. Không nên biến mọi lỗi thành null im lặng vì client sẽ không phân biệt không có dữ liệu với bị từ chối.

Cache cần được thiết kế cùng schema, không thêm sau khi production bị chậm. Một query chỉ cacheable khi contract và identity phù hợp. Identity class trả cache tag từ resolved data để đúng result bị invalid khi entity thay đổi. Nếu service option phụ thuộc product, service group và store configuration, identity chỉ chứa product tag có thể chưa đủ. Developer phải lập dependency map, xác định entity nào ảnh hưởng output, save path clean tag nào và response mang tag nào. Tag quá ít gây stale, còn tag quá nhiều làm metadata và purge tốn kém. Field phụ thuộc customer hoặc company còn nguy hiểm hơn. Nếu query public cacheable nhưng resolver đọc private context, một user có thể nhận result của user khác. Không nên giải quyết bằng customer id trong public cache key vì cardinality tăng lớn và mất khả năng chia sẻ. Tốt hơn là tách public service information khỏi private entitlement, rồi dùng query yêu cầu token hoặc policy không cache phù hợp. Khi debug stale, phải phân biệt client cache, edge cache, full page cache cho graphql get, resolver result cache và domain cache.

Mở rộng store config là trường hợp không cần viết resolver riêng nếu Adobe đã cung cấp extension point. Module thêm configuration path vào data provider ở area graphql, rồi khai báo field tương ứng trên StoreConfig. Cách này vẫn cần review bảo mật. Chỉ configuration an toàn cho storefront mới được expose. Api key, shared secret, internal endpoint, margin rule và credential không được thêm vào public schema. Configuration storage thường là string, trong khi schema có thể công bố boolean hoặc integer, nên conversion phải đúng. Kết quả cũng phải theo store context hiện tại. Test default scope chưa đủ cho hệ thống nhiều website và store view. Có thể cấu hình service support bật ở một store nhưng tắt ở store khác. Nếu resolver hoặc provider đọc nhầm global scope, client nhận behavior sai mà không có exception. Configuration cache và graphql result cache còn có thể giữ value cũ, vì vậy test cần thay config qua flow thật, clean hoặc invalid đúng layer và xác nhận query mới trả scope chính xác. Khi thêm config mới, review cần ghi rõ ai sở hữu setting, scope nào được phép override và field có cần xuất hiện khi feature bị tắt hay không.

Eav custom attribute, extension attribute và graphql field giải quyết ba vấn đề khác nhau. Eav attribute là cách lưu metadata và value linh hoạt cho entity như product hoặc customer. Extension attribute mở rộng data interface và service contract, nhưng module vẫn phải populate và persist dữ liệu. Graphql field công bố data shape cho graphql client. Một graphql resolver có thể đọc extension attribute, nhưng extension attribute không tự đảm bảo field xuất hiện, authorization đúng hoặc query nhanh. Với product custom attribute, các phiên bản Adobe Commerce hiện hành có contract generic và metadata query hỗ trợ nhiều trường hợp. Trước khi tạo field riêng cho từng attribute, developer cần xem client có thể dùng contract có sẵn không. Tạo hàng trăm field riêng làm schema lớn, introspection nặng và code generation phức tạp. Field riêng hợp lý khi dữ liệu có semantics business rõ, output là object tính toán hoặc cần resolver đặc thù. Quyết định nên dựa vào ổn định của contract, cách filter, cache, authorization và nhu cầu storefront, không dựa vào việc cách nào viết nhanh nhất.

Enum và interface cần được xem như contract với generated client. Nhiều module có thể stitch thêm enum value, nhưng app mobile hoặc frontend dùng exhaustive switch có thể crash khi server trả value mới chưa biết. Client nên có unknown fallback và team cần coordination khi mở rộng enum. Field trên interface phải có semantics nhất quán cho mọi concrete type. Nếu simple product có service group nhưng bundle product không có, resolver phải định nghĩa fallback rõ hoặc field chỉ nên nằm trên type phù hợp. Khi tạo interface hoặc union mới, type resolver quyết định object runtime thuộc concrete graphql type nào. Nếu module chỉ thêm field vào interface có sẵn, thường không cần type resolver mới. Nullability trên interface phải tương thích với implementation. Schema validation bắt được nhiều lỗi cấu trúc, nhưng không bắt được trường hợp resolver thường xuyên trả dữ liệu sai nghĩa. Contract test phải chạy nhiều product type, store và customer context. Introspection chỉ chứng minh field tồn tại, không chứng minh business semantics đúng. Trước khi mở rộng enum dùng chung, team nên kiểm tra schema diff, client generation và release cadence của ứng dụng mobile vốn không thể cập nhật đồng thời với backend.

Query dùng để đọc và mutation dùng để thay đổi state. Không nên tạo query vừa trả dữ liệu vừa đặt lịch sửa chữa, trừ lượt bảo hành hoặc tạo service request. Query có thể được cache, prefetch và gọi lại nên side effect dễ bị lặp. Mutation cần input type rõ, output ổn định, authentication, authorization, validation, transaction và idempotency nếu client retry. Graphql request có thể trả http success nhưng payload chứa errors, nên client phải đọc cả data và errors. Partial data là đặc trưng quan trọng. Một field lỗi có thể trả null trong khi branch khác thành công. Nếu field non null lỗi, null có thể lan lên parent. Vì vậy error policy và nullability phải được thiết kế cùng nhau. External service failure cần timeout, fallback hoặc circuit breaker phù hợp. Không để php worker chờ vô hạn. Nếu service tạm thời lỗi, không nên cache error quá lâu. Server log cần operation name, correlation id, field path, store và user type an toàn, nhưng không ghi token hoặc dữ liệu cá nhân không cần thiết.

Graphql cho client chọn response shape nên có thể giảm over fetching trên network, nhưng backend vẫn có thể tải thừa. Resolver luôn load toàn bộ entity graph dù client chỉ hỏi một field vẫn gây lãng phí. Resolve info có thể giúp biết selection, nhưng không nên để mỗi resolver tự parse tree phức tạp nếu provider design tốt hơn. Collection cần chọn column cần thiết và bảng riêng phải có index theo key batch thực tế. External api không nên được gọi cho từng product. Có thể dùng batch endpoint, local projection đồng bộ bằng queue hoặc cache domain. Cần đo resolver duration, query count, batch size, response size, external call count, cache hit và error theo field path. Client production nên gửi operation name để dashboard phân nhóm query. Nếu mọi request đều anonymous, incident khó xác định operation nào gây tải. Query depth và complexity là lớp bảo vệ, nhưng không thay pagination và efficient resolver. Tăng limit để query tùy chỉnh chạy được có thể mở cửa cho query khác tiêu tốn tài nguyên hơn.

Security review cần bao gồm query depth, complexity, page size, string length và nested collection. Một product list chứa service options, mỗi option chứa nhiều location và mỗi location chứa calendar có thể tạo response rất lớn. Đôi khi query riêng có pagination tốt hơn thêm một tree sâu vào product. Introspection hữu ích cho development và code generation. Adobe cho phép disable introspection ở production như một lớp hardening, nhưng việc đó không thay authorization. Token thường phù hợp hơn session cookie cho graphql application theo khuyến nghị Adobe, song resolver vẫn phải dùng context đúng. Input strongly typed không ngăn client gửi string rất dài hoặc list lớn. Mutation cần clamp batch size và validate business relation giữa argument. Rate limit và web application firewall có thể hỗ trợ, nhưng root cause vẫn phải được xử lý trong schema và resolver. Một endpoint linh hoạt chỉ an toàn khi cost của mỗi traversal được hiểu và giới hạn. Security test nên gửi query sâu, nhiều alias và fragment lặp để quan sát complexity limit thật sự. Chỉ kiểm thử query hợp lệ thông thường không chứng minh endpoint chịu được input cố tình tiêu tốn tài nguyên.

Testing phải bắt đầu từ schema build. Một field type conflict có thể làm toàn graphql endpoint lỗi chứ không chỉ module mới. Pipeline cần enable module, compile dependency injection, build schema và chạy introspection smoke test. Unit test resolver kiểm tra parent value đủ hoặc thiếu key, context guest và customer, store khác nhau, authorization và service exception. Integration test gửi query thật với fixture. Với batch resolver, test cần chứng minh provider được gọi một lần cho nhiều item hoặc query count không tăng theo item. Cache invalidation test phải tạo cache, thay entity qua save path thật rồi query lại mà không flush mọi cache. Contract test với storefront xác nhận query cũ vẫn chạy và query mới xử lý nullable hoặc enum value đúng. Mọi concrete type triển khai interface cần được test. Chỉ test simple product có thể bỏ lỗi bundle, configurable hoặc gift card. Ngoài assertion dữ liệu, integration test nên đo số lần provider được gọi và kiểm tra query plan của bảng tùy chỉnh. Performance regression cần bị phát hiện trong pipeline trước khi page size production làm lỗi trở nên rõ ràng.

Quy trình debug field không xuất hiện bắt đầu từ module status, file schema đúng thư mục, dependency, syntax, cache và collision. Nếu introspection bị disable, cần dùng schema build hoặc môi trường development phù hợp thay vì kết luận field không tồn tại. Field xuất hiện nhưng luôn null thì kiểm tra resolver directive, parent value, concrete type và exception bị che. Query chậm theo page size thường gợi ý n cộng một. Đo query count thay vì đoán. Dữ liệu đúng khi cache tắt nhưng sai khi cache bật cho thấy identity hoặc context variation có vấn đề. Nếu chỉ browser sai còn query tool đúng, kiểm tra client cache và entity normalization. Khi external service chậm, log phải tách thời gian database, service và serialization. Không restart hoặc flush toàn bộ ngay vì hành động đó làm mất bằng chứng về layer gây lỗi. Debug tốt đi theo request tree và dependency chain từ schema tới resolver, service, storage, cache và client. Nếu field phụ thuộc nhiều module, có thể bật tắt từng module trong môi trường test để xác định schema contribution nào thay đổi contract. Cách này đặc biệt hữu ích khi extension bên thứ ba thay resolver hoặc enum mà không được tài liệu hóa rõ.

Một incident phổ biến là hai module định nghĩa cùng field với type khác nhau. Release lên một node làm schema build fail và mọi storefront query lỗi. Ci phải phát hiện collision trước merge. Incident khác là product listing tạo một query service cho mỗi item. Batch resolver giảm hàng trăm query thành một vài batch. Trường hợp nghiêm trọng hơn là company entitlement nằm trong public product query cache, khiến guest nhận benefit của customer doanh nghiệp. Cách sửa không phải thêm customer id vào cache public mà là tách contract private. Service option stale sau Admin save cho thấy identity hoặc invalidation thiếu dependency. Bundle product trả null trong khi simple đúng cho thấy parent data shape không đồng nhất. Enum mới làm app cũ crash cho thấy server và generated client chưa có compatibility policy. Những tình huống này chứng minh lỗi graphql thường nằm ở giao điểm giữa schema, data lifecycle, cache và client, không chỉ trong một resolver method. Runbook incident nên nêu cách tạm vô hiệu field hoặc query tốn kém mà không phá toàn schema, đồng thời giữ log và sample query đã che dữ liệu nhạy cảm để phân tích root cause.

Git review nên coi schema là artifact public api. Pull request phải làm rõ field mới, type, nullability, resolver, cache directive, authorization assumption và query cost. Rename hoặc xóa field cần deprecation window. Pipeline nên so schema, chạy query guest và customer, nhiều store và package bên thứ ba. Deployment nhiều node có rủi ro schema cũ và mới cùng phục vụ. Nếu storefront bắt đầu hỏi field mới trong khi một node chưa deploy, lỗi xảy ra ngẫu nhiên theo load balancer. Thứ tự an toàn là deploy backend tương thích trên mọi node, smoke test rồi mới deploy storefront query mới. Rollback cũng cần giữ field nếu client mới đã sử dụng. Không nên dựa vào việc cache clean sẽ làm schema đồng nhất nếu code trên node vẫn khác. Release note phải nêu client impact, enum addition và deprecation. Schema diff nên được review giống database migration hoặc service contract change. Một review tốt cũng hỏi field có thật sự thuộc product list hay nên là query riêng. Đưa mọi dữ liệu vào product interface làm response tree ngày càng nặng và khiến client vô tình yêu cầu field đắt trong nhiều màn hình.

Best practice là mở rộng đúng node, thêm field mới thay vì thay semantics lõi, giữ resolver mỏng và dùng service domain. Tận dụng parent value, dùng batch cho collection và giới hạn page size. Authorization phải theo caller, entity, store và website. Tách public data khỏi private entitlement. Cache identity cần phản ánh dependency thật và save path phải invalid đúng. Không expose secret qua store config. Enum cần unknown fallback ở client. Query không có side effect, mutation cần idempotency. Nullability phải theo khả năng thực tế, không theo mong muốn. Test mọi concrete type, nhiều store và customer context. Ci phải build schema và chạy smoke query. Backend nên deploy trước storefront khi thêm field. Observability cần operation name, resolver duration, query count và cache hit. Anti pattern gồm repository call cho từng item, serialize model trực tiếp, field private trong public cache, list không giới hạn, flush mọi cache và xóa field không deprecate. Khi thay đổi schema, team nên lưu snapshot introspection hoặc schema diff làm artifact của release. Artifact này giúp frontend, kiểm thử và vận hành biết chính xác contract nào đã được thêm, deprecated hoặc thay đổi description.

Để tự kiểm tra, hãy giải thích schema stitching và cách tìm node đúng trong response tree. Phân biệt graphql field, extension attribute và database field. Mô tả vai trò của context, info, parent value và args. Nêu vì sao batch resolver giảm n cộng một và khi batch service contract phù hợp. Giải thích authentication khác authorization. Trình bày cách field theo company có thể gây rò rỉ qua public cache. Mô tả identity class và dependency map. Giải thích vì sao store config không được chứa secret. Nêu ảnh hưởng của enum mới với generated client và của non null với null bubbling. Thiết kế test cho simple, bundle và configurable product. Cuối cùng, mô tả rollout nhiều node khi storefront cần field mới, rollback an toàn và dashboard giúp phát hiện resolver chậm. Khi trả lời được toàn bộ chuỗi này, người học đã hiểu mở rộng graphql schema ở mức production thay vì chỉ biết thêm một dòng schema và một class resolver. Bài tập cuối là thêm field service options, tạo lỗi n cộng một có chủ đích, sửa bằng batch, thêm authorization theo company, viết identity test và thực hiện rolling deployment trên hai node với schema khác nhau. Sau đó hãy ghi lại mọi điểm có thể làm storefront lỗi ngẫu nhiên.
