Script source là directive trong content security policy quyết định JavaScript nào được browser phép tải và thực thi. Nó không chỉ kiểm soát file JavaScript bên ngoài, mà còn liên quan tới inline script, inline event handler và một số cách code tạo script động. Khi response chứa policy, browser so từng execution point với allowlist. Browser không hiểu mục tiêu business và không hỏi server xem script có an toàn không. Nếu external file đến từ host không được phép, nó bị chặn. Nếu code nằm trực tiếp trong thẻ script, việc host của tag manager hoặc payment provider đã được whitelist không tự làm inline content hợp lệ. Inline code cần một cơ chế riêng như hash, nonce hoặc permission rộng cho inline. Đây là lý do developer phải phân loại chính xác violation trước khi sửa. Nếu nhầm network call với script loading, họ có thể mở script source trong khi directive bị thiếu thật sự là connect source. Nếu nhầm external container với Custom HTML do container inject, họ có thể thêm cùng một domain nhiều lần mà checkout vẫn trắng.

External script là file được tải qua thuộc tính source của thẻ script. Để browser chạy file, origin và scheme phải phù hợp policy. Inline script là code nằm trực tiếp trong html response. Inline event handler là code gắn trong thuộc tính như click handler. JavaScript url cũng là một dạng execution inline không nên duy trì. Một library đã được phép tải có thể tạo thêm script element, nhưng script mới vẫn phải đáp ứng policy. Việc parent library trusted không cấp quyền vô hạn cho mọi code nó sinh ra. Sự phân biệt này đặc biệt quan trọng với tag manager. Container external có thể tải từ host đã whitelist, trong khi Custom HTML tag được chèn vào document lại là inline code. Browser đánh giá hai lớp riêng. Developer nên dùng source map, initiator stack, elements panel và page source để biết element nào thực sự bị block. Không nên chỉ nhìn tên vendor trong console rồi mở toàn bộ domain. Quyết định trust phải dựa trên execution category và exact directive. Việc xác định đúng loại script giúp remediation nhỏ hơn và tránh mở quyền không liên quan.

Keyword self cho phép script từ cùng origin với page. Nó không cho inline script chạy và không tự bao gồm mọi subdomain. Same origin cũng không có nghĩa mọi file đều an toàn. Nếu application cho phép upload JavaScript vào nơi được web server phục vụ, self có thể cho file độc hại chạy. Content security policy không thay upload validation hoặc access control. Host source cho phép external script từ host cụ thể. Wildcard parent domain mở trust cho nhiều subdomain hơn nhu cầu và có thể bao gồm service ít được kiểm soát. Scheme source như https cho phép script từ mọi host dùng scheme đó, tạo boundary rất rộng. Policy tốt nên liệt kê host tối thiểu theo integration thật. Khi provider redirect qua domain khác, developer cần xác minh chain và tài liệu chính thức thay vì thêm wildcard. Một allowlist lớn có thể làm console sạch nhưng làm giảm giá trị phòng thủ. Review nên hỏi host nào sở hữu, script nào được tải, dữ liệu nào script truy cập và liệu scope có thể giới hạn theo page hay không.

Tài liệu Adobe lưu ý eval vẫn được cho phép trong default configuration, nên developer không nên giả định policy mặc định đã chặn mọi dynamic evaluation. Vì vậy, hash phù hợp với script nhỏ, tĩnh và ít thay đổi. Nó không phù hợp với code chứa customer data, store config hoặc giá trị runtime. Browser extension hoặc malicious probe cũng có thể tạo violation và gợi ý hash. Authorize một nội dung không hiểu chỉ để console sạch có thể mở đúng thứ không nên chạy. Hash inventory cũng cần liên kết với source file để lần chỉnh sửa sau biết giá trị nào phải cập nhật.

Nonce là token ngẫu nhiên được tạo theo request. Server đưa nonce vào content security policy header và gắn cùng giá trị vào script element cần cho phép. Browser chỉ chạy element khi hai giá trị khớp. Nonce phải khó đoán, thay đổi theo request và không lấy từ user input. Một nonce cố định trong configuration không còn cung cấp tính request specific. Nếu response chứa nonce bị cache rồi reuse cho nhiều người, security assumption cũng bị phá. Custom code nên dùng provider cùng rendering path được support, không tự ghép token bằng random function rời. Khi debug, cần kiểm tra header có nonce, script tag có cùng nonce, cdn không strip header và cache không reuse markup sai. Nonce phù hợp hơn hash khi inline content có thay đổi runtime, nhưng nó đòi hỏi propagation chính xác từ server tới element và mọi layer cache. Token chỉ nên được truyền tới element cần thiết, không phát tán cho mọi script trên page.

Hash và nonce đều tránh việc mở toàn bộ inline code, nhưng trust khác nhau. Hash trust nội dung. Nếu content không đổi, cùng hash có thể dùng qua nhiều request. Nonce trust element được đánh dấu trong một response cụ thể. Whitespace thay đổi làm hash fail nhưng không ảnh hưởng nonce nếu element giữ token đúng. Dynamic value làm hash khó quản lý, còn nonce phù hợp hơn. Ngược lại, một script tĩnh nhỏ có thể dùng hash mà không cần request token. Cache architecture cũng khác. Không có lựa chọn tốt nhất cho mọi trường hợp. Team nên bắt đầu bằng câu hỏi script có thể chuyển thành external module không. Framework đã có cơ chế CSP và nonce, nhưng custom proxy hoặc manual header injection có thể phá contract. Test cần bao phủ guest, logged in, store view và payment route nếu response variation khác. Security control phải hoạt động trong architecture thật, không chỉ trên local không có cdn. Team nên xác định một nơi sở hữu policy để application và edge không âm thầm đưa ra hai quyết định khác nhau. Proxy configuration cần nằm trong source control và được review cùng application change để tránh policy drift giữa environment. Đây là lỗi architecture cần sửa, không phải tình trạng chấp nhận lâu dài.

Các anti pattern phổ biến gồm thêm unsafe inline, mở wildcard domain, copy hash từ console, dùng nonce cố định và chỉ test page load. Một anti pattern khác là để marketing chỉnh Custom HTML trên checkout mà không review. Thêm host vào default source để sửa một JavaScript file cũng mở trust cho resource khác. Browser extension violation không nên được whitelist; hãy reproduce trên profile sạch. Secure renderer không nên dùng để bọc một khối logic lớn thay vì refactor. Nonce không nên được log hoặc đưa vào data layer rộng hơn nhu cầu. Mỗi exception trong policy phải có owner và lý do. Trust boundary càng rõ, incident response càng dễ. Khi một domain không còn được dùng, remove khỏi whitelist thay vì giữ phòng hờ. Content security policy không nên chỉ tăng theo thời gian. Nó cần được review và thu hẹp sau mỗi integration change. Automated integration test có thể so nonce trong header với html và fail khi cache hoặc proxy làm chúng lệch nhau. Cache test nên chạy trên nhiều request liên tiếp và so token, header cùng element thay vì chỉ kiểm tra một response.

Kiến thức cốt lõi là script source kiểm soát execution trust, không chỉ network host. External file, inline block, event handler và dynamic injection là các loại khác nhau. Host whitelist không cho inline Custom HTML tự chạy. Hash trust exact content và phù hợp script tĩnh. Nonce trust element theo request và phù hợp content động hơn. SecureHtmlRenderer cùng nonce provider là công cụ framework nên ưu tiên. Payment pages ở các phiên bản hiện hành enforce policy chặt hơn, nên checkout và admin create order phải được test riêng. Payment sdk có thể cần connect, frame hoặc image directive ngoài script. Final header sau cdn mới là policy browser thực thi. Multiple header có thể làm kết quả chặt hơn. Content security policy vẫn cần escaping, validation và dependency security. Hướng tốt nhất thường là giảm inline code và chuyển behavior vào module được version control. Policy review định kỳ nên xóa host, hash và exception không còn dùng, đồng thời xác minh owner của phần còn lại. Review cũng phải xác nhận mỗi quyền còn phục vụ business flow hiện tại, không chỉ nhìn xem console có lỗi hay không.
