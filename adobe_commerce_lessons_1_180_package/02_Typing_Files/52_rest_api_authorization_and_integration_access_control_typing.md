Rest api authorization trong Adobe Commerce không chỉ là kiểm tra một token có tồn tại. Request phải đi qua nhiều lớp. Hệ thống xác thực caller, xác định actor type, resolve route, tìm resource được yêu cầu, kiểm permission, kiểm ownership của entity, kiểm store scope, rồi mới gọi service contract và serialize response. Authentication trả lời ai đang gọi. Authorization trả lời identity đó được phép làm gì. Một token hợp lệ không đồng nghĩa có quyền trên mọi endpoint. Integration chỉ được cấp catalog read không được refund order. Customer có token không được đọc order của customer khác. Guest gọi endpoint anonymous vẫn phải qua input validation, rate control và data policy. Một api an toàn phải kết hợp resource permission với business rule. Resource permission cho biết actor có quyền dùng loại operation. Object authorization cho biết actor có quyền trên entity cụ thể. Field policy cho biết dữ liệu nào được trả. Nếu chỉ kiểm token rồi load entity theo id do client truyền, hệ thống có thể lộ dữ liệu dù acl configuration nhìn có vẻ đúng.

Commerce platform cần được xác định trước khi thiết kế authentication. Adobe Commerce PaaS, on premises và Magento Open Source dùng web api framework truyền thống với admin token, customer token, integration credential và session trong một số use case. Permission được nối từ acl tree tới web api route. Adobe Commerce as a Cloud Service dùng Adobe Identity Management System theo OAuth hiện đại. Traditional admin token và integration token generation của PaaS không được áp dụng giống nhau trên nền tảng này. SaaS có flow server to server cho automated integration và user authentication khi operation cần permission của admin user. Url structure và store scope cũng khác. Một tài liệu vận hành phải ghi rõ target platform. Nếu client SaaS cố gọi endpoint tạo admin token của PaaS, flow sẽ không hoạt động. Nếu developer copy hướng dẫn store code trong url của PaaS sang SaaS, request có thể sai scope. Phân biệt platform là bước đầu tiên trước khi debug token hoặc permission. Vì vậy runbook, client library và test suite phải ghi rõ đang nói về PaaS hay SaaS, tránh dùng cùng tên token cho hai contract khác nhau.

Trên PaaS, actor phổ biến gồm administrator, integration, customer và guest. Admin token đại diện admin user và quyền phụ thuộc role. Integration là identity dành cho hệ thống bên ngoài như erp, warehouse hoặc crm. Merchant chọn available api resources cho integration. Customer token chỉ truy cập resource dành cho customer, thường là self hoặc anonymous. Guest chỉ dùng endpoint anonymous. Mỗi actor có lifecycle và risk khác nhau. Admin token không nên được chia sẻ cho integration dài hạn vì nó gắn với user, có thể có quyền rộng và làm audit khó. Integration riêng giúp least privilege, rotate, revoke và xác định owner. Customer identity phải được lấy từ authenticated context, không từ customer id trong payload. Guest không có identity đăng nhập, nên endpoint public phải đặc biệt chú ý abuse, enumeration và dữ liệu nhạy cảm. Khi debug, cần biết token thuộc actor nào, vì cùng route có thể cho admin gọi nhưng từ chối integration hoặc customer. Mỗi identity nên có owner, business purpose, environment và ngày review để credential không tồn tại vô thời hạn mà không ai chịu trách nhiệm.

Acl xml định nghĩa cây permission có thể cấp cho admin role hoặc integration. Webapi xml expose service method thành route và tham chiếu resource cần có. Có thể hình dung acl là danh mục quyền, còn web api configuration là cánh cửa yêu cầu một quyền trong danh mục đó. Một module supplier có thể tách view, manage và approve. Route đọc supplier yêu cầu view, route update yêu cầu manage, route approve yêu cầu approve. Nếu mọi operation dùng một resource root, merchant không thể cấp read only. Granularity quá thô làm quyền rộng. Granularity quá nhỏ làm quản trị phức tạp. Nên nhóm theo business operation và risk. Read, delete, refund, approve hoặc export thường đáng tách. Route mới phải có resource và authorization test trong cùng pull request. Xml hợp lệ chưa đủ. Reviewer phải kiểm service contract, http method, resource id và actor use case. Integration available api screen lấy resource từ acl tree, nên permission id thay đổi có thể ảnh hưởng integration đã cấu hình. Khi resource tree đổi tên hoặc vị trí, cần đánh giá integration đã cấu hình và cache acl, không chỉ validate xml trong source.

Anonymous resource cho phép request không có authenticated identity. Nó phù hợp với public catalog data, guest cart hoặc public configuration đã được whitelist. Anonymous không có nghĩa endpoint được bỏ mọi bảo vệ. Search public có thể bị dùng để tạo query đắt. Mutation guest có thể bị spam. Endpoint public có thể lộ email, internal id hoặc store data nếu output contract quá rộng. Cần input limit, pagination, rate policy, validation, output filtering và monitoring. Không chọn anonymous chỉ vì frontend khó lấy token. Đó là đổi security lấy convenience. Khi một route được đặt anonymous tạm trong development, cần policy ci hoặc security review để ngăn config đó đi production ngoài ý muốn. Test phải gồm request không token, input xấu, pagination cực lớn và store scope khác. Log public endpoint không được ghi sensitive payload. Nếu anonymous traffic tăng đột biến, metric và alert phải giúp phân biệt campaign thật với abuse. Public endpoint còn cần quota hoặc query cost khi operation đắt, vì authentication không phải lớp duy nhất chống tải lạm dụng. Test cần đo cả latency và response size để phát hiện abuse pattern trước khi endpoint ảnh hưởng storefront.

Self resource dùng cho customer đã authenticate truy cập dữ liệu của chính mình. Ví dụ là profile hiện tại, address, cart hoặc order của customer. Tuy nhiên self không tự bảo đảm mọi custom service an toàn. Nếu route nhận order id, service load order theo id rồi trả ngay, customer A có thể đổi id thành order của customer B. Đây là object authorization failure. Service phải lấy customer id từ user context và so với owner của entity. Không tin customer id do client gửi. Với entity ngoài ownership, response có thể dùng not found để giảm khả năng xác nhận entity tồn tại, miễn policy nhất quán. Resource level trả lời actor có quyền dùng loại operation, còn ownership trả lời entity cụ thể có thuộc actor không. Test cần negative case cross customer, không chỉ happy path. Một endpoint self đạt review khi identifier tampering không làm lộ data, update không chuyển owner và search chỉ trả entity thuộc context. Search hoặc list endpoint cũng phải filter theo owner từ query đầu tiên, không load tất cả rồi lọc sau vì vừa chậm vừa dễ lộ total count.

Integration least privilege yêu cầu tách identity theo responsibility. Catalog import không nên dùng cùng credential với reporting và refund. Warehouse chỉ cần inventory, shipment hoặc source data liên quan. Reporting thường chỉ cần read. Crm cần subset customer field chứ không nhất thiết cần order mutation. Khi credential bị lộ, blast radius phụ thuộc permission đã cấp. Integration riêng còn giúp disable một hệ thống khi incident mà không dừng hệ thống khác. Permission matrix cần được document với owner, environment, business purpose, resource, rotation và contact. Không chọn all resources vì tiện test rồi giữ đến production. Khi resource mới được thêm, integration không nên tự nhận quyền rộng nếu policy yêu cầu approval. Audit định kỳ phải so resource được cấp với request thực tế. Một integration không dùng permission trong thời gian dài có thể được thu hẹp. Least privilege là lifecycle, không phải checklist một lần lúc onboarding. Permission review định kỳ nên so resource được cấp với request log để phát hiện quyền thừa và integration đã không còn sử dụng. Khi integration ngừng hoạt động, credential và permission phải được thu hồi theo offboarding checklist.

Credential lifecycle trên PaaS gồm admin token, customer token và integration credentials. Token phải được lưu trong secret manager, tách theo environment và rotate theo policy. Không commit token vào source, ci yaml, postman collection public hoặc wiki không kiểm soát. Không in authorization header vào log. Admin token thường có lifetime theo configuration, customer token có lifetime riêng và client cần xử lý expiry. Integration credential truyền thống có consumer key, consumer secret, access token và access token secret trong OAuth flow. Khi người phụ trách rời team hoặc vendor contract kết thúc, credential phải revoke. Runbook cần mô tả cách rotate không dừng integration, cách xác minh token mới và cách rollback. Secret scanning trong ci có thể phát hiện credential bị commit. Nếu secret từng xuất hiện trong Git history, chỉ xóa file hiện tại chưa đủ. Cần rotate ngay và xử lý history theo quy trình bảo mật. Audit log không được lưu token nhưng cần ghi integration id đã mask. Các collection export và tool hỗ trợ phải dùng placeholder hoặc secret reference, không chứa giá trị thật có thể bị chia sẻ ngoài team.

Commerce as a Cloud Service dùng Adobe IMS cho REST authentication. Server to server flow phù hợp background sync, report hoặc automated process không cần user interaction. User authentication phù hợp ứng dụng admin nơi operation phải mang permission và attribution của người dùng. Client secret chỉ được giữ ở backend hoặc secure environment, không expose trong browser. Token manager cần biết expiry, request token mới trước khi hết hạn và xử lý unauthorized hoặc forbidden đúng cách. Project, credential và scope trong Adobe Developer Console cần owner và audit. Store scope có thể đi qua header theo platform contract, khác url pattern PaaS. Endpoint available trên SaaS cũng không hoàn toàn giống PaaS. Integration design phải dựa trên api reference đúng nền tảng. Một client library dùng chung có thể cần adapter riêng cho base url, store context và token provider. Không nên che khác biệt bằng nhiều if rải rác mà không có platform boundary rõ. Khi token refresh fail, client cần backoff và alert thay vì liên tục request credential mới làm lỗi lan sang identity provider.

Http status giúp phân loại failure. Unauthorized thường cho biết authentication thiếu, token invalid, expired hoặc bị revoke. Forbidden thường nghĩa identity đã được nhận nhưng không có permission. Not found có thể là entity không tồn tại hoặc policy không xác nhận entity ngoài ownership. Bad request liên quan input format hoặc validation. Client cần xử lý từng nhóm khác nhau. Không retry vô hạn forbidden vì permission không tự thay đổi. Token expiry có thể refresh. Validation lỗi cần sửa payload. Server response production không nên chứa stack trace, sql, class internal hoặc permission tree chi tiết. Log server cần correlation id, actor, route, resource, store scope và exception detail đã kiểm soát. Khi debug, phải lưu status, response header và correlation id trước khi thay config. Xóa cache hoặc tạo token mới quá sớm có thể làm mất evidence về lỗi permission thật. Chính sách response cần thống nhất giữa các endpoint để client không thể suy ra entity tồn tại từ sự khác nhau không cần thiết. Client cũng cần giữ correlation id để support phân biệt lỗi identity với lỗi entity.

Store và website scope là lớp authorization business thường nằm ngoài acl resource. Integration có quyền đọc order không nhất thiết được đọc mọi website nếu hợp đồng chỉ áp dụng một region. Custom service cần kiểm store header, website assignment, company context, shared catalog hoặc scope mapping của integration. Nếu integration website A truyền store B và service chỉ kiểm acl, data B có thể bị lộ. Scope policy nên nằm trong service hoặc policy layer, không chỉ trong client. Test cần wrong store, wrong website và entity không thuộc scope. Customer endpoint cũng phải xử lý store context nhất quán. Price, currency và locale có thể khác nhưng permission vẫn phải dựa trên ownership và business scope. Audit log nên ghi store context để incident timeline nhìn thấy request bất thường. Khi lỗi chỉ xảy ra một store, kiểm scope trước khi nghi token. Scope map nên được quản lý như configuration có audit và test, không hardcode rải rác trong controller hoặc plugin. Policy nên có owner và version để thay đổi scope được review giống code.

Field level authorization và data minimization giảm lượng dữ liệu caller nhận. Actor có quyền đọc customer không có nghĩa cần date of birth, tax identifier, phone, address, internal risk score hoặc credit data. Service nên dùng output contract phù hợp operation, tách summary và detail, mask field hoặc dùng resource restriction cho extension attribute khi framework hỗ trợ. Không trả model đầy đủ chỉ vì serializer làm việc đó dễ. Schema change thêm field nhạy cảm cần security review và regression test. Một integration reporting có thể cần order total nhưng không cần customer phone. Nếu credential bị lộ, data minimization làm giảm hậu quả. Test output phải assert field không được phép không xuất hiện, không chỉ assert field cần thiết có mặt. Log và error cũng phải tuân thủ minimization. Debug mode không nên biến thành cách lộ toàn payload production. Data minimization cũng làm response nhỏ hơn, nhưng lợi ích hiệu năng chỉ là phụ; mục tiêu chính vẫn là giảm quyền truy cập dữ liệu. Test nên kiểm field nhạy cảm vắng mặt trong cả success response lẫn error payload.

Mass assignment xảy ra khi update endpoint nhận entity đầy đủ từ client rồi repository save trực tiếp. Client có thể gán status hệ thống, approved flag, customer id, website id, internal note hoặc credit limit. Acl resource có thể đúng nhưng input contract quá rộng vẫn tạo privilege escalation. Hướng tốt là command dto theo use case. Supplier profile update chỉ nhận display name và contact email. Approval dùng command khác với permission approve. Service map từng field được phép sang entity. Read và write resource cũng nên tách. Reporting integration cần view không phải manage. Approve và refund thường cần quyền riêng vì risk cao. Test phải gửi extra field và chứng minh service bỏ qua hoặc reject. Không dựa vào frontend form để hạn chế field, vì external caller có thể gửi payload trực tiếp. Nó cũng giúp version api dễ hơn vì contract update được tách theo use case. Reviewer có thể đối chiếu dto với permission matrix.

Async và bulk api tạo thách thức vì operation được xử lý sau request ban đầu. Hệ thống cần quyết định actor identity được capture thế nào, permission được kiểm lúc enqueue hay consume và consumer có chạy system context không. Không nên cho consumer quyền tuyệt đối rồi tin mọi message chỉ vì message nằm trong queue. Producer phải trusted, payload cần validation và operation phải nằm trong quyền ban đầu. Nếu credential bị revoke sau enqueue, policy cần rõ. Một số hệ thống chấp nhận operation đã được authorize tại thời điểm enqueue, hệ thống khác recheck khi consume. Quyết định phụ thuộc business và compliance. Message cần correlation id và actor context đã tối giản, không chứa token raw. Retry không được biến forbidden operation thành allowed. Queue audit phải nối request ban đầu với consumer result. Đây là nơi authorization, message contract và observability gặp nhau. Bulk job cần lưu snapshot permission tối thiểu hoặc reference actor bền vững để incident có thể truy lại quyết định authorization ban đầu. Nếu policy recheck lúc consume, consumer phải xử lý actor đã bị disable một cách có quan sát.

Observability cho api authorization cần metric và log có mục đích.
