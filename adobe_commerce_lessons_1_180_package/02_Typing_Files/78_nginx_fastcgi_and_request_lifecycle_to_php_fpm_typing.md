Một request động tới adobe commerce không đi thẳng từ browser vào php. Nó có thể qua cdn, router, nginx, socket fastcgi, php fpm rồi mới tới front controller và application. Nginx trước hết chọn virtual server dựa trên address, port, sni và host. Nếu hostname không match, request có thể rơi vào default server của listen đó, nên gọi bằng địa chỉ ip và gọi bằng domain có thể dùng hai configuration khác nhau. Sau khi chọn server, nginx tìm location theo uri. Exact location có ưu tiên cao nhất, longest prefix được ghi nhớ, prefix có ký hiệu đặc biệt có thể chặn regex, còn regex được kiểm tra theo thứ tự khai báo. Query string không quyết định location, vì application mới xử lý argument. Một rule rộng cho file php có thể vô tình gửi upload hoặc file không mong muốn vào interpreter. Developer cần phân biệt uri gốc với uri hiện tại sau rewrite, vì internal redirect có thể thay đổi location search mà client không nhận redirect. External redirect tạo response ba trăm và client gửi request mới, còn internal redirect chỉ thay luồng xử lý bên trong nginx. Mỗi lần rewrite hoặc index chuyển uri có thể làm location được chọn lại. Nếu rule tạo cycle, nginx có thể trả lỗi trước khi php nhận request. Vì vậy khi một trang trả bốn trăm linh bốn hoặc năm trăm, việc đầu tiên không phải luôn đọc exception log. Cần xác định vhost, location, current uri, static mapping và upstream decision. Effective configuration từ nginx mới là bằng chứng, không phải file vhost mà developer nghĩ đang được include. Trên cloud managed, quyền sửa và reload còn phụ thuộc platform. Một sơ đồ request rõ ràng giúp team biết request đã dừng trước nginx, trong nginx, trước php fpm hay trong adobe commerce.

Try files là cầu nối quan trọng giữa static file và front controller. Nginx kiểm tra path dựa trên root hoặc alias, dùng file đầu tiên tồn tại, rồi có thể internal redirect tới index php nếu không tìm thấy. Với adobe commerce, url đẹp như customer account login không phải file thật, nên nó cần đi vào front controller trong document root pub. Ngược lại, ảnh, css hoặc javascript đã deploy đúng nên được nginx phục vụ trực tiếp để tránh khởi động php. Sai root, alias, symlink hoặc permission có thể làm static file bốn trăm linh bốn dù file tồn tại ở nơi khác. Sai fallback có thể làm mọi asset đi vào php và tạo tải lớn. Root ghép uri vào đường dẫn, còn alias thay phần location, nên copy một biểu thức giữa hai loại mà không kiểm tra có thể map sai filesystem. Internal redirect do try files, index, rewrite hoặc error page có thể chạy lại location matching. Rewrite last thường tìm location lại, còn break dừng rule hiện tại nhưng tiếp tục trong context đang dùng. Dùng sai có thể tạo loop hoặc bỏ qua parameter fastcgi. Static request nhanh không tự chứng minh origin dynamic khỏe, vì asset có thể là cdn hit và không tới nginx. Khi asset lỗi, kỹ sư cần kiểm tra cache state, server block, location, path, version, file permission và fallback. Không nên chạy full static deployment chỉ vì một route sai. Khi dynamic route lỗi, cần phân biệt nginx bốn trăm linh bốn với application no route. Nếu php access log không có entry, request có thể chưa vào front controller. Nếu có entry cùng request id, investigation chuyển sang application routing. Phân chia này ngăn team sửa sai tầng và giúp giữ outage evidence trước khi restart hoặc redeploy.

Fastcgi là protocol giữa nginx và php fpm, không phải nguyên bản http được chuyển tiếp. Nginx tạo record chứa parameter và body, kết nối qua unix socket hoặc tcp socket, rồi php fpm chọn child để thực thi script. Parameter script filename là contract quan trọng vì nó chỉ ra file php thực tế. Nếu ghép uri tùy ý vào filesystem, server có thể execute file upload hoặc path không mong muốn. Front controller architecture an toàn hơn khi chỉ cho phép entry point rõ và dùng document root pub. Các parameter khác truyền method, query string, content type, content length, request uri, server name, scheme và remote address. Sai indicator https có thể tạo redirect loop hoặc cookie không secure. Sai trusted proxy handling có thể làm application tin địa chỉ giả từ header. Unix socket cần path đúng, listener đang tồn tại, owner group mode phù hợp và parent directory cho phép traverse. Tcp socket cần address, port và namespace đúng. Master php fpm sống không chứng minh pool đã bind thành công. File socket có thể là stale artifact từ instance trước, child có thể bận hết, backlog có thể đầy hoặc deploy có thể đang graceful reload. Nginx connect được bằng công cụ tcp chỉ chứng minh listener tồn tại, không chứng minh fastcgi request tạo response hợp lệ. Khi thay php version, effective nginx config có thể vẫn trỏ socket cũ. Kỹ sư cần so fastcgi pass thực tế với listener, không chỉ đọc process list. Permission không được chữa bằng chmod toàn quyền. Cần xác định nginx worker user, fpm listen owner, group, mode, acl và permission từng directory. Một configuration đúng phải vừa route chính xác, vừa giới hạn script được execute, vừa truyền đủ metadata cho commerce mà không tin header từ nguồn không được kiểm soát.

Buffering quyết định resource nào giữ request và response trong từng giai đoạn. Khi request buffering bật, nginx đọc toàn bộ body từ client trước khi gửi tới php fpm. Body nhỏ nằm trong memory buffer, body lớn có thể được ghi vào temporary file. Cách này bảo vệ php worker khỏi slow upload và cho nginx xử lý client chậm hiệu quả hơn, nhưng dùng disk, inode và tạo latency trước khi php bắt đầu. Nếu temp path hết dung lượng hoặc permission sai, upload có thể fail trước application. Tắt request buffering gửi body tới fpm khi đang nhận, nhưng làm worker bị giữ bởi client chậm và có thể hạn chế retry upstream sau khi body đã gửi. Response buffering có chiều ngược lại. Nginx đọc response từ php nhanh vào buffer hoặc temp file rồi gửi dần cho client, nhờ đó php worker được giải phóng sớm hơn. Tắt buffering có thể cần cho streaming, nhưng giữ worker lâu và vẫn chưa chắc byte tới browser ngay vì output buffer, compression, cdn hoặc client còn tham gia. Client max body size có thể trả bốn trăm mười ba trước khi php chạy. Php còn có post max size cùng upload max filesize, và cdn có giới hạn riêng. Các limit phải align với business cùng security. Header response quá lớn có thể vượt fastcgi buffer, thường do cookie, debug header hoặc redirect metadata. Tăng buffer có thể là mitigation nhưng permanent fix nên giảm header bất thường. Large response có thể tạo fastcgi temp file và disk io. Team cần đo body size, buffer, temp disk, request timing và worker occupancy thay vì tăng mọi buffer. Mục tiêu không phải giữ mọi thứ trong memory, mà là chọn nơi chịu slow client và large payload với giới hạn có thể quan sát.

Timeout trong request lifecycle không phải một con số chung. Nginx có timeout đọc header hoặc body từ client, timeout kết nối tới fpm, timeout gửi request fastcgi, timeout đọc response và timeout gửi response cho client. Fastcgi read timeout chỉ đo khoảng giữa hai lần đọc từ upstream, không phải tổng thời gian thực thi. Php gửi một ít dữ liệu định kỳ có thể tránh timeout dù request chạy rất lâu. Php fpm còn có request terminate timeout và slowlog timeout. Cdn có first byte cùng origin timeout riêng. Nếu cdn bỏ cuộc sau sáu mươi giây nhưng nginx chờ ba phút và php chờ năm phút, client nhận lỗi trong khi backend vẫn làm việc. Điều này lãng phí worker và có thể tạo side effect sau khi user bấm lại. Status code giúp định hướng nhưng không xác định root cause một mình. Bốn trăm chín mươi chín thường nghĩa client hoặc proxy đóng trước khi nginx trả xong. Năm trăm có thể là response application với exception. Năm trăm linh hai thường liên quan connection refused, socket permission, reset, invalid fastcgi header hoặc upstream đóng trước header. Năm trăm linh bốn nghĩa gateway chờ upstream quá giới hạn, nhưng php process có thể vẫn sống và đang chờ database, search hoặc external integration. Năm trăm linh ba có thể do maintenance, rate limit, application hoặc backend health. Tăng fastcgi read timeout có thể giảm năm trăm linh bốn bề mặt nhưng giữ resource lâu hơn. Batch admin dài nên được tối ưu, chia nhỏ hoặc chuyển cli và queue thay vì biến web request thành job không giới hạn. Timeout hierarchy phải dựa trên latency budget, cancellation behavior và idempotency. Sau mọi thay đổi, team cần kiểm tra cùng workload, đo request time, upstream time, listen queue, tỷ lệ lỗi và xác nhận operation không bị chạy trùng sau khi client đã bỏ cuộc.

Gateway error khi php vẫn sống là tình huống buộc kỹ sư tách process existence khỏi service health. Master có thể tồn tại nhưng pool config fail, listener không bind hoặc unix socket có owner sai. Child có thể tồn tại nhưng mọi child đang bận, listen queue đầy hoặc request mới chưa được chọn. Một child đã nhận request có thể gặp memory limit, segfault extension, out of memory kill, terminate timeout hoặc reset connection trước khi gửi header, khiến nginx trả năm trăm linh hai. Một child khác có thể chờ database lock hoặc integration, không dùng nhiều cpu và không gửi byte trong read interval, khiến nginx trả năm trăm linh bốn. Graceful reload còn tạo giai đoạn worker cũ và mới cùng tồn tại, trong khi socket hoặc process identity thay đổi. Stale socket file có thể tồn tại dù không có listener phía sau. Vì vậy ps không đủ. Investigation cần exact error message từ nginx, effective fastcgi pass, socket listener, permission path, fpm master cùng child state, queue metric, slowlog, application fatal, kernel kill và deploy marker. Connection refused khác permission denied, còn prematurely closed connection khác upstream timed out. Khi header quá lớn, php có thể hoàn tất logic nhưng nginx không chấp nhận response header. Khi client hoặc cdn timeout trước, nginx log bốn trăm chín mươi chín trong khi php tiếp tục side effect. Request id và timestamp phải nối cả nginx access, nginx error, php access, fpm, application và new relic. Restart có thể làm symptom biến mất nhưng cũng xóa queue và process evidence. Mitigation chỉ nên thực hiện sau khi capture trạng thái tối thiểu, trừ khi user impact buộc hành động khẩn cấp có audit. Nếu buộc phải restart để giảm impact, incident note vẫn phải ghi trạng thái trước hành động, service nào được restart, lý do, thời điểm và bằng chứng sau recovery.

Access log timing biến request lifecycle thành dữ liệu có thể so sánh. Request time mô tả thời gian nginx giữ request theo contract của nó, còn upstream connect time đo connect tới fastcgi, upstream header time đo đến response header và upstream response time đo response của upstream. Upstream status cùng address cho biết backend nào và attempt nào. Nếu có retry hoặc nhiều upstream, variable có thể chứa danh sách, nên parser không được ép thành một số duy nhất. Khi request time gần upstream response, phần lớn thời gian có thể nằm ở fpm hoặc application. Khi request time lớn hơn upstream response nhiều, cần xem client upload, response send, buffering, internal redirect hoặc time ngoài upstream. Nginx access log có request nhưng php access log không có thường gợi ý static route, rewrite, body rejection hoặc fastcgi connect fail trước khi php nhận. Có cả hai log chứng minh request đi sâu hơn, nhưng duration semantics vẫn cần hiểu. Adobe commerce cloud có access, error, php access và fpm log theo environment, với path cùng rotation khác integration và pro cluster. Team phải tìm đúng node cùng timestamp. New relic transaction và external span bổ sung application cùng dependency detail. Fastly log hoặc header cho biết cache hit, shield và origin behavior, vì nhiều client request không tới nginx. Correlation id cần truyền qua layer nhưng không chứa secret. Access log không nên ghi authorization, cookie hoặc query nhạy cảm. Một runbook tốt thu thập host, uri, method, status, request id, upstream address, connect, header, response, body size và deployment marker. Sau fix, cùng request class phải cho tail latency, error, queue và correctness tốt hơn. Log format còn phải được version control để mọi node ghi cùng field, nếu không dashboard có thể trộn dữ liệu không cùng semantics và dẫn tới kết luận sai.

Technical lead nên coi nginx và php fpm là một pipeline có queue cùng backpressure, không phải hai service chỉ cần còn process. Configuration review phải bắt default server không rõ, regex location quá rộng, alias sai, try files mất query string, front controller mở execute tùy ý và script filename ghép từ input không kiểm soát. Security baseline cần document root pub, chặn source cùng config, không execute php trong media và chỉ tin forwarded header từ proxy được xác định. Performance review cần bảo đảm static file tránh php, static content được deploy, request và response buffering có lý do, body limit align, upstream timing được log và batch dài không chạy như web request vô hạn. Timeout change phải có owner, rollback và test cả client, cdn, nginx, fpm cùng dependency. Khi gặp năm trăm linh hai, team phải phân loại refused, permission, reset, invalid header hoặc crash. Khi gặp năm trăm linh bốn, team phải xác định layer tạo timeout và xem fpm queue, slowlog, database, search cùng external call. Khi gặp bốn trăm chín mươi chín, team phải xác định client thực là browser, cdn hay load balancer và kiểm tra side effect tiếp tục sau disconnect. Debug log chỉ bật phạm vi hẹp vì volume và dữ liệu nhạy cảm. Effective config cùng log evidence phải được lưu trước reload. Mục tiêu không phải tăng buffer, timeout hoặc child cho tới khi lỗi biến mất. Mục tiêu là request đi đúng route, static được phục vụ đúng tầng, fastcgi contract an toàn, queue có giới hạn, failure có phân loại và mọi thay đổi được chứng minh bằng timing cùng business correctness. Mỗi runbook cần owner, mức ưu tiên, lệnh read only trước tiên, tiêu chí escalates platform support và điều kiện dừng mitigation khi dữ liệu hoặc checkout có nguy cơ sai.
