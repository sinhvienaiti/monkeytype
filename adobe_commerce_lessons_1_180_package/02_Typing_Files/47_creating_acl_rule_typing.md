Acl trong Adobe Commerce là cơ chế authorization cho Admin users và integrations. Authentication chỉ xác định caller là ai, còn authorization xác định caller được làm gì. Một Admin user đăng nhập thành công chưa chắc được approve, export hoặc delete hồ sơ. Integration token hợp lệ cũng chỉ dùng được resources đã được cấp. Acl không thay toàn bộ business policy. User có resource approve vẫn có thể bị từ chối nếu record đã approved, thuộc website khác hoặc vượt approval threshold. Khả năng hiển thị trên giao diện cũng không phải security boundary. Menu hoặc button bị ẩn không ngăn người dùng nhập direct url hay gọi endpoint. Một thiết kế tốt bắt đầu bằng capability matrix, không bắt đầu bằng route names. Ví dụ module supplier compliance cần view, edit, approve, export, delete và view assessment cost. Viewer không được thấy cost, editor không được approve, exporter không được edit. Ma trận nên được lưu cùng tài liệu thiết kế trong Git, để mỗi thay đổi quyền có người review và bằng chứng test. Khi audit xảy ra, team phải chỉ ra quyền nào cho phép hành động, dữ liệu nào được trả về và log nào chứng minh actor đã thực hiện thao tác.

Mọi acl xml từ enabled modules được merge thành một resource tree. Custom resources thường nằm dưới Admin root và dùng id theo convention vendor module cùng capability. Id phải unique và ổn định vì Admin roles và integration permissions lưu reference tới id đó. Rename không chỉ là refactor string; role cũ có thể mất access. Title cần rõ để security administrator hiểu quyền đang cấp. Sort order chỉ điều khiển presentation. Parent resource giúp grouping và role selection, nhưng tree quá sâu làm permission khó audit. Resource nên mô tả business action như view, approve hoặc export thay vì controller method như index và save. Read và write nên tách khi risk khác nhau. Sensitive field như assessment cost có thể cần resource riêng. Quá granular tạo nhiều combinations và test, còn một resource manage cho mọi thứ vi phạm least privilege. Granularity nên dựa risk, irreversibility, financial impact, bulk export và sensitive data. Việc chọn parent cũng cần phản ánh ranh giới quản trị thật. Một quyền xem chi phí không nên nằm dưới nhóm chỉnh sửa nội dung nếu security administrator có thể hiểu nhầm và cấp cùng lúc. Trước khi release, team nên dựng role mẫu trên staging, export danh sách quyền và so sánh với permission matrix đã được phê duyệt.

Admin controller phải extend backend action và khai báo Admin resource constant. View action dùng view resource, approve action dùng approve resource, delete action dùng delete. Không dùng menu parent resource cho mọi controller nếu business muốn phân quyền chi tiết. Framework check permission trước execute, còn service tiếp tục validate entity state. Menu item cũng có resource để quyết định visibility, nhưng menu resource không bảo vệ controller. User có thể đoán url hoặc gọi bookmark. Mass actions và ajax actions cần constant riêng. Một bug phổ biến là approve button bị hide nhưng mass approve controller dùng edit resource, nên editor vẫn approve qua crafted request. Direct url tests phải nằm trong security suite. Không chỉ test click path từ menu. Page title, layout block và button provider là presentation; side effect boundary vẫn ở controller và service. Form key và csrf bảo vệ request khỏi một lớp tấn công khác, nhưng không thay thế acl. Một request có form key hợp lệ vẫn phải bị từ chối nếu role thiếu quyền. Test nên gọi controller bằng account có quyền, account không có quyền và account đã bị khóa để phân biệt lỗi authentication, csrf và authorization.

Adobe cảnh báo ui component có thể được render trực tiếp qua mui render mà không đi qua page controller. Vì vậy listing và data provider chứa dữ liệu nhạy cảm phải có acl resource. Chỉ bảo vệ controller page chưa đủ. Grid page có thể trả access denied nhưng attacker vẫn gọi data source endpoint nếu component thiếu resource. Hidden column cũng không bảo vệ dữ liệu nếu raw json vẫn chứa field. Data provider hoặc operation dto phải loại assessment cost khi caller không có view cost. Form data provider, mass action và export source đều cần review. Acl trên visual column chỉ cải thiện ui. Network response mới là boundary cần kiểm tra. Security test phải gọi data provider trực tiếp, không chỉ mở page. Đây là ví dụ rõ về defense in depth trong Adobe Commerce Admin. Khi kiểm tra network, team cần xác nhận cả tên field, giá trị, total count và metadata phụ đều không tiết lộ thông tin bị cấm. Cách an toàn là data provider xây response theo permission ngay từ đầu, thay vì tải full record rồi hy vọng component sẽ ẩn đúng. Điều này cũng giảm dữ liệu truyền và đơn giản hóa audit.

Layout block có thể khai báo acl resource để conditionally render content. Button provider cũng có thể hỏi authorization service để hide approve hoặc delete button. Những check này giúp giao diện đúng với role, nhưng không thay data authorization. Nếu parent block hoặc global JavaScript object đã chứa sensitive value, child block bị ẩn vẫn không ngăn leak. Service trả object quá rộng là root cause. View model cũng không nên assume nơi dùng luôn được block acl bảo vệ. Method có thể được gọi từ template khác hoặc test tool. Operation-specific service và dto nên chỉ trả fields cần cho use case. Viewer dto có supplier, status và expiration, còn cost dto yêu cầu permission riêng. Data minimization giảm khả năng một layer presentation quên check. Nếu một component được tái sử dụng ở dashboard khác, permission của trang cũ không tự đi theo nó. Vì vậy contract của view model hoặc provider phải nói rõ dữ liệu nào được phép trả và caller cần capability nào. Đây là lý do data minimization nên nằm gần source, không nằm ở lớp template cuối cùng.

Rest và soap web api routes tham chiếu resource từ acl tree. Admin token hoặc integration phải được cấp custom resource. Anonymous chỉ dùng cho endpoint thật sự public, không dùng để sửa unauthorized nhanh. Self phù hợp một số customer operations, nhưng service vẫn phải check ownership. Caller authenticated không có nghĩa entity id trong request thuộc caller. Multiple resource declarations cần được test theo version và policy thực tế, không dùng để biểu diễn rule phức tạp một cách mơ hồ. Integration resource selector dùng title và hierarchy từ acl tree, nên naming rõ giúp tránh cấp nhầm quyền rộng. Export endpoint nên dùng export resource, không dùng view chỉ vì cùng đọc data. Bulk export có risk cao hơn page view và có thể chứa nhiều records. Với endpoint chạy bất đồng bộ, permission còn phải được chụp cùng request hoặc kiểm tra lại khi job thực thi. Token đã bị thu hồi không nên tiếp tục cho phép một export dài chạy vô hạn. Team cần quy định rõ behavior khi role thay đổi giữa lúc tạo job và lúc worker đọc message, rồi kiểm tra trường hợp đó bằng integration test.

Configuration-based authorization không giải quyết mọi condition. Service có thể inject authorization interface và check resource explicitly. Trường hợp phù hợp gồm page có nhiều fields với permissions khác nhau, button visibility, service được gọi từ nhiều entry points và async operation cần giữ actor context. Resource strings không nên được copy tùy ý khắp code vì typo tạo drift. Có thể dùng constants theo domain, nhưng policy vẫn nên chia theo service. Queue consumer và cron không có Admin session giống request. Nếu export job đại diện cho user, message cần lưu actor, requested operation và field policy. Worker không được mặc định superuser rồi export full entity. Permission có thể thay đổi giữa lúc request và lúc consumer chạy, nên business phải quyết định authorize tại request, execute hoặc cả hai. Nếu authorize lại tại thời điểm execute, worker cần một actor identifier đáng tin và cách resolve quyền hiện hành. Nếu chỉ authorize khi enqueue, message phải chứa immutable snapshot đủ để audit nhưng không được chứa secret. Với tác vụ tài chính hoặc export nhạy cảm, kiểm tra ở cả hai thời điểm thường an toàn hơn và cần idempotency để retry không tạo kết quả lặp.

Acl không bảo vệ khỏi mass assignment. Edit service nhận toàn request data rồi set vào model có thể cho editor thay approved state, internal owner hoặc cost dù ui không có fields đó. Input dto phải allowlist writable properties. Approve là operation riêng với resource và validation riêng. Repository thường là persistence contract dùng cả internal trusted flows, nên không phải nơi duy nhất cho use-case authorization. Application service theo operation biết actor, scope và business intent. Sensitive information guidance của Adobe khuyến khích case-specific service và dto thay vì trả full entity. Điều này giúp html page, ui component và api không vô tình expose extra properties. Authorization và data shape phải được thiết kế cùng nhau. Ví dụ, editor có thể thay ngày hết hạn và ghi chú, nhưng không được sửa trạng thái approved, reviewer id hoặc assessment cost. Approve service chỉ nhận record identifier và decision, sau đó tự lấy entity, kiểm tra resource, website, trạng thái và concurrency token. Thiết kế này làm input nhỏ, dễ test và giảm đường tấn công qua field không mong muốn.

System configuration có thể dùng acl để giới hạn section hoặc capability. Tuy nhiên acl không biến secret thành dữ liệu an toàn nếu value được render đầy đủ. Credential cần encrypted backend và sensitive environment configuration khi phù hợp. Capability quản lý config cũng không tự giới hạn website scope. Nếu organization cần role chỉ được quản lý một website, custom scope policy có thể cần thiết. Admin acl, customer authorization và company roles là các permission systems khác nhau. Admin resource không nên được dùng mù trong storefront customer flow. Customer access dựa token, ownership, group và service policy. Company users có role tree riêng. Command line và deployment jobs dùng os và application service permissions, không phải Admin session. Cùng tên capability không có nghĩa cùng engine. System job cũng cần identity và secret riêng theo nguyên tắc least privilege. Một deployment command có quyền đọc config không nên mặc định có quyền export hồ sơ supplier. Khi nhiều permission engine cùng tồn tại, tài liệu phải chỉ rõ engine nào kiểm tra entry point nào, để developer không gọi nhầm Admin acl trong storefront hoặc company role trong cron.

Resource hierarchy cần cân bằng coarse và fine grained. Một manage resource dễ cấu hình nhưng cấp quyền rộng. Nhiều child resources hỗ trợ least privilege và separation of duties nhưng làm role matrix lớn. Action irreversible, financial, approval, export, delete và sensitive data nên tách. Low risk metadata edit có thể group khi business chấp nhận. New capability nên deny by default và cần explicit resource. Không thêm feature rồi cho tất cả roles có parent resource tự được quyền nếu risk mới cao hơn. Parent selection semantics cần test bằng role fixtures. Security administrator cần documentation nêu capability, entry points và data exposed. Resource title không nên mơ hồ như manage advanced. Tên rõ giúp audit và giảm configuration error. Deny by default đặc biệt quan trọng khi thêm action mới vào module cũ. Team nên coi capability chưa được map là không khả dụng, thay vì kế thừa một parent quá rộng vì tiện. Với quyền nhiều mức, hãy tạo bảng actor, action, scope, field và side effect; bảng này giúp phát hiện sớm chỗ một role được xem nhưng vô tình cũng được tải file hoặc kích hoạt workflow.

Rename hoặc move resource là migration. Existing authorization rules tham chiếu old id. New id có thể làm roles và integrations mất permission sau upgrade. Có thể giữ compatibility resource trong window hoặc migrate rules có kiểm soát. Không direct update authorization tables nếu chưa hiểu inheritance và deny behavior. Move parent cũng có thể thay cách role ui hiển thị và cách administrator chọn permissions. Delete resource để lại orphan rules và documentation cũ. Title change ít ảnh hưởng runtime nhưng có thể khiến operator không nhận ra capability. Release note cần nêu. Acl code còn được cache với configuration, nên deploy phải clean đúng cache và bảo đảm mọi nodes có cùng code. Access ngẫu nhiên theo request thường là dấu hiệu node hoặc cache generation khác nhau. Nếu cần chuyển id, migration phải có inventory của role, integration và automation đang dùng quyền cũ. Sau deploy, hãy chạy script kiểm tra số account bị mất quyền, so kết quả trước và sau, rồi chỉ xóa compatibility mapping khi mọi consumer đã chuyển. Rollback cũng phải xét việc code cũ có hiểu resource mới hay không.

Testing acl cần role fixtures như viewer, editor, approver, exporter và financial viewer. Mỗi entry point có positive và negative cases. Approver được approve, editor và viewer bị deny. Direct url, mass action, data provider endpoint và rest token đều phải test. Viewer response không được chứa cost key, không chỉ column hidden. Business state test tách authorization với validation, chẳng hạn approver có quyền nhưng record không ở trạng thái cho phép. Integration tests có thể kiểm merged resource tree, controller constant và menu resource để phát hiện typo. Chỉ test Administrator role không đủ vì role này thường có toàn quyền. Permission regression suite phải chạy khi acl xml, menu, webapi hoặc ui component thay đổi. Test matrix nên bao gồm request trực tiếp tới mui render, export controller, mass action và api với token chỉ có đúng một capability. Cần kiểm tra response body, status code, audit log và việc không có side effect khi bị deny. Các test này phải chạy trên role hạn chế, vì Administrator thường che mất lỗi mapping do có gần như toàn bộ quyền.

Debug access denied bắt đầu từ caller type. Admin user, integration, customer và worker dùng context khác nhau. Sau đó xác định entry point là menu, controller, ui data source, rest route, layout block hay service. Tìm exact resource id và case. Kiểm module enabled, acl xml valid, parent resource và configuration cache. Xác nhận user được assign đúng role và selection. So sánh resources ở menu, controller và endpoint vì chúng có thể drift. Explicit business policy có thể thêm website hoặc ownership condition. Nếu lỗi ngẫu nhiên, so nodes và release version. Không flush mọi cache ngay vì sẽ mất evidence. Ghi actor, resource, entity và deny reason an toàn trong log giúp incident analysis, nhưng không log token hoặc sensitive payload. Khi điều tra, hãy chụp merged configuration hoặc dùng công cụ đọc resource tree thay vì chỉ nhìn một file module. Nếu deny chỉ xảy ra sau deploy, kiểm tra generated configuration, cache id, artifact hash và role assignment trên từng node. Một timeline rõ gồm request, actor, node, resource và policy result sẽ giúp phân biệt bug code với cấu hình vận hành.

Các incident phổ biến cho thấy ui security không đủ. Menu ẩn nhưng direct url chạy vì controller thiếu constant. Page bị deny nhưng grid data vẫn tải vì ui component thiếu acl resource. Cost column hidden nhưng json vẫn chứa value. Editor approve qua mass action dùng sai resource. Integration mất access sau resource rename. Mass assignment cho phép đổi approved state. Root cause thường là permission matrix không được áp dụng nhất quán trên mọi entry point. Fix bền vững cần service boundary, dto và negative tests, không chỉ thêm một check ở ui. Trong incident thật, hành động khẩn cấp có thể là disable endpoint, thu hồi integration token hoặc tạm hạ role trước khi sửa code. Sau đó cần xác định dữ liệu nào đã bị đọc hoặc sửa, phạm vi actor, thời gian và bằng chứng audit. Mỗi security bug cần thêm negative test để ngăn tái diễn. Review owner nên gồm developer hiểu flow, người phụ trách security và đại diện business của capability nhạy cảm.
