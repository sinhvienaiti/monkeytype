Khi developer nói muốn quay lại, câu hỏi đầu tiên phải là thay đổi đang ở đâu và đã được chia sẻ đến đâu. Một edit chưa stage khác hoàn toàn một commit đã push, và một commit đã deploy lại khác một database migration đã chạy. Nếu file tracked chỉ bị sửa local, restore có thể đưa working file về version trong index. Nếu file đã stage nhầm nhưng content vẫn cần, restore staged hoặc path reset chỉ thay index và giữ working edit. Nếu commit local chưa chia sẻ có phạm vi sai, soft hoặc mixed reset có thể đưa change về staged hay unstaged để viết lại. Nếu commit đã nằm trên shared branch, revert thường an toàn hơn vì tạo inverse commit và giữ audit trail. Nếu branch tip bị reset sai, reflog có thể chỉ ra vị trí cũ, nhưng candidate phải được giữ bằng recovery branch trước khi chạy thêm command. Nếu code đã deploy, lựa chọn không còn chỉ là git. Cần biết setup upgrade có chạy không, data patch nào đã ghi patch list, queue message nào đã phát, media nào đã đổi và external api nào đã nhận request. Một git revert không đảo các side effect đó. Vì vậy decision model tốt có bốn lớp là commit graph, index, working tree và runtime external state. Trước undo, developer lưu status, diff, head, reflog, remote tip và deployment identity. Sau đó mới chọn công cụ nhỏ nhất giải quyết đúng layer. Hard reset toàn repository để sửa một file là phạm vi quá lớn. Force push shared branch để bỏ một commit là phá audit và collaborator state. Database restore để sửa lỗi php không migration có thể tạo data loss không cần thiết. Senior developer không chọn command theo tên nghe quen, mà dự đoán ref nào di chuyển, index nào thay đổi, file nào bị ghi đè, commit nào được tạo và side effect nào còn tồn tại. Mục tiêu của recovery không phải chỉ làm git status sạch, mà khôi phục một trạng thái hệ thống tương thích, có evidence và có đường kiểm tra sau khi triển khai.

Commit level reset thay đổi current branch hoặc detached head rồi xử lý index và working tree theo mode. Soft reset chỉ di chuyển ref đến target. Index và working files vẫn giữ snapshot change, vì vậy change của commit bị bỏ khỏi tip vẫn staged. Đây là lựa chọn hữu ích khi local commit chưa chia sẻ cần sửa message hoặc bổ sung file. Mixed reset là default. Nó di chuyển ref và reset index theo target nhưng giữ working tree, nên change trở thành unstaged. Mode này phù hợp khi developer muốn chia lại phạm vi commit. Hard reset đi xa hơn, nó di chuyển ref, reset index và cập nhật tracked working files theo target. Staged và unstaged change trên tracked paths có thể mất khỏi working tree. Hard reset không đồng nghĩa xóa mọi untracked file như git clean, nhưng untracked path cản trở việc ghi tracked path có thể bị xóa. Trước reset, cần xem status, diff, cached diff và tạo recovery branch cho commit hiện tại. Recovery ref chỉ bảo vệ commit objects, không bảo vệ mọi uncommitted byte. Nếu local edit quan trọng, phải stash hoặc copy evidence trước operation. Path reset là trường hợp khác. Git reset head theo một path không di chuyển head, nó chỉ đưa index entry về source tree và giữ working file, về ý nghĩa tương đương unstage. Restore staged diễn đạt intent này rõ hơn. Reset merge và reset keep có thể bảo vệ một số local change, nhưng chúng không phải phép màu và có thể abort khi update sẽ ghi đè change. Trên shared branch, commit level reset tạo history rewrite và thường không phù hợp. Nếu rewritten task branch được policy cho phép, vẫn cần backup, collaborator coordination và force with lease. Dự đoán đúng reset nghĩa là luôn trả lời ba câu hỏi là ref có di chuyển không, index có đổi không và working tree có bị ghi lại không.

Restore được thiết kế cho path level recovery nên thường an toàn và rõ ý hơn khi developer không muốn di chuyển branch. Mặc định git restore path lấy content từ index để cập nhật working tree. Điều này bỏ unstaged edit của tracked path, vì vậy phải xem diff trước. Khi có staged flag, target là index và default source trở thành head, nên file được unstage nhưng working edit còn nguyên. Khi dùng cả staged và worktree cùng source head, index và working file đều trở về committed version, làm mất các edit local của path. Restore source cho phép lấy file từ commit khác mà không switch branch. Result xuất hiện như một working change cần review và commit mới. Patch mode cho phép chọn hunk thay vì bỏ cả file, hữu ích khi một phần edit sai còn phần khác cần giữ. Tuy nhiên hunk operation không thích hợp để tạo composer lock hoặc generated artifact vì file có thể cần tool tái tạo để bảo đảm consistency. Restore không xóa untracked file và không thay branch tip. Điểm dễ nhầm nhất là source default khác nhau. Restore working tree không staged lấy từ index, còn restore staged mặc định lấy từ head. Vì index có thể khác head, hai command cùng path có thể tạo result khác. Developer nên dùng status và cả git diff lẫn git diff cached để biết ba version đang tồn tại. Với conflict, ours và theirs option cũng phụ thuộc operation context như bài trước, nên không dùng theo thói quen. Restore là công cụ chính xác khi mục tiêu là một file hoặc hunk, nhưng sự chính xác chỉ có giá trị nếu source và target được hiểu đúng. Trước command destructive cho path, có thể copy diff ra file evidence hoặc tạo temporary commit trong recovery branch. Sau restore, cần xem diff, chạy syntax hoặc targeted test nếu file ảnh hưởng behavior. Một working tree sạch không chứng minh remote hay deployment đã đổi, vì restore chỉ là local state operation.

Revert phù hợp khi một bad commit đã được chia sẻ vì nó không xóa commit cũ khỏi history. Git tính inverse change trên current state và tạo commit mới. Audit trail cho thấy feature đã được đưa vào rồi bị đảo vì một lý do cụ thể. Revert vẫn có thể conflict nếu code hiện tại đã thay đổi quanh vùng cần đảo, vì vậy resolution phải dùng base và behavior evidence như merge conflict. Sau khi stage result, revert continue hoàn tất sequence, còn revert abort quay về state trước sequence. Khi đảo nhiều commit, dependency order quan trọng. Một commit sau có thể phụ thuộc schema hoặc api từ commit trước, nên không chọn range mơ hồ trong incident. No commit mode có thể áp nhiều inverse vào index để review chung, nhưng release commit quá lớn cũng khó audit. Commit message cần giải thích nguyên nhân, impact và điều kiện reapply. Revert không làm old commit biến mất, không xóa secret khỏi clone và không đảo database side effect. Nếu secret đã commit, credential phải được revoke hoặc rotate ngay, sau đó mới thực hiện history cleanup theo policy. Nếu bad commit chỉ ở private local branch, reset có thể phù hợp hơn revert vì không cần tạo noisy inverse commit. Nhưng khi branch protected, integration, staging hoặc production đã nhận commit, revert thường là default an toàn. Recovery commit phải được build và test như code mới, vì inverse patch áp trên current state có thể tạo behavior chưa từng tồn tại trước đó. Một revert pass về git chỉ chứng minh final tree được tạo. Developer vẫn cần composer validation, compile, automated test, smoke và deployed commit evidence. Rollback source không phải quay thời gian của toàn hệ thống, mà là phát hành một snapshot mới có mục tiêu đảo một change cũ.

Reflog là nhật ký local về việc các ref đã di chuyển, và head reflog còn ghi branch switch. Nó rất hữu ích sau reset sai, rebase, amend hoặc xóa branch, vì commit cũ có thể không còn reachable từ branch nhưng object vẫn tồn tại. Developer bắt đầu bằng git reflog với date và all để tìm entry theo thời gian và operation. Mỗi candidate phải được xem bằng git show trước khi dùng. Bước quan trọng nhất là tạo một named recovery branch trỏ vào candidate, vì selector như head at three có thể thay đổi ý nghĩa khi nhiều operation mới được ghi. Sau khi durable ref tồn tại, developer có thể inspect graph, test commit và quyết định merge, cherry pick hoặc reset private branch. Reflog không phải remote backup. Clone khác có reflog khác, push không gửi local reflog, và entry có expiration policy. Unreachable objects còn có thể bị garbage collection. Trong lúc recovery không nên chạy aggressive gc hoặc prune. Orig head đôi khi giữ tip trước merge hoặc reset, nhưng nó có thể bị command sau ghi đè, nên cũng phải chuyển thành named branch khi đúng. Nếu reflog không còn entry mà object chưa bị prune, git fsck có thể tìm unreachable commit. Output cần inspect cẩn thận vì có thể chứa nhiều object và blob không có path context rõ. Nếu work chưa từng commit hoặc stash, reflog không bảo đảm giữ bytes bị hard reset ghi đè. Khi đó editor local history, filesystem backup hoặc temporary files có thể là nguồn khác. Branch deletion thường chỉ xóa ref, không xóa object ngay. Remote branch, tag, collaborator clone hoặc reflog đều có thể cứu. Senior recovery luôn dừng thao tác phá hủy, thu evidence, giữ candidate bằng ref và chỉ sau đó thay branch chính. Cách này giảm nguy cơ một command cứu hộ lại làm mất recovery point vừa tìm thấy.

Revert merge commit cần mainline parent vì merge có nhiều parent và git phải biết history line nào được giữ làm baseline. Developer không được đoán parent một chỉ vì command phổ biến dùng m one. Cần xem pretty raw hoặc parent list, đọc graph và xác định branch nào đang checkout khi merge được tạo. Khi chọn parent một làm mainline, revert tạo change đảo phần merge đưa vào so với parent đó. Chọn sai mainline có thể loại code của nhánh chính hoặc giữ faulty feature. Hậu quả còn kéo dài đến lần merge sau. Merge commit vẫn nằm trong ancestry và ghi rằng hai histories đã được kết hợp. Revert chỉ đảo tree effect. Nếu merge lại cùng topic mà không có commit mới phù hợp, git thường chỉ mang change sau merge cũ, nên phần đã revert không tự quay lại. Muốn reintroduce, team có thể revert commit đã revert merge, tạo commits mới tái áp behavior hoặc rebuild topic trên base mới. Mỗi lựa chọn cần test vì surrounding code đã đổi. Nếu merge revert sai đã push, không reset protected branch. Tạo corrective revert hoặc new commit qua review. Trước operation cần lưu merge commit id, parent ids, diff relative mỗi parent, faulty behavior và expected recovery. Sau revert cần xem final parent graph, staged inverse, dependency, compile và application test. Trên cloud, merge revert commit chỉ là source input cho deployment mới. Database changes từ merge cũ vẫn còn trừ khi có recovery riêng. Mainline reasoning vì vậy phải nối graph với release lineage và data state, không chỉ parent number. Một command đúng cú pháp nhưng mainline sai là một trong những lỗi rollback nguy hiểm nhất vì nó tạo commit hợp lệ, dễ push và có thể chỉ lộ khi production flow chạy.

Adobe commerce làm recovery phức tạp vì code deployment có thể thay schema, data, configuration, queue và external state. Data patch được ghi trong patch list và thường chỉ áp một lần khi setup upgrade chạy. Nếu source commit bị revert, row patch list và data đã đổi không tự biến mất. Xóa row thủ công để patch chạy lại là anti pattern vì patch có thể không idempotent và tạo duplicate hoặc corruption. Patch revertable interface cũng không phải nút undo riêng một patch. Adobe dùng revert method trong module uninstall flow, có thể tác động tất cả revertable patches và module data, nên chỉ phù hợp khi lifecycle được thiết kế và test. Declarative schema có dry run để xem ddl, safe mode để tạo dump cho destructive schema operation được hỗ trợ và data restore để quay schema với dump sau khi checkout code trước. Cơ chế này không phải general database rollback và không đảo data patch, queue message, media hoặc external api. Khi bad release đã chạy migration, team lập matrix gồm deployed commit, ddl, patch list, data mutation, media, consumers và third party transaction. Nếu change chỉ là php behavior, revert commit và redeploy có thể đủ sau compile, cache và smoke. Nếu schema additive còn backward compatible, old code có thể chạy nhưng phải test. Nếu destructive schema hoặc data migration tạo incompatibility, cần forward fix, compensation patch hoặc database snapshot restore. Snapshot restore có data loss window, nên order, payment và customer changes sau snapshot phải được reconcile. External email hoặc payment capture cần compensation riêng. Mục tiêu rollback là khôi phục business consistency, không chỉ storefront trả status success. Runbook phải có database owner, application owner, reconciliation owner và monitoring. Recovery code cần đi qua integration và staging nếu severity cho phép, vì inverse change cũng là release mới. Nếu emergency buộc rút ngắn gate, residual risk phải được ghi rõ và theo dõi chặt.

Một cloud incident recovery tốt bắt đầu bằng freeze và evidence. Team ghi current commit, remote environment ref, cloud activity, build log, deployment time, error onset và database actions. Sau đó phân loại code only, schema, data patch, media, queue và external side effect. Nếu code only, developer tạo recovery branch từ đúng parent, revert faulty commit, review inverse, chạy composer validation, di compile, targeted tests và smoke trên integration. Final commit được promote qua hierarchy thật của project, không ssh edit deployed filesystem. Nếu database bị ảnh hưởng, code plan phải đi cùng snapshot hoặc forward compensation plan. Trước restore, xác nhận snapshot timestamp, scope, media consistency, data loss window và order payment reconciliation. Sau recovery, kiểm tra schema code compatibility, patch list, indexer, cron, consumer, cache, search và business metrics. Reflog và reset chỉ giúp local source recovery, không thay cloud backup. Protected branch không nên force reset để che incident vì điều đó phá audit và có thể không kích hoạt đúng deployment lineage. Revert commit giữ history và cho phép activity liên kết recovery release. Một evidence package nên chứa original bad commit, recovery commit, parent, test result, database decision, side effect compensation, cloud deployment id và monitoring result. Team cũng phải chuẩn bị rollback of recovery nếu inverse patch gây lỗi mới. Performance có thể thay đổi vì old code chạy trên new data, cache phải warm lại hoặc reindex tạo tải. Security patch không được revert máy móc nếu điều đó mở vulnerability. Trong một số incident, traffic mitigation hoặc forward fix an toàn hơn quay lại version cũ. Senior developer đánh giá recovery theo toàn bộ system state và thời gian phục hồi, không theo số lượng git command. Sau khi ổn định, post incident review phải cập nhật pre deployment backup, migration compatibility, automated gate và runbook để cùng loại lỗi không lặp lại.
