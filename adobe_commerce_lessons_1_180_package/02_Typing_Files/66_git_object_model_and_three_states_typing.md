Git trở nên dễ suy luận hơn khi người học bỏ hình ảnh commit là một thư mục chứa các dòng diff. Mô hình logic của git là một graph snapshot được xây từ object bất biến và các ref có thể di chuyển. Blob chứa bytes của file nhưng không biết filename. Tree đặt tên, mode và object id vào cấu trúc directory. Commit trỏ đến root tree, parent commit và metadata như author, committer cùng message. Annotated tag là object mô tả một target, còn branch chỉ là ref trỏ đến tip commit. Khi hai commit được so sánh, git tính diff giữa hai tree. Packfile có thể delta compress bytes để tiết kiệm storage, nhưng tối ưu vật lý đó không biến commit logic thành diff. Phân biệt hai lớp này giúp developer không đưa ra kết luận sai khi điều tra release. Object id nên được dùng như thuật ngữ trung lập vì repository có thể dùng object format khác nhau, không phải mọi repository tương lai đều bắt buộc sha một. Nội dung giống nhau trong cùng object database có thể reuse một blob dù xuất hiện ở path khác. Rename cũng không cần một object riêng; nó thường được phát hiện khi so snapshot. Với adobe commerce, điều này có nghĩa một commit xác định chính xác tree của custom module, theme, cloud configuration và composer lock đã tracked. Nó không tự chứa vendor, cache, generated code hoặc runtime media nếu các path đó không tracked. Senior developer cần biết đâu là snapshot nguồn và đâu là artifact được build từ snapshot. Khi một hotfix không xuất hiện trên môi trường, câu hỏi đầu tiên không phải editor đang hiển thị gì mà là commit nào chứa blob nào, branch ref nào trỏ đến commit đó và cloud activity đã build object id nào.

Bốn object chính có trách nhiệm khác nhau và không nên trộn. Blob là content. Tree là mapping từ name và mode đến blob, tree hoặc gitlink. Commit là node history trỏ root tree và parent. Annotated tag là object có target, tagger, message và có thể có signature, trong khi lightweight tag chỉ là ref trực tiếp. Filename không nằm trong blob, nên cùng blob có thể được tree tham chiếu bằng hai tên. Permission executable và symlink mode thuộc tree entry, không thuộc bytes của blob. Commit đầu không có parent, commit thường có một parent, merge commit có nhiều parent. History của branch là tập commit reachable từ tip theo parent edge; branch không chứa một mảng commit riêng. Ref có thể được lưu loose hoặc packed, vì vậy không nên kiểm tra branch bằng cách chỉ tìm file trong thư mục refs. Dùng show ref, for each ref và rev parse để hỏi git. Head lại là current checkout selector. Khi attached, head là symbolic ref đến local branch. Commit mới làm branch đó di chuyển. Khi detached, head trỏ trực tiếp commit. Developer vẫn commit được, nhưng line mới chưa có branch name giữ lại nếu họ chuyển đi. Tag release thường cần bất biến để artifact có thể truy vết; force move tag đã công bố làm cùng tên trỏ đến snapshot khác và phá audit. Signed tag hoặc commit có thể tăng integrity khi policy key đúng, nhưng hash và signature không thay thế review. Một object id chứng minh content identity trong mô hình git, không chứng minh code an toàn hoặc tác giả được tin tưởng. Tree cũng giải thích vì sao git không theo dõi directory rỗng, vì không có entry reachable để đại diện cho nó. Convention như gitkeep chỉ hoạt động vì đó là một file bình thường được tree tham chiếu, không phải tính năng đặc biệt của git.

Ba vùng trạng thái giải thích phần lớn câu hỏi hằng ngày. Working tree là file developer và tool đang sửa. Index là proposed snapshot cho commit tiếp theo. Head tree là snapshot đã commit mà current head resolve tới. Git status thực hiện hai so sánh chính và thêm untracked set. So sánh head với index tạo staged changes. So sánh index với working tree tạo unstaged changes. Path không có index entry và không ignored được báo untracked. Index không chỉ là danh sách tên file đã chọn. Nó lưu path, mode, blob object và metadata, đồng thời có thể giữ nhiều conflict stage. Git add đọc content hiện tại, tạo hoặc reuse blob rồi cập nhật index. Nó không khóa file và không tạo commit. Git commit xây tree từ index, tạo commit rồi update branch ref nếu head attached. Vì vậy unstaged edit không tự vào commit. Commit a có thể tự stage modification và deletion của tracked path nhưng vẫn không thêm untracked file, và nó có thể gom thay đổi ngoài ý muốn nếu developer không review. Một working tree sạch chỉ chứng minh hai so sánh local không có khác biệt và không có untracked path được báo. Nó không chứng minh commit đã push, remote branch đã cập nhật hoặc cloud đã deploy. Trước commit, senior developer đọc status hai cột, diff working với index và diff cached index với head. Sau commit, họ dùng show để xác nhận snapshot thật thay vì dựa vào trí nhớ về lệnh add. Index còn quan trọng trong merge vì một path có thể mang nhiều stage cho base, ours và theirs. Trạng thái bình thường dùng stage zero, nhưng conflict cho thấy index thực sự là cấu trúc snapshot có dữ liệu chi tiết chứ không phải hộp đánh dấu đơn giản.

Một file có thể tồn tại ở ba version cùng lúc. Giả sử config được commit với version một. Developer sửa thành version hai và chạy git add, nên index giữ blob version hai. Sau đó họ sửa working file thành version ba nhưng chưa add lại. Status sẽ báo path vừa staged vừa modified. Git show head path đọc version một. Git show colon path đọc index version hai. Cat file thường đọc version ba trong working tree. Git diff cached hiển thị thay đổi sẽ vào commit từ version một đến version hai. Git diff không option hiển thị thay đổi còn ngoài commit từ version hai đến version ba. Git diff head hiển thị tổng khác biệt working so với version một. Nếu developer chỉ nhìn một diff, họ có thể commit version hai trong khi tưởng version ba đã được chọn. Case composer lock đặc biệt nguy hiểm vì tool có thể sửa lock lần nữa sau lần add đầu. Reviewer phải xem cả staged và unstaged diff, sau đó quyết định content mong muốn và stage lại có chủ đích. Object id cung cấp cách kiểm chứng chính xác. Head colon path cho blob trong commit, colon path cho blob trong index, còn hash object trên working file tính id của content hiện tại. Ba id giống nhau nghĩa ba content giống nhau, dù stat metadata có thể khác. Direction của diff cũng phải được ghi rõ. Màu đỏ xanh không đủ vì command khác direction sẽ đổi cách đọc. Đây là nền tảng cho conflict lesson sau, nơi index có base, ours và theirs thay vì chỉ stage zero. Cách kiểm tra bằng object id hữu ích khi tool tự sửa file sau lần add đầu. Nếu developer stage lại không chủ đích, họ có thể thay đổi phạm vi commit. Nếu không stage lại, bản editor mới nhất vẫn ở ngoài commit dù màn hình đang hiển thị nó.

Ref và branch terminology thường gây lỗi release. Local branch là ref trong heads. Remote tracking ref như origin main là local bookmark về last known state của branch trên remote sau fetch hoặc operation phù hợp. Nó không phải kết nối trực tiếp luôn cập nhật. Đồng đội có thể push nhưng origin main trên máy bạn vẫn cũ cho đến khi fetch. Upstream lại là configuration của local branch, thường gồm remote và merge target. Nó giúp status tính ahead behind và giúp pull biết integrate với đâu. Upstream không phải object type và không bắt buộc là origin main. Khi điều tra, hãy ghi local head, branch ref, upstream, remote tracking id sau fetch và remote ref từ ls remote. Attached head cho biết commit mới sẽ di chuyển branch nào. Detached head có thể bình thường trong ci vì pipeline checkout exact commit. Trong workstation, commit detached cần được đặt branch nếu muốn giữ line dễ tìm. Multiple worktree còn làm trạng thái tinh tế hơn vì object database có thể share nhưng head và index là per worktree. Hai terminal trong hai worktree có thể cùng repository mà khác branch, staged content và working file. Vì vậy mọi incident note nên ghi repository root, worktree path và exact object id. Nói tôi đang ở main mà không có rev parse chưa đủ. Nói origin main có fix mà chưa fetch cũng chưa đủ. Evidence cần phân biệt cached local knowledge với server query thật. Upstream cũng ảnh hưởng hành vi pull và thông tin ahead behind, nên cấu hình sai có thể làm developer tích hợp nhầm branch dù local ref vẫn hợp lệ. Trước release, branch name chỉ là nhãn; exact object id và quan hệ reachability mới là bằng chứng có thể kiểm tra.

Khi fix không xuất hiện trên adobe commerce cloud, chuỗi điều tra phải đi từ local state đến artifact thay vì push lặp. Đầu tiên kiểm tra status, staged diff và unstaged diff. Tiếp theo mở path trực tiếp từ head để chứng minh commit chứa fix. Sau đó ghi local branch tip và fetch remote tracking ref. Nếu muốn chứng minh commit x có trong branch y, chạy ancestor test theo đúng direction x trước y. Query remote ref trực tiếp khi cần phân biệt local cache với server. Tiếp theo mở cloud activity hoặc build log để lấy commit id thực sự được build. Một commit có thể đã push vào repository nhưng vào branch không active hoặc environment khác. Nếu cloud build đúng commit mà behavior vẫn cũ, chuyển lớp điều tra sang composer dependency, patch, generated code, static content, cache, database schema và runtime configuration. Adobe cloud là git driven nhưng deployed result không chỉ là raw tree. Build đọc cloud config, cài dependency theo composer lock, chạy hook và tạo artifact. Vì vậy source commit identity và artifact identity cần được lưu riêng. Sửa file trực tiếp trên read only environment không phải workflow source of truth. Một empty commit có thể trigger redeploy nhưng không sửa nguyên nhân nếu artifact input hoặc configuration sai. Runbook tốt ghi từng object id và thời điểm ref di chuyển, giúp thấy edge nào trong chuỗi local branch, remote branch, cloud build và runtime chưa đồng bộ. Một branch remote đã chứa commit cũng chưa bảo đảm deployment hoàn tất, vì build có thể pending, failed hoặc bị hủy. Vì thế release evidence phải nối ref movement với activity status và artifact được tạo, không chỉ với thông báo push thành công. Review như vậy biến lock thành bằng chứng tái tạo thay vì file phụ được commit cho đủ.

Composer lock là ví dụ rõ nhất về tracked build input. Composer json mô tả constraint, còn lock ghi package version và dependency resolution cụ thể. Adobe cloud build cài dependency dựa trên lock, nên dependency change không có lock tương ứng có thể làm local và cloud khác nhau. Developer cần kiểm tra lock trong working tree, index và head giống như mọi file khác. Nếu lock vừa staged vừa modified, commit sẽ lấy staged version chứ không lấy file mới nhất editor đang thấy. Blob id của head lock có thể lấy bằng revision path, index lock bằng colon path và working lock bằng hash object. Sau khi commit, mở file từ commit và review diff package thay vì chỉ thấy command composer update kết thúc thành công. Vendor thường ignored và được build lại, vì vậy nó không phải bằng chứng commit chứa package. Commit giống nhau cũng chưa luôn bảo đảm artifact giống nhau nếu composer version, plugin policy, php platform, authentication, repository response, patch stack hoặc external script khác. Reproducibility yêu cầu kiểm soát toàn bộ input. Generated code, cache và static asset cũng là output, không nên force add chỉ để làm server giống máy local. Khi artifact khác, tách câu hỏi git tree có đúng không khỏi câu hỏi build có deterministic không. Cách tách này ngăn team dùng reset hoặc recommit để chữa vấn đề thực ra nằm trong environment hoặc dependency pipeline. Khi review dependency update, thay đổi lock cần được đọc như thay đổi source có tác động production. Package được thêm, bỏ hoặc đổi version phải phù hợp mục tiêu task, và platform requirement phải được kiểm tra trước khi merge vào environment branch. Giới hạn này giữ việc kiểm tra low level trong phạm vi an toàn và vẫn tôn trọng quy trình nhóm.

Senior review biến mô hình object thành checklist bằng chứng. Trước merge, reviewer xác nhận status, staged diff, untracked path và composer lock. Họ dùng commit id thay vì mô tả latest. Họ kiểm tra branch protected, upstream đúng và remote tracking đã refresh. Khi release, pipeline ghi commit, tag nếu có, lock checksum, tool version và artifact identifier. Khi incident, người trực vẽ graph ngắn bằng log decorated, xác định head attached hay detached, rồi so remote ref với cloud activity. Họ không gọi commit là diff, không gọi origin branch là live server và không gọi clean tree là deployed. Object model cũng giúp security. Secret đã commit không biến mất chỉ vì file bị xóa ở commit mới; object có thể còn trong history, remote, tag, clone hoặc reflog. Credential phải rotate và history remediation cần kế hoạch riêng. Signed commit hoặc tag chỉ có giá trị khi key trust và verification policy tồn tại. Sau incident, team xem edge nào thiếu evidence. Nếu không biết build commit, bổ sung deployment marker. Nếu lock không được review, thêm ci check. Nếu developer thường commit staged version cũ, thêm pre commit review hoặc training về hai diff. Mục tiêu không phải dùng plumbing command trong mọi task. Mục tiêu là có mental model đủ chính xác để porcelain output không còn bí ẩn và release decision có thể được chứng minh. Lệnh plumbing nên được dùng để giải thích hoặc kiểm chứng khi porcelain chưa đủ, không phải để bỏ qua guardrail. Update ref thủ công trong repository production có thể di chuyển branch ngoài workflow review, nên protected branch và server policy vẫn là lớp kiểm soát chính. Khi các bằng chứng đó được chuẩn hóa, việc bàn giao giữa developer, reviewer và người trực production trở nên nhanh hơn, ít phụ thuộc trí nhớ cá nhân và giảm xu hướng chạy lệnh sửa chữa trước khi hiểu trạng thái thật.
