Lựa chọn extension point bắt đầu từ loại thay đổi, không phải thói quen của developer. Nếu cần thêm hành vi nhỏ trước hoặc sau public method, plugin có thể phù hợp. Nếu nhiều subscriber độc lập phản ứng với một fact, event và observer có thể phù hợp. Nếu cần thay implementation của interface có chủ đích, composition hoặc preference có thể cần. Nếu chỉ cần biến thể constructor argument, virtual type rõ hơn subclass. Nếu thêm dữ liệu vào public data object, extension attribute đúng hơn plugin getter tùy ý. Nếu đổi presentation, layout, view model hoặc template nên được xem trước khi chạm controller hay repository. Mỗi mechanism có blast radius. Plugin tạo chain và sort order. Observer tạo hidden side effect và order không rõ. Preference chỉ có một winner. Template override mang upgrade diff. Câu hỏi review là owner public contract nào, behavior có cần nhiều module cùng tồn tại, failure có làm request fail không và test nào chứng minh. Một custom chạy đúng khi đứng một mình chưa đủ. Production có toàn bộ module, area và configuration merge. Vì vậy integration test phải bật stack thật. Không dùng sequence để che dependency kiến trúc. Sequence chỉ ảnh hưởng load và config merge, không làm behavior trở nên composable. Một decision matrix được ghi trong guide module giúp người sau hiểu vì sao chọn mechanism và khi nào phải refactor. Senior engineer ưu tiên mechanism yếu nhất đủ đáp ứng, vì càng mạnh càng dễ conflict và khó nâng cấp. Một requirement có thể cần nhiều mechanism nhưng mỗi mechanism phải có responsibility riêng. Ví dụ service mới giữ use case, plugin nhỏ nối core entry point, còn event phát fact sau success. Không đặt toàn bộ business flow trong around plugin. Sơ đồ call chain giúp reviewer thấy điểm fail và transaction. Khi core đã có public service contract, ưu tiên gọi hoặc decorate contract đó.

Plugin interception mạnh nhưng control flow dễ bị che. Before plugin có thể normalize input nhưng phải trả đúng parameter sequence và không bỏ validation. After plugin nhận output sau method và phù hợp enrich hoặc audit sau success. Around plugin bao toàn invocation, có thể thay input, output, exception và không gọi proceed. Chính khả năng đó làm around plugin nguy hiểm. Một around return sớm có thể khiến core method và mọi plugin phía trong không chạy. After plugin của module khác có thể mất mà không compile error. Plugin cũng có target limitation như final, static, non public và constructor. Không dùng plugin để thêm method vào class. Trên hot path, plugin getter có thể chạy hàng nghìn lần và khởi tạo dependency nặng. Sort order không nên là business architecture. Nếu correctness yêu cầu plugin a luôn trước b, cân nhắc một orchestration service rõ. Khi debug plugin chain, xác định area, type runtime, preference, plugin disabled flag và sort order. Trace around có gọi proceed trong mọi branch. Kiểm tra input đã bị plugin trước đổi. Một plugin khai báo trên interface có thể áp dụng rộng hơn dự kiến tùy object implement. Test happy path, exception path và module combination. Trong upgrade, compare signature target và public api status. Một method vẫn tồn tại nhưng semantic đổi có thể làm plugin sai. Around plugin chỉ để đo thời gian thường không đáng; observability hoặc decorator có thể rõ hơn. Plugin test nên kiểm tra cả null, exception và plugin khác thay input. Một after plugin không được giả định result luôn là model nếu contract cho phép interface hoặc null. Khi around catch exception, nó phải giữ loại lỗi và observability theo policy. Swallow exception để storefront không lỗi có thể làm dữ liệu silently inconsistent.

Observer phù hợp khi publisher phát fact và nhiều subscriber độc lập có thể phản ứng. Tuy nhiên event payload, timing và area là contract ngầm. Observer đồng bộ chạy trong request hoặc transaction hiện tại có thể làm save chậm hoặc fail. Không giả định mọi event được dispatch sau commit. Nếu observer gọi save cùng entity trong save event, recursion hoặc duplicate side effect có thể xảy ra. Cần guard rõ nhưng guard static mù có thể che event hợp lệ khác. Observer name trong merged configuration phải unique. Hai module dùng cùng name có thể override configuration. Business order không nên phụ thuộc observer order nếu framework không hứa. Nếu invoice creation phải luôn reserve credit trước gửi integration, orchestration service rõ hơn hai observer cạnh tranh. Event name nên namespace đủ để tránh collision. Payload không nên là mutable model được observer tùy ý thay theo order. Data contract hoặc ids rõ giúp giảm coupling. Khi observer fail, policy phải rõ: rollback core action, log và tiếp tục hay enqueue retry. Không swallow exception mù vì business state có thể sai. Khi debug, ghi event name, area, observer class, elapsed và exception. Tắt observer trong staging để isolate nhưng không dùng production disable làm root fix. Nếu side effect dài hoặc retryable, observer có thể tạo outbox/message thay vì gọi network trực tiếp. Event giúp decoupling nhưng không miễn thiết kế consistency. Event inventory nên ghi publisher location và timing tương đối với commit. Cùng tên event ở admin và frontend có thể có payload khác nếu area configuration khác. Observer chỉ đăng ký area cần thiết để giảm cost. Một event không có tài liệu payload nên được bọc bởi adapter nội bộ nếu nhiều module phụ thuộc lâu dài. Nếu publisher thay payload hoặc timing trong core upgrade, observer có thể sai dù tên event giữ nguyên. Integration fixture nên assert field dùng thật và transaction state. Một observer không dùng payload phải tránh load lại toàn entity nếu event chạy trên list lớn.

Preference là extension point mạnh vì thay implementation được resolve cho type. Merged configuration chỉ giữ một preference cho một type, nên hai module cùng thay class tạo winner cuối và behavior module kia biến mất. Di compile có thể vẫn thành công vì graph hợp lệ. Đây là conflict semantic. Preference subclass concrete còn phụ thuộc protected method và internals, dễ vỡ khi upgrade. Khi cần thêm validation nhỏ, plugin hoặc policy composition thường an toàn hơn. Khi cần thay adapter theo interface, preference có thể hợp lý nếu một owner chủ động chọn implementation. Decorator implement cùng interface và gọi inner service, cho phép nhiều behavior xếp rõ hơn nhưng cần graph tránh recursion. Virtual type giúp tạo inner và outer instance với argument khác. Không inject decorator vào chính nó qua preference không kiểm soát. Khi điều tra, dùng di info, merged config và code search toàn dự án để tìm preference. Kiểm tra module load order không chỉ composer package. Nếu hai behavior đều cần, refactor thành interface nhỏ, strategy pool hoặc decorator chain. Không cố chain hai preference bằng subclass module này extends class module kia, vì dependency giữa extension trở nên mong manh. Preference inventory nên là gate upgrade. Mỗi preference cần rationale, target api stability, alternative đã xem xét và integration test. Càng gần core concrete class, risk càng cao. Khi refactor preference, hãy tạo characterization test cho behavior hiện tại trước. Sau đó tách rule độc lập thành policy hoặc decorator, giữ implementation core qua composition. So generated di graph và runtime. Rollout có feature flag hoặc module version guard nếu nhiều package deploy không cùng lúc. Không xóa preference trước khi mọi caller đã chuyển. Trong emergency fix, thêm preference thứ hai để override winner thường làm debt nặng hơn. Hãy containment bằng module disable hoặc targeted patch có rollback, rồi refactor graph. Merged configuration cần được lưu làm evidence trước và sau để biết behavior nào biến mất.

Virtual type và extension attribute thường bị hiểu sai. Virtual type không tạo php class mới và không intercept method. Nó tạo cấu hình object variant với constructor argument khác. Nó hữu ích khi cùng implementation cần policy, pool hoặc adapter khác ở một injection point. Lạm dụng virtual type nhiều tầng làm graph khó đọc, nên tên phải nói responsibility và di test phải xác nhận instance runtime. Extension attribute mở rộng public data interface nhưng không tự tạo database column, hydrate hoặc save. Repository hoặc plugin cần load và persist. Với get list, load từng row tạo n cộng một. Batch theo ids hoặc join phù hợp. Extension attribute cũng ảnh hưởng rest, graphql và serialization, nên scope và nullability phải rõ. Không dùng plugin getter gọi repository mỗi lần để giả lập attribute. Nếu dữ liệu chỉ dành cho presentation, view model có thể tốt hơn public data contract. Nếu dữ liệu là business property ổn định, custom attribute hoặc schema field và service contract cần cân nhắc. Khi debug missing extension attribute, kiểm tra declaration, generated code, data object, repository population, web api output và cache. Khi save không persistence, kiểm tra handler write. Mechanism đúng phải hoàn thành toàn lifecycle, không chỉ làm getter xuất hiện. Virtual type naming nên thể hiện role như export retry policy thay vì tên kỹ thuật dài. Nếu graph có nhiều inner service giống nhau, dùng di inspection trong test để tránh inject nhầm. Extension attribute cần cache và batch plan; nếu attribute đắt và chỉ một màn hình dùng, một query service riêng có thể hợp lý hơn public attribute toàn entity. Nếu virtual type chỉ khác một scalar nhưng được dùng ở nhiều area, config scope phải được test. Một argument override global có thể ảnh hưởng admin ngoài ý định. Extension attribute write path cũng cần authorization, không chỉ hydrate response.

Presentation customization có extension point riêng. Đổi vị trí block, bỏ section hoặc thêm view model nên bắt đầu từ layout. Template override phù hợp khi markup thực sự phải đổi, nhưng copy toàn template làm diff upstream lớn. Security fix hoặc accessibility improvement trong core có thể không vào override. Giữ override nhỏ, ghi source version và diff khi upgrade. Không plugin repository chỉ để đổi label hoặc css class. Ui component merge có scope và name conflict tương tự configuration khác. Cacheability phải được review. Một block private bị đặt trong full page cache có thể lộ dữ liệu giữa user. Một template gọi service nặng trong loop có thể tạo query n cộng một. View model giúp tách logic nhưng không nên chứa business mutation. Khi module và theme cùng override, precedence cần test trên store thật. Layout handle, area và theme inheritance tạo nhiều lớp. Debug bằng layout hints, merged layout và template path, không sửa core file. Nếu customization ảnh hưởng email, admin và storefront, có thể cần contract dữ liệu chung nhưng view riêng. Presentation mechanism không được dùng để bypass authorization; dữ liệu nhạy cảm phải không được cấp từ backend. Một lựa chọn extension point tốt giữ layer đúng trách nhiệm. Template review cần compare upstream security patch. Một override copy cũ có thể bỏ escaping mới hoặc form key. Automated diff theo release giúp phát hiện. Full page cache test phải dùng hai customer context để chắc dữ liệu không leak. Presentation performance test kiểm tra query count trong list và asset load, không chỉ screenshot. Email template và admin ui cũng có inheritance khác storefront. Upgrade checklist phải bao phủ từng area được override. Không copy asset hoặc javascript bundle core nếu mixin, layout hoặc component extension nhỏ hơn có thể đáp ứng.

Conflict control cần automation và inventory. Quét preference toàn codebase, liệt kê plugin theo target, sort order và area, liệt kê observer theo event và name, cùng template override. Không dựa allow list vĩnh viễn; mỗi exception cần owner. Khi incident behavior mất sau deploy, xem config cache và generated code nhưng đừng chỉ clear cache. Xác định module mới, merge order và chain. Nếu around không proceed, fix control flow. Nếu preference winner thay, refactor. Nếu observer name collision, đổi name và test. Nếu layout override che patch, rebase template. Postmortem nên tạo guard như static scan hoặc integration assertion. Conflict là property của combination, nên quy trình phải kiểm tra combination. Static scan chỉ là lớp đầu. Conflict semantic cần scenario chạy đủ module. Tạo một matrix cho module core, payment, b2b và custom extension trên các use case quan trọng. Khi matrix quá lớn, ưu tiên theo shared targets như repository, checkout và company. Observability trong staging giúp thấy method implementation và plugin timing mà không bật debug production lâu. Inventory nên xuất machine readable để pipeline so thay đổi. Một pull request thêm around plugin, preference hoặc full template override có thể yêu cầu architecture approval. Metric runtime giúp ưu tiên debt theo traffic và latency, không chỉ số lượng extension point. Báo cáo conflict nên được giữ cùng release artifact để điều tra regression. Khi pipeline phát hiện target shared mới, reviewer có thể yêu cầu test combination trước merge.

Checklist expert cho extension point gồm mười câu. Behavior thuộc layer nào. Public owner nào. Mechanism yếu nhất đủ dùng là gì. Có nhiều extension cùng tồn tại không. Order có ảnh hưởng correctness không. Failure propagation là gì. Hot path cost ra sao. Security invariant nào phải giữ. Upgrade surface nào bị phụ thuộc. Rollback thế nào. Test không chỉ output cuối mà cả method được gọi, event được phát, transaction và query count. Khi composition rõ hơn interception, ưu tiên composition. Một hệ thống dễ nâng cấp không phải hệ thống không tùy biến, mà là hệ thống tùy biến qua boundary rõ, override nhỏ, test combination và có evidence khi core thay đổi. Một quyết định tốt còn có exit strategy. Nếu core release cung cấp extension point chính thức mới, module phải có kế hoạch bỏ override mạnh. Sau deploy, canary phải kiểm tra behavior core và behavior custom cùng tồn tại. Rollback module có thể yêu cầu compile và cache invalidation, nên thời gian phục hồi phải được thử trước. Mỗi mechanism mạnh cần owner, test và ngày review lại. Documentation nên nêu fallback khi extension bị disable và dữ liệu nào cần cleanup.
