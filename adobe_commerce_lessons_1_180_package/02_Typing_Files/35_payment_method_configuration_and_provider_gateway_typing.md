Payment Provider Gateway trong Adobe Commerce tách payment integration thành nhiều component có trách nhiệm rõ. Sales management gọi payment method facade. Facade lấy command theo action từ command pool. Command dùng request builder tạo payload, transfer factory tạo request transport, gateway client gọi provider, response validator kiểm tra kết quả và response handler cập nhật payment state. Error mapper chuyển provider code thành message an toàn. Cách tách này giúp authorize, capture, void và refund được test độc lập. Một payment model duy nhất vừa build payload, gọi network, save order và map error rất khó retry an toàn. External provider không nằm trong cùng database transaction với Commerce, nên integration cần state machine, idempotency và reconciliation. Khi học kiến trúc, hãy theo luồng từ sales action tới provider rồi quay lại transaction state. Mỗi component chỉ nên làm một loại việc và không được vượt boundary chỉ vì code ngắn hơn. Một architecture diagram nên ghi input, output và side effect của từng component. Khi client vừa gọi provider vừa save order, hoặc handler tự build request mới, boundary đã bị phá. Review theo trách nhiệm giúp phát hiện coupling trước khi integration gặp lỗi retry hoặc cần thêm payment action mới.

Các payment operation có nghĩa khác nhau. Authorize giữ funds nhưng chưa rút tiền cuối cùng. Sale thực hiện authorize và capture trong một lần. Capture rút funds từ authorization. Void hủy authorization chưa capture. Refund trả funds đã capture. Commerce action và provider capability phải khớp. Nếu payment method cấu hình capture nhưng command pool không có capture, invoice có thể fail runtime. Partial capture, multiple capture và partial refund còn phụ thuộc provider. Không được hardcode capability chỉ từ order status. Value handler có thể tính can capture hoặc can void theo transaction state và amount đã xử lý. Authorization cũng có thể hết hạn. Test cần có authorize only, authorize and capture, void trước capture, refund sau capture và amount một phần. Việc gọi sai operation không chỉ tạo lỗi kỹ thuật mà có thể giữ hoặc di chuyển tiền không đúng business intent. Business team cũng cần chọn payment action theo fulfillment risk. Hàng số có thể capture sớm, còn hàng cần kiểm tra tồn kho có thể authorize trước. Developer không nên quyết định chỉ dựa trên field có sẵn. Provider fee, authorization lifetime và cancellation policy phải được đưa vào lựa chọn.

Custom payment module cần dependency tối thiểu vào Payment và Sales, cùng Checkout nếu method xuất hiện trên storefront. Module riêng bảo vệ upgradability và tránh sửa core. Configuration thường gồm module metadata, default payment config, Admin system field, dependency injection và area-specific configuration. Credential phải được mã hóa hoặc quản lý như secret. Sandbox và production cần tách rõ. Store scope của config phải được đọc theo quote hoặc order, không theo current Admin context tùy ý. Một method active chưa chắc available vì còn country, currency, order total, customer, company, fraud rule và provider health. Configuration là policy input, còn validator quyết định method có hợp lệ trong transaction hiện tại không. Debug cần phân biệt field chưa save, config scope sai, validator fail và frontend không render. Configuration change cần audit vì đổi environment, merchant account hoặc payment action có thể ảnh hưởng money flow ngay lập tức. Secret rotation phải được test với request thật và rollback key. Nếu website dùng currency khác, credential hoặc merchant account cũng có thể cần mapping riêng thay vì dùng một global value cho mọi store.

Storefront và Admin có thể dùng payment flow khác nhau. Flag can use checkout quyết định method có xuất hiện ở storefront, còn can use internal quyết định Admin order creation. Storefront có browser của cardholder, device data, hosted field hoặc challenge. Admin có thể chỉ dùng token đã lưu hoặc không được phép dùng method đó. Adobe cho phép frontend và adminhtml dependency injection khác nhau. Cùng virtual type có thể nhận builder khác theo area. Không nên đưa challenge builder vào Admin nếu không có customer browser. Ngược lại, Admin flow không được bypass provider security bằng cách bỏ field bắt buộc. Test phải chạy cả checkout thật và Admin create order. Một method hoạt động ở storefront không chứng minh Admin flow đúng, và lỗi Admin không nên được sửa bằng cách bật method rộng hơn mà không hiểu provider policy. Area test nên xác nhận request builder thật sự khác khi cần, không chỉ method visibility. Một payment method có thể hiện trong Admin nhưng gửi payload thiếu browser data và bị provider decline. Nếu Admin không được hỗ trợ, nên ẩn rõ thay vì để operator thử rồi nhận lỗi khó hiểu sau khi order đã tạo dở dang.

Payment method facade là lớp kết nối sales management với gateway infrastructure. Adapter mặc định nhận value handler pool, validator pool và command pool. Sales code không cần biết provider endpoint hoặc payload. Facade chỉ điều phối và không nên chứa toàn bộ provider business logic. Value handler đọc hoặc tính configuration như can void hoặc can capture. Validator pool kiểm tra country, currency, availability và global condition trước place order. Payment method validator khác response validator. Lớp đầu kiểm tra method có dùng được với quote hoặc order không. Lớp sau kiểm tra response provider có hợp lệ không. Frontend disable method chỉ là trải nghiệm. Server validation vẫn bắt buộc. Nếu customer sửa request hoặc gọi api trực tiếp, global validator phải chặn transaction không hợp lệ. Validator result nên gắn với message phù hợp cho customer và reason đủ cho operator. Không nên trả cùng một lỗi chung cho currency sai, country bị chặn và provider unavailable trong internal log. Tuy nhiên storefront cũng không cần tiết lộ fraud threshold hoặc merchant configuration chi tiết. Validation order cũng cần ổn định để customer nhận lỗi quan trọng nhất thay vì message thay đổi ngẫu nhiên giữa các request.

Gateway command đại diện một payment action. Một integration thường có authorize command, capture command, void command và refund command. Command được cấu hình bằng request builder, transfer factory, gateway client và optional validator, handler, error mapper. Command pool map action name tới command. Cách này cho phép thêm hoặc thay action mà không sửa facade. Missing command và capability mismatch là lỗi cấu hình phổ biến. Command cần chuyển transport hoặc provider error thành result mà Commerce hiểu, nhưng vẫn giữ correlation và transaction reference cho điều tra. Không nên nuốt exception rồi trả false chung chung vì support không phân biệt decline, timeout và invalid signature. Decline thường không retry tự động, còn timeout cần query trạng thái. Command boundary là nơi điều phối, không phải nơi nhồi mọi payload field hoặc trực tiếp render customer message. Command name là contract giữa payment facade và pool, nên typo hoặc override từ module khác có thể làm runtime failure. DI compile không luôn phát hiện key thiếu nếu action chỉ chạy trong flow hiếm. Integration test phải thực thi từng command thật qua facade, không chỉ instantiate object graph.

Request builder tạo provider payload từ payment subject và order data. Builder nhỏ nên sở hữu một concern như merchant, amount, order, customer, address, token hoặc risk. Builder composite ghép chúng lại. Nếu hai builder tạo cùng key, merge strategy có thể ghi đè value mà unit test riêng lẻ không phát hiện. Integration test phải kiểm tra payload cuối. Amount cần xử lý currency minor unit và rounding, không dùng float tùy tiện. Order total phải được lấy từ server, không tin browser. Token hoặc hosted payment reference được ưu tiên để giảm card data đi qua Commerce. Builder không nên gọi provider và không save order. Nó chỉ biến domain input thành request data. Khi payload thay đổi theo provider version, tách builder giúp giới hạn phạm vi sửa và kiểm tra backward compatibility. Payload snapshot trong test nên loại secret nhưng giữ structure, amount và reference. Khi provider đổi api version, diff giúp thấy field bị mất hoặc đổi type. Builder owner cũng cần quy ước không mutate payment object. Request generation nên deterministic với cùng subject để retry và audit dễ hơn.

Transfer factory chuyển payload thành transfer object chứa endpoint, method, header, body và authentication. Sandbox cùng production endpoint phải được chọn từ secure store configuration. Authorization header và secret không được xuất hiện trong debug log. Timeout cần được chọn có chủ đích. Timeout quá dài giữ worker và làm checkout treo. Timeout quá ngắn tăng trạng thái không xác định. Gateway client nhận transfer, gọi provider và trả response. Client là transport layer, không nên save payment hoặc order. Nếu network timeout xảy ra sau khi provider đã nhận request, Commerce không biết transaction thành công hay chưa. Retry capture mù có thể charge hai lần. Integration cần idempotency key, provider status query, webhook và reconciliation. Unknown outcome là trạng thái cần được thiết kế, không phải exception có thể bỏ qua. HTTP client cần phân biệt connect failure, read timeout và provider response lỗi. Ba trường hợp tạo recovery khác nhau. Circuit breaker hoặc health signal có thể tạm ẩn method khi provider down, nhưng không được làm mất transaction đang pending. Metric latency và timeout nên tách theo operation vì capture thường quan trọng hơn availability check.

Response validator xác minh response provider trước khi Commerce tin kết quả. Validation có thể kiểm tra data format, signature, merchant account, amount, currency, transaction type và provider status. Http success không đủ để kết luận payment success. Một response có code thành công nhưng amount khác order phải fail closed. Validator implement contract và trả result gồm trạng thái cùng error. Validator composite cho phép ghép nhiều check. Response handler chỉ chạy với response đã được chấp nhận và cập nhật transaction id, authorization id, provider status hoặc additional information an toàn. Handler không được lưu card number, security code hoặc secret. Side effect như email nên gắn với lifecycle sau commit phù hợp, tránh gửi success khi database rollback. Validator trả lời có tin response không, còn handler trả lời ghi state nào từ response đó. Signature validation cần dùng raw body hoặc canonical form đúng theo provider contract. Parse rồi serialize lại có thể làm signature mismatch. Clock skew và timestamp window cũng cần monitor. Khi validation fail hàng loạt sau provider change, team phải giữ sample an toàn để điều tra mà không bỏ qua verification trên production.

Error mapper chuyển provider error code thành message an toàn và có thể dịch. Không nên hiển thị raw response vì có thể lộ fraud rule, internal identifier hoặc thông tin nhạy cảm. Internal log cần provider code, correlation id và reference nhưng phải mask token cùng credential. Decline, system error và validation failure cần được phân loại. Decline có thể yêu cầu customer dùng method khác. Provider unavailable có thể cần status query hoặc retry có kiểm soát. Signature mismatch là security signal. Response validator không nên chịu trách nhiệm map message vì nó thuộc layer xác minh. Gateway command hoặc error mapper chọn message cho customer và operator. Một message generic không có nghĩa log cũng generic. Support cần evidence đủ để xử lý mà không biến storefront thành kênh tiết lộ provider policy. Error taxonomy cũng giúp customer support chọn hành động. Decline có thể hướng dùng payment method khác. Duplicate reference cần query transaction cũ. Invalid credential là incident vận hành. Rate limit có thể retry sau delay. Không nên cho customer bấm lại liên tục khi provider đã nhận transaction nhưng response đang unknown.

Authorize only và authorize capture tạo lifecycle khác. Với authorize only, Commerce cần lưu authorization reference và amount còn có thể capture. Capture có thể xảy ra khi invoice được tạo. Partial capture cần giữ captured total, remaining authorization và relation với invoice. Multiple capture chỉ hoạt động nếu provider hỗ trợ. Với sale, funds được capture gần place order, nên timeout có rủi ro order và provider lệch state. Provider có thể capture thành công nhưng Commerce rollback. Ngược lại order có thể tồn tại trong khi callback báo failure sau. Không có distributed transaction tự động giữa database và provider. Idempotency, durable state và reconciliation phải bù khoảng trống. Test cần cố tình tạo network reset sau request send để chứng minh recovery, không chỉ test response success và decline thông thường. Authorization amount có thể khác final captured amount do shipment, tax adjustment hoặc partial cancellation, nhưng mọi thay đổi phải nằm trong provider capability. Nếu capture vượt authorization, provider có thể reject hoặc tạo behavior ngoài dự kiến. Invoice creation cần đọc remaining amount thay vì dùng original order total một cách máy móc.

Void và refund không giống nhau. Void hủy authorization chưa capture, còn refund trả tiền đã capture. Cancel order cũng không tự chứng minh provider void thành công. Flow phải gọi operation phù hợp, validate response và update transaction. Nếu void timeout, authorization có thể đã được hủy hoặc vẫn tồn tại, nên không retry mù. Admin action availability cần dựa trên payment capability và transaction state. Refund cần nối Commerce credit memo với provider money movement. Credit memo offline không gọi provider và phải được phân biệt trong audit. Partial refund không được vượt captured amount còn lại. Provider có thể xử lý refund async, vì vậy accepted không luôn là final success. Webhook hoặc query cập nhật state sau. Một UI hiển thị refund complete quá sớm có thể khiến finance tin tiền đã trả trong khi provider vẫn pending. Online và offline refund phải được đặt tên rõ trong Admin training. Operator có thể nghĩ credit memo luôn trả tiền cho customer, trong khi offline option chỉ sửa Commerce record. Reconciliation report nên liệt kê credit memo không có provider refund và provider refund không có matching credit memo.

Webhook xử lý trạng thái đến từ provider như capture, refund, dispute hoặc failure. Endpoint phải validate signature, timestamp và replay protection theo provider contract. Provider có thể gửi cùng event nhiều lần, nên handler phải idempotent. Event cũng có thể đến out of order. Refund update có thể được nhận trước một capture notification bị delay. State machine phải dùng provider transaction và event semantics thay vì chỉ arrival time. Unknown order reference cần được quarantine và alert, không tự tạo transaction tùy tiện. Webhook response nên nhanh, còn xử lý nặng có thể đưa vào durable queue sau khi event đã được xác minh và lưu. Logging phải giữ event id và correlation nhưng mask data nhạy cảm. Test duplicate, replay, invalid signature và out of order là bắt buộc. Webhook endpoint nên lưu event envelope sau verification trước khi xử lý domain logic, để retry không phụ thuộc provider gửi lại. Event id là natural idempotency key nếu provider đảm bảo uniqueness. Nếu không, cần key từ transaction, event type và provider sequence theo contract. Event storage cần retention và access policy vì payload có thể chứa personal data hoặc transaction detail nhạy cảm.

Security boundary của payment integration phải giảm tối đa card data đi qua Commerce. Hosted field, redirect, provider sdk và tokenization giúp giảm scope. Card verification code không được lưu sau authorization. Browser amount, currency và order reference phải được server tính hoặc xác minh. Secret được encrypt, rotate và giới hạn Admin access. Debug mode production không được dump full transfer. Payment additional information cũng không phải nơi lưu card number. Callback từ browser không được tin chỉ vì có transaction id, mà phải được verify bằng signed response hoặc provider query. Một data flow diagram nên đánh dấu token, secret, personal data và provider reference ở từng component. Security review phải bao gồm log platform, support export và monitoring, không chỉ database. Token cũng là dữ liệu nhạy cảm dù không phải card number. Một số token có thể charge lại và cần encryption hoặc provider vault reference. Log masking phải áp cho request, response, exception và tracing tag. Security review nên kiểm tra cả staging vì test credential và customer data thường bị bảo vệ kém hơn production.

Idempotency bảo vệ mọi money movement khi request retry hoặc customer bấm nhiều lần. Key phải ổn định cho cùng logical action nhưng khác giữa authorize, capture và refund. Provider reference được lưu ngay khi response hợp lệ. Khi timeout, integration query provider bằng merchant reference hoặc idempotency key trước khi retry. Reconciliation job so sánh Commerce order, payment transaction, invoice, credit memo và provider amount. Mismatch không phải lúc nào cũng được sửa tự động. Captured ở provider nhưng order thiếu có thể cần manual review hoặc refund. Commerce capture nhưng provider không có transaction có thể là state corruption. Automation nên classify safe retry, safe status import và manual investigation. Report phải theo currency và amount, không chỉ count. Một transaction orphan nhỏ nhưng lặp nhiều lần vẫn là financial incident. Idempotency database record cần transaction state và response reference, không chỉ một cache key có thể hết hạn. Nếu key biến mất trước retry muộn, duplicate charge vẫn có thể xảy ra. Reconciliation schedule phải nhanh đủ cho business risk nhưng không gọi provider quá mức hoặc bị rate limit.

Transaction boundary là phần cốt lõi của payment architecture. External provider call và Commerce database không cùng atomic transaction. Provider có thể success rồi Commerce rollback. Commerce có thể commit order rồi webhook báo failure. Network có thể mất response sau khi provider xử lý. Design cần explicit state như pending, authorized, captured, failed hoặc unknown theo provider contract. Durable job, webhook và reconciliation giúp đưa state hội tụ. Không nên giữ database transaction mở quá lâu quanh slow network call vì lock và throughput. Nhưng cũng không được tách state change tùy tiện làm mất relation. Mỗi step cần idempotency và recovery. Compensation không phải lúc nào cũng là tự động refund. Nếu provider captured nhưng order thiếu, system cần biết product fulfillment đã xảy ra hay chưa và customer communication nào đã gửi. Manual queue với evidence đầy đủ đôi khi an toàn hơn một automation xử lý mọi orphan theo cùng rule.

Best practice là dùng module riêng và tách facade, command, builder, client, validator, handler cùng mapper. Capability và command pool phải nhất quán. Amount cùng currency được validate server-side. Card data được token hóa và secret được mask. Mọi authorize, capture, void hoặc refund có idempotency. Timeout dẫn tới status query, không retry mù. Webhook được verify, duplicate safe và chịu out of order. Commerce được reconciliation với provider. Credit memo và provider refund được phân biệt. Storefront cùng Admin được test riêng. Code sample Braintree cũ chỉ dùng để hiểu pattern vì Adobe ghi sample không còn được hỗ trợ. Khi review integration, hãy tìm boundary bị trộn, side effect không idempotent và state không thể giải thích bằng transaction history. Dependency review cần xác nhận module sample hoặc package provider đang được Adobe hay vendor hỗ trợ cho exact Commerce version. Pattern framework ổn định không có nghĩa mọi code example cũ vẫn an toàn. Security patch, sdk version và provider api deprecation cũng phải nằm trong release planning. Vendor release note và certification requirement của payment provider cũng cần được review trước mỗi upgrade.

Những điểm phải nhớ là gateway command điều phối một payment action. Command pool chọn command. Request builder tạo payload. Transfer factory tạo request. Gateway client gọi provider. Response validator xác minh kết quả. Response handler cập nhật payment state. Error mapper tạo message an toàn. Authorize, sale, capture, void và refund có semantics khác nhau. Storefront với Admin có thể dùng configuration riêng. Provider call không atomic với database. Idempotency, webhook, state machine và reconciliation là nền tảng. Không lưu card data nhạy cảm, không log secret và không tin amount từ browser. Sau timeout, phải xác minh provider trước retry. Một payment integration tốt không chỉ chạy happy path mà còn phục hồi được khi network, database và callback xảy ra ở thứ tự bất lợi. Khi trả lời câu hỏi Expert, hãy mô tả cả success path và failure recovery. Chỉ nêu command pool hoặc request builder là chưa đủ nếu bỏ timeout, duplicate webhook và database rollback. Payment architecture được đánh giá bằng khả năng bảo toàn money state trong điều kiện không chắc chắn. Một câu trả lời tốt luôn nêu invariant, evidence và compensation khi hai hệ thống không cùng trạng thái.
