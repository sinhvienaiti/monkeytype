Cherry pick phù hợp khi một nhóm cần đưa một thay đổi cô lập sang nhánh có lịch sử và mục đích phát hành khác mà không kéo theo toàn bộ nhánh nguồn. Cơ chế này không gắn commit nguồn vào ancestry của nhánh đích. Nó lấy phần thay đổi mà commit nguồn tạo ra so với parent, thử áp phần thay đổi đó lên trạng thái hiện tại, rồi thường ghi một commit mới. Vì parent, committer, thời gian và có thể cả nội dung resolution khác, hash mới không giống hash nguồn. Điều này giải thích vì sao tìm một hash trong log không đủ để kết luận fix đã có hay chưa. Trước khi chọn cherry pick, developer cần hỏi liệu mục tiêu thật sự là lấy một patch riêng lẻ, tích hợp toàn branch hay replay cả chuỗi trên base mới. Merge phù hợp hơn khi muốn giữ quan hệ lịch sử và lấy đầy đủ branch. Rebase phù hợp hơn khi chỉnh một topic series trước khi tích hợp. Patch artifact phù hợp hơn khi vendor hoặc adobe phát hành fix có compatibility matrix và lifecycle riêng. Một hotfix commerce có thể kết hợp cả hai lớp, vì commit chỉ thêm file patch hoặc cấu hình patch, còn thay đổi vendor code được áp trong build. Mỗi lần selective replay tạo thêm divergence và chi phí vận hành. Cùng một intent có thể có nhiều hash trên production, release và integration, mỗi bản có conflict decision, test result và rollback riêng. Vì vậy cherry pick không phải lối tắt miễn phí. Nó là lựa chọn có chủ đích khi việc lấy toàn nhánh nguy hiểm hơn chi phí duy trì nhiều bản sao. Một senior reviewer sẽ kiểm tra phạm vi commit, dependency, target context, khả năng test và kế hoạch promotion về các nhánh còn lại. Nếu commit chứa refactor, schema, code và cấu hình không thể tách, việc cherry pick một sha có thể tạo trạng thái thiếu. Nếu thay đổi chỉ có ý nghĩa khi đi cùng toàn branch, merge thường trung thực hơn. Giá trị của cherry pick nằm ở sự chọn lọc có bằng chứng, không nằm ở khả năng chạy một lệnh nhanh.

Một backport an toàn bắt đầu bằng preflight chứ không bắt đầu bằng xử lý conflict. Người thực hiện phải xác nhận source sha, parent của source, target branch, target tip và environment thật sự deploy từ target đó. Working tree cần sạch, remote state cần được fetch mới, và source diff phải được đọc như một review độc lập. Dependency không chỉ là commit đứng ngay trước trong log. Nó có thể là schema, config export, composer package, module sequence, test fixture hoặc feature flag đã tồn tại ở source nhưng chưa có ở target. Khi một chuỗi nhiều commit được áp, thứ tự phải giữ trạng thái trung gian có thể validate. Dùng range mà không xem revision list có thể kéo thêm merge commit hoặc housekeeping ngoài scope, nên explicit sha list thường dễ audit hơn trong emergency. Nếu conflict xảy ra, git giữ branch ở commit cuối thành công và chỉ ra commit đang vướng qua trạng thái sequencer. Resolution phải dựa vào intent trong target context. Với php, cần xem contract và dependency injection. Với xml, cần parse và compile. Với composer lock, nên tái tạo từ dependency intent trên target thay vì ghép hai graph. Với declarative schema, cần hiểu fresh install và upgrade path. Một conflict text đã hết marker vẫn có thể là semantic conflict. Ours và theirs chỉ mô tả hai side của operation, không phải bên đúng và bên sai. Sau khi resolve, reviewer cần xem staged diff trước continue, chạy kiểm tra theo artifact và ghi lý do cho từng lựa chọn quan trọng. Skip chỉ hợp lệ khi evidence cho thấy commit đã được thay thế hoặc không thuộc target. Abort phù hợp khi dependency map sai hoặc adaptation vượt phạm vi hotfix. Quit chỉ xóa operation state và giữ thay đổi hiện tại để điều tra, vì vậy không nên dùng nếu người thực hiện chưa hiểu hậu quả. Một empty result cũng cần dừng lại để xác minh. Nó có thể là duplicate patch, implementation khác đã xử lý cùng behavior, commit trước đã bao phủ delta hoặc resolution đã bỏ nhầm toàn bộ thay đổi. Quy trình tốt biến mỗi trạng thái git thành một câu hỏi kỹ thuật thay vì một trở ngại cần bấm qua.

Patch id và git cherry giúp tìm những commit có diff tương đương dù hash khác, nhưng chúng chỉ là công cụ thu hẹp phạm vi điều tra. Patch id được tính từ file diff theo quy tắc bỏ line number và xử lý whitespace, còn stable mode giảm ảnh hưởng của thứ tự file diff. Hai commit có cùng patch id gần như chắc chắn biểu diễn cùng thay đổi văn bản theo thuật toán đó, nhưng runtime vẫn có thể khác vì package, schema, config, extension và data target không giống nhau. Git cherry so các commit trên một branch với upstream và đánh dấu commit đã có patch equivalent bằng dấu trừ, commit chưa tìm thấy equivalent bằng dấu cộng. Dấu trừ không tự nói bản tương ứng nào an toàn, còn dấu cộng không chứng minh target chưa sửa behavior bằng implementation khác. Một quy trình duplicate review nên đi qua ba lớp. Lớp đầu kiểm tra cùng commit identity trong ancestry. Lớp hai kiểm tra patch equivalence bằng patch id, cherry hoặc cherry mark. Lớp ba kiểm tra behavior equivalence bằng source inspection và test. Ví dụ target đã thay một điều kiện checkout bằng configuration provider mới, còn source commit sửa trực tiếp method cũ. Patch id sẽ khác, nhưng hai thay đổi có thể cùng giải quyết carrier visibility. Cherry pick thêm source commit lúc này có thể tạo hai rule chồng nhau. Trường hợp ngược lại, patch id giống nhưng target đang chạy package version có side effect mới, nên cùng diff không đủ. Promotion ledger nên ghi canonical source sha, target result sha, patch id, conflict decision và evidence. Khi merge line sau này, ledger giúp reviewer hiểu vì sao cùng fix xuất hiện dưới hash khác và tránh xóa nhầm. Patch equivalence đặc biệt hữu ích với history đã rebase hoặc backport, nhưng không được dùng như security certification. Một security remediation cần bulletin, applicable version, package set và tests riêng. Công cụ tốt nhất chỉ có giá trị khi câu hỏi được đặt đúng. Patch id trả lời patch có giống không, không trả lời hệ thống đã an toàn chưa.

Hotfix production cần được tạo từ commit thật đang deploy, vì integration mới nhất có thể chứa feature chưa phát hành hoặc schema chưa có trên production. Incident lead trước tiên ghi production sha, deployment activity, symptom và reproduction. Branch hotfix xuất phát từ tip đó, thay đổi được giữ tối thiểu và có test chứng minh invariant cần khôi phục. Sau review và pipeline, fix phải được kiểm tra ở staging hoặc môi trường gần production nhất trước khi promotion cuối. Khi production ổn định, công việc chưa kết thúc. Fix cần được forward promote về integration, release branch và mọi line có thể tái sinh bug. Không nên reverse merge toàn production một cách mù quáng, vì production có thể chứa version marker, emergency revert hoặc commit release specific. Cherry pick commit atomic thường kiểm soát scope tốt hơn, nhưng project có thể dùng ancestry policy yêu cầu merge. Branch topology phải được xác minh theo môi trường thật, không suy từ tên main, master, staging hay production. Mỗi target promotion tạo commit mới và phải có test riêng. Một bảng ledger tối thiểu ghi incident, source sha, source line, target pre pick sha, target result sha, patch id, conflict decision, pipeline, deployment và rollback. Nếu target cần adaptation, reviewer phải biết phần nào giữ nguyên intent và phần nào thay đổi vì api hoặc package version. Đừng đánh dấu hoàn tất chỉ vì tất cả branch có commit message giống nhau. Cần kiểm tra behavior trên từng target. Với adobe commerce cloud, evidence còn gồm build, patch apply, dependency injection compile, static content, migration, cache, indexer, cron, queue và smoke test. Backup trước deployment và deployment marker giúp điều tra nếu metric thay đổi sau hotfix. Một emergency flow có thể rút ngắn thời gian chờ nhưng không bỏ source identity, approver và rollback. Sau sự cố, follow up review cần xác nhận fix đã trở lại main development line, temporary bypass đã đóng và patch debt đã có owner. Nếu production được sửa nhưng integration không nhận fix, release kế tiếp có thể đưa bug quay lại. Promotion vì thế là một vòng đời, không phải một lần push.

Security remediation trên nhiều release line phải bắt đầu từ tài liệu adobe chứ không bắt đầu từ một commit custom đã chạy ở project khác. Bulletin cho biết affected version, fixed version và phạm vi sản phẩm. Nhóm cần xác định line nào còn supported, latest applicable security patch và companion package như b2b. Security patch release dùng hậu tố p và có thể chứa security bug fix, compliance change hoặc security enhancement, nên vẫn cần regression. Isolated security patch là artifact standalone, non cumulative và chỉ được adobe test trên latest security only patch của từng supported line. Điều này có nghĩa một project ở baseline cũ không nên lấy isolated file rồi ép apply. Project phải nâng đúng baseline hoặc theo hướng dẫn chính thức khác. Nếu bulletin không phát hành isolated patch hoặc hotfix, hướng chuẩn là upgrade lên latest applicable patch version của line, không chờ một file riêng sẽ được tạo sau. Hai line cùng bị ảnh hưởng có thể cần hai artifact hoặc implementation khác nhau vì framework, composer dependency và b2b package khác. Cùng intent bảo mật không đồng nghĩa cùng patch bytes. Mỗi line phải có package inventory, applicable matrix, build test, functional regression và security verification riêng. Không ghi exploit detail nhạy cảm trong branch công khai hoặc commit message nếu disclosure policy chưa cho phép. Không dùng patch từ nguồn không tin cậy. Khi fix liên quan credential, code deployment không thay thế rotation hoặc revocation. Audit record nên ghi bulletin, baseline, artifact checksum hoặc identifier, target version, approver, deployment và monitoring. Sau khi security release tiếp theo đã tích hợp isolated fix, nhóm cần xác minh và retire artifact cũ nếu không còn cần. Giữ patch vĩnh viễn làm stack phức tạp và có thể conflict với vendor code mới. Một senior developer sẽ phân biệt urgency với sự hấp tấp. Remediation nhanh là chọn official artifact đúng line, test risk focused và triển khai có evidence. Remediation hấp tấp là dùng một patch thành công trên line khác rồi coi clean apply như bằng chứng an toàn.

Quality patch, cloud patch và custom patch có nguồn, thứ tự và lifecycle khác nhau. Trên adobe commerce cloud, required cloud patches được áp trước, quality patches được chọn áp sau, rồi custom patch trong m2 hotfixes được áp theo thứ tự tên file. Một commit thêm patch id vào cấu hình hoặc thêm file patch chỉ thay đổi inventory trong repository. Fix thật chỉ xuất hiện khi build áp patch thành công, vì vậy review phải nối commit diff với patch status, patch log và runtime test. Quality patches tool phù hợp với fix được adobe hoặc cộng đồng phân phối trong package và có applicable version cùng dependency. Adobe khuyến nghị chỉ dùng patch cần thiết, tránh tích lũy số lượng lớn và ưu tiên upgrade. Custom patch phù hợp khi support hoặc team cung cấp artifact riêng, nhưng filename, order, source, owner và removal condition phải rõ. Vendor upgrade là thời điểm bắt buộc kiểm kê patch. Fix có thể đã được vendor tích hợp, patch có thể không còn apply, hoặc nguy hiểm hơn là vẫn apply nhưng làm thay đổi behavior mới không còn phù hợp. Apply success không chứng minh patch còn cần. Nhóm cần so vendor source, release notes, issue invariant, quality patch replacement và test. Nếu fix đã được tích hợp, remove patch là một change cần deploy và regression, vì patch cũ có thể đã che conflict khác. Nếu issue còn nhưng source target đổi, adaptation phải được tạo cho version mới và review lại, không chỉ sửa context cho lệnh xanh. Với m2 hotfixes, remove file rồi commit và deploy là cách gỡ custom patch trên cloud, nhưng thao tác đó không tự phục hồi schema hoặc data side effect ngoài vendor source. Patch inventory nên được promotion theo release line. Một file chạy trên line cũ không mặc định tương thích line mới. Prefix tên giúp order rõ nhưng dependency phải được ghi bằng tài liệu và test. Patch log, package lock, exact commerce version và b2b version là bằng chứng bắt buộc khi debug. Mục tiêu dài hạn là giảm patch debt bằng upgrade, không biến patch stack thành một fork ẩn khó bảo trì.

Emergency change cần đường thực thi nhanh nhưng vẫn phải giữ accountability. Protected branch bình thường nên chặn direct push rõ ràng và yêu cầu merge request. Một số nền tảng hoặc security policy cho phép designated exception với reason và audit event, nhưng tính năng phụ thuộc tier, version và configuration. Nhóm không nên mở direct push vĩnh viễn chỉ để chuẩn bị cho một sự cố hiếm. Khi bypass thật sự cần, người thực hiện và người chấp nhận risk nên tách nhau khi có thể. Record phải có incident, latest sha, reason, source fix, tests tối thiểu, approver, deployment activity và follow up action. Pipeline phải thuộc commit hiện tại, không dùng kết quả của tip cũ. Deployment evidence cần nối repository với môi trường. Trên adobe commerce cloud, một commit đã merge không chứng minh build, patch apply hoặc deploy thành công. Activity id, build log, patch log, smoke test và new relic deployment marker giúp tạo chuỗi chứng cứ. Metric sau deploy như error rate, response time, queue backlog và checkout success phải được theo dõi trong window phù hợp. Nếu policy bypass tạo audit event, event đó cần được liên kết với incident. Nếu tool không hỗ trợ, tổ chức vẫn phải tạo record tương đương bằng change ticket và follow up merge request. Emergency review không chỉ hỏi fix có hoạt động không. Nó còn hỏi scope có tối thiểu không, có secret trong diff không, rollback có khả thi không, branch nào chưa nhận fix và temporary permission nào cần thu hồi. Một post incident review nên kiểm tra vì sao bug lọt qua, vì sao normal path không đủ nhanh và control nào cần cải thiện. Bypass có quản trị là một exception với owner và closure. Bypass không kiểm soát là một khoảng trống nơi không ai biết ai đã đổi gì hoặc evidence nào còn đại diện. Tốc độ và audit không đối lập nếu workflow đã được thiết kế trước sự cố.

Rollback sau multi branch promotion phải dựa trên target specific state. Mỗi cherry pick tạo commit riêng, nên source sha không phải hash để revert trên mọi branch. Release manager cần ledger ánh xạ source intent với từng target result sha. Nếu fix chỉ thay code và chưa tạo side effect ngoài repository, revert commit đích rồi redeploy thường an toàn hơn reset protected branch. Nếu fix được quản lý bằng custom patch file, remove file, commit và deploy có thể gỡ patch khỏi vendor source. Tuy nhiên rollback thực tế còn phải xem schema, data, config, cache, generated artifact, queue và external integration. Một code revert không hoàn tác order đã gửi sang erp, email đã phát hoặc payment đã capture. Data patch đã chạy cũng không tự đảo chỉ vì commit bị revert. Trước emergency deployment, plan cần mô tả state nào có thể reverse, state nào cần compensation và data loss window nào được chấp nhận. Khi regression xuất hiện, đừng vội revert toàn bộ source line nếu chỉ một target adaptation sai. Xác định environment, result sha, deployment activity và metric bắt đầu thay đổi. Revert đúng target, chạy pipeline và smoke test, rồi đánh giá các line khác có cùng failure mode hay không. Nếu patch removal làm build xanh nhưng storefront vẫn lỗi, kiểm tra cache, generated code, database compatibility và patch log. Sau rollback, ledger phải ghi revert sha, deployment result và quyết định giữ hay sửa canonical fix. Một senior workflow còn xem xét forward path. Có thể rollback production nhưng tiếp tục sửa trên integration, hoặc retire custom patch vì vendor release đã thay thế. Mục tiêu không phải đưa git về một hash cũ bằng mọi giá. Mục tiêu là khôi phục invariant hệ thống với audit rõ và không làm mất thay đổi hợp lệ khác. Khi branch, code và runtime state được tách đúng, nhóm có thể rollback có chọn lọc. Khi tất cả bị coi là một thứ, emergency dễ chuyển từ bug ban đầu thành sự cố dữ liệu và lịch sử.
