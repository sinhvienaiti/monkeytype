Khi một hệ thống thương mại điện tử dùng php fpm, việc chọn process manager không nên bắt đầu bằng câu hỏi mode nào nhanh nhất. Câu hỏi đúng là traffic đến theo nhịp nào, child process mất bao lâu để sẵn sàng, mỗi worker giữ bao nhiêu memory, và node cần giữ bao nhiêu capacity khi không có request. Static tạo một số child cố định bằng max children, nên latency ổn định hơn trong steady state nhưng baseline memory cao. Dynamic giữ một nhóm worker khởi đầu, tạo thêm khi số idle giảm và thu hồi khi số idle vượt ngưỡng. Ondemand chỉ tạo child khi có request rồi dừng child đã idle đủ lâu, vì vậy tiết kiệm memory cho endpoint ít dùng nhưng có thể tạo cold start trong burst. Một senior không chọn mode bằng thói quen của distribution. Họ quan sát request rate, burst width, spawn time, warm up cost và memory pressure. Storefront có traffic liên tục thường cần capacity nóng. Internal tool chỉ được gọi vài lần mỗi ngày có thể phù hợp với ondemand. Admin có workload ít đều nhưng mỗi request nặng có thể cần pool riêng để không tranh child với storefront. Tách pool tạo isolation về socket, user, log và configuration, nhưng không tạo thêm cpu hay database capacity. Nếu tổng max children của nhiều pool vượt memory budget, node vẫn có thể bị out of memory. Nếu nhiều pool cùng gọi database, tổng connection còn có thể vượt khả năng downstream. Vì vậy process manager chỉ là policy tạo worker, không phải lời giải hoàn chỉnh cho capacity. Thay đổi mode phải đi cùng load test đại diện, đo thời gian spawn, theo dõi listen queue và xác nhận memory sau spike. Sau khi deploy, team cần so sánh latency đầu tiên với steady state, xem child có được thu hồi đúng và bảo đảm health check không làm hệ thống trông ấm hơn traffic thật. Một cấu hình tốt là cấu hình giải thích được bằng evidence, có headroom và có rollback, chứ không phải cấu hình có nhiều worker nhất.

Max children là giới hạn số request đồng thời mà một pool có thể phục vụ, nhưng nó không phải throughput guarantee. Một child xử lý request cache hit trong thời gian rất ngắn khác hoàn toàn một child chờ database lock hoặc external api trong nhiều giây. Khi tất cả child bận, request mới có thể nằm trong listen queue. Queue giúp hấp thụ burst ngắn nhưng không tạo thêm năng lực xử lý. Nếu service time tăng, cùng request rate sẽ cần nhiều concurrency hơn, pool chạm trần, queue tăng, client timeout rồi retry, và retry lại làm load lớn hơn. Để đánh giá đúng, team cần nhìn active process, idle process, total process, listen queue, max listen queue, max children reached, request rate và latency percentile trên cùng timeline. Counter max children reached chỉ cho biết pool từng chạm trần kể từ lần khởi động, không cho biết hiện tại có khủng hoảng hay không. Nếu counter tăng một lần trong deploy warm up nhưng queue không tăng và latency không đổi, tăng worker có thể không cần thiết. Nếu active luôn bằng total, idle bằng không, queue tăng và nhiều route cùng chậm, saturation đã rõ hơn. Trước khi tăng max children, phải kiểm tra node còn memory headroom hay không, cpu có bão hòa không, và database hoặc redis có chịu được concurrency mới không. Tăng php worker khi database đang lock có thể tạo thêm connection cùng chờ và kéo sự cố sâu hơn. Công thức lấy memory budget chia cho memory mỗi worker chỉ là ceiling sơ bộ. Memory mỗi worker nên lấy từ workload đại diện và percentile bảo thủ, không chỉ average rss. Host còn cần memory cho operating system, page cache, nginx, agent, opcache, cron và consumer. Trong container, cgroup limit mới là boundary đáng tin hơn tổng ram vật lý. Quyết định cuối phải kết hợp memory ceiling, cpu throughput, dependency capacity và mục tiêu latency. Nếu không có đủ evidence, hành động an toàn hơn là giảm retry, rate limit endpoint đắt hoặc sửa dependency chậm trước khi mở rộng concurrency.

Memory của php fpm cần được tách thành nhiều lớp để tránh kết luận sai. Memory limit là giới hạn allocation mà php theo dõi cho một script, không phải reservation và không bảo đảm resident memory của child luôn thấp hơn đúng con số đó. Native extension, allocator overhead, shared library và một số vùng ngoài accounting có thể làm rss khác. Opcache lại dùng shared memory cho bytecode và interned strings, nên nhiều child có thể dùng chung một phần memory. Ngược lại, object graph của request, hydrated entity, query result, image buffer và temporary data thường làm private memory tăng. Cộng rss của mọi worker như thể tất cả page đều private sẽ phóng đại usage, nhưng cho rằng phần lớn đều shared cũng có thể làm capacity plan quá lạc quan. Khi có quyền, team nên đọc proportional memory hoặc smaps rollup và theo dõi theo pid, tuổi process, release id và workload gần nhất. Một worker vừa chạy export lớn có thể giữ allocator arena cao dù request đã kết thúc. Điều đó chưa đủ để gọi là leak. Leak đáng tin hơn khi memory tăng theo request count với cùng workload, không tạo plateau, và pattern lặp lại sau mỗi lần recycle. Max requests có thể giới hạn lifetime của worker để giảm blast radius của leak hoặc fragmentation. Tuy nhiên giá trị quá thấp gây spawn churn, opcache warm up lặp lại và latency dao động. Giá trị quá cao để worker lỗi tăng memory quá lâu. Vì vậy recycle là mitigation có evidence, không phải permanent fix. Team cần profile code hoặc extension tạo growth, sửa root cause rồi đánh giá lại policy. Một lỗi thường gặp khác là lấy memory limit một gigabyte rồi nhân với max children và cho rằng đó là usage thật. Phép nhân này chỉ mô tả worst case cực đoan, nhưng cũng cảnh báo rằng nhiều request nặng cùng lúc có thể làm node hết memory trước khi từng script chạm fatal riêng. Capacity plan tốt phải giữ emergency headroom, tính background workload và kiểm tra event out of memory của cgroup hoặc kernel thay vì chỉ nhìn dashboard memory trung bình.

Slow request không đồng nghĩa pool bị bão hòa. Một admin export chạy ba mươi giây có thể giữ một child, trong khi ba mươi child khác vẫn idle và storefront hoạt động bình thường. Ngược lại, nhiều request chỉ chậm năm giây nhưng cùng chờ một database lock có thể chiếm toàn bộ pool và tạo queue. Slowlog giúp lấy php backtrace khi request vượt ngưỡng slowlog. Backtrace cho biết child đang ở frame nào tại thời điểm sample, nhưng không chứng minh toàn bộ thời gian được dùng ở frame đó. Cần ghép slowlog với fpm access log, nginx upstream timing, application trace và dependency span bằng cùng request id và timestamp. Request terminate timeout là một safety boundary khác. Khi vượt ngưỡng, fpm có thể terminate worker, nhưng điều này không đảm bảo business transaction được rollback sạch. Một order có thể đã gọi payment hoặc ghi database trước khi worker bị cắt. Vì vậy dependency timeout và application deadline phải được thiết kế trước, còn terminate timeout là last resort. Fastcgi finish request cũng dễ gây hiểu nhầm. Response có thể đã được gửi cho client, nhưng php code vẫn tiếp tục làm shutdown work trong child. Nếu nhiều request gửi email, export hoặc đồng bộ dài sau response, user thấy nhanh nhưng pool vẫn mất capacity. Công việc dài nên chuyển sang queue có retry, idempotency và observability. Khi điều tra, hãy tách queue time khỏi execution time. Nếu request mất mười giây trước khi child nhận, tối ưu code php không giải quyết phần chờ. Nếu queue bằng không nhưng một route có trace dài, tập trung vào query, payload hoặc external service. Nếu queue tăng, idle bằng không và nhiều route cùng chậm, xử lý saturation và nguyên nhân chung. Slowlog path, permission và retention cũng phải được kiểm tra, vì log không xuất hiện có thể do configuration sai chứ không phải hệ thống không có request chậm. Log còn có thể chứa url, path và identifier, nên endpoint status cùng slowlog phải được bảo vệ và redaction phù hợp.

Opcache cải thiện hiệu năng bằng cách lưu bytecode đã compile trong shared memory, nhờ đó php không phải đọc, parse và compile cùng source cho mọi request. Nó không thay thế full page cache, redis, database optimization hoặc generated code. Khi đánh giá opcache, team không nên chỉ nhìn hit rate. Cần đọc used memory, free memory, wasted memory, cache full, số script đã cache, key capacity, interned strings và các counter restart. Main memory đầy có thể tạo miss hoặc restart theo policy. Interned strings có buffer riêng, nên buffer này gần đầy không nhất thiết được giải quyết đúng chỉ bằng tăng một metric khác. Max accelerated files phải đủ cho codebase và extension thực tế. Nếu hash capacity quá thấp, hash restart có thể tăng. Hit rate cao vẫn có thể đi cùng site chậm vì request đang chờ database hoặc external service. Sau restart hoặc deploy, miss tăng trong warm up có thể bình thường. Alert cần correlate với thời điểm release và traffic. Adobe đưa ra một số ví dụ setting cho commerce, nhưng con số phải được đọc đúng phạm vi. Hướng dẫn hai gigabyte được ghi cho kiến trúc cloud pro phiên bản cũ cụ thể, không phải chuẩn bắt buộc cho mọi dự án hiện tại. Sizing đúng dựa trên status của release thật, số file, extension, free và wasted memory, cùng headroom của node. Opcache save comments cũng cần giữ theo yêu cầu của commerce, vì framework và extension có thể phụ thuộc metadata trong comment. Một lỗi vận hành phổ biến là tăng opcache rất lớn trong khi fpm child đã thiếu memory, làm tổng node pressure nặng hơn. Shared cache vẫn là memory thật. Dashboard tốt nên đặt opcache cạnh worker private memory và cgroup limit. Khi có oom restart, hash restart hoặc manual restart, team phải gắn chúng với deploy, configuration change và process start time. Counter có thể reset khi runtime restart, nên monitoring cần lưu history bên ngoài thay vì chỉ đọc snapshot hiện tại.

Invalidation là phần khó nhất của opcache trong deployment. Khi validate timestamps được bật, runtime có thể kiểm tra file thay đổi theo revalidate policy, thuận tiện hơn cho development nhưng tạo filesystem work. Khi validate timestamps bị tắt để tối ưu production, việc ghi file mới lên disk không tự bảo đảm worker dùng code mới. Release process phải tạo worker generation mới hoặc thực hiện invalidation trong đúng context. Gọi opcache reset từ command line không phải bằng chứng cache của fpm đã được reset, vì cli và fpm có thể dùng cache instance khác. Endpoint công khai gọi reset còn tạo rủi ro bảo mật và cold miss đồng loạt. Mô hình an toàn hơn là build release bất biến, cài đúng vendor từ lock file, compile dependency injection, tạo generated code, kiểm tra artifact, chuyển release, khởi động hoặc reload worker mới, chạy health check rồi drain worker cũ. Atomic symlink chỉ giải quyết tên đường dẫn tại filesystem. Process cũ có thể đã resolve realpath, load class, giữ file descriptor hoặc cache bytecode. Vì vậy symlink switch không thay thế worker lifecycle. Generated code phải khớp source, module list, php version và configuration. Xóa hoặc tái tạo một phần generated trong khi traffic đang chạy có thể làm old bytecode gọi new class contract hoặc gặp file missing. Mỗi response nội bộ nên có release marker để phát hiện node hoặc pool lệch version. Khi một số request trả code cũ ngẫu nhiên, team cần kiểm tra load balancer, node, pool, worker start time, opcache policy, realpath cache, preload và drain state. Clear cache chung không giải thích layer nào đã thay đổi. Rollback cũng phải phục hồi coherent release, không chỉ đổi source. Vendor, generated code, configuration, process generation và database compatibility phải cùng nằm trong kế hoạch. Mục tiêu cuối là mỗi request chạy trên một tập artifact nhất quán từ đầu tới cuối.

Preloading đưa function và class vào persistent memory khi php runtime khởi động. Lợi ích tiềm năng là giảm work trong request, nhưng đổi lại baseline memory cao hơn và release coupling mạnh hơn. Symbol đã preload không thể được thay riêng lẻ như một file vừa sửa trong development. Khi release thay đổi class preload, process generation mới thường cần được khởi động. Preload script còn phải load dependency đúng thứ tự. Tự liệt kê toàn bộ codebase dễ gặp class condition, generated file, side effect hoặc module chỉ tồn tại ở một environment. Vì vậy preloading phải được coi là release artifact có version, test và rollback, không phải một dòng tuning bật sau cùng. Một quy trình tốt tạo preload list từ đúng source và vendor của release, kiểm tra syntax và dependency trong build, khởi động worker mới bằng release đó, thực hiện functional health check rồi drain generation cũ. Nếu worker cũ vẫn giữ preload từ release trước trong khi shared mutable directory đã đổi, mixed state có thể xảy ra. Preloading cũng không thay thế composer autoload optimization hay dependency injection compilation. Mỗi cơ chế giải quyết một bước khác. Trước khi bật, team nên đo startup cost, memory tăng, request latency và operational complexity. Nếu lợi ích nhỏ nhưng restart và rollback trở nên khó, không preload có thể là quyết định tốt hơn. Cần tránh benchmark chỉ chạy một endpoint đơn giản trên một node. Commerce có nhiều route, module và extension, nên preload file phù hợp phải đại diện cho production. Status và health endpoint cũng phải xác nhận release id, không chỉ trả ok từ web server. Nếu preloading gây startup fatal, fpm listener có thể không có child khỏe dù configuration syntax hợp lệ. Log master và child startup là evidence quan trọng. Một senior sẽ yêu cầu canary, rollback trigger và maximum drain time. Họ cũng kiểm tra memory headroom vì persistent symbols lấy memory trước khi request workload bắt đầu. Optimization chỉ có giá trị khi không phá tính nhất quán và khả năng phục hồi của deployment.

Trong incident, trưởng nhóm cần chống lại hai phản xạ là tăng max children ngay hoặc đổ lỗi cho một slow trace duy nhất. Trước tiên hãy dựng timeline chung gồm request rate, latency percentile, error rate, active và idle child, listen queue, max children reached, cpu, memory, out of memory event và dependency latency. Nếu queue bằng không, idle còn nhiều và chỉ một route chậm, hãy điều tra route đó. Nếu queue tăng, idle bằng không và nhiều route chậm, pool đang saturation, nhưng vẫn phải tìm lý do worker bị giữ. Slowlog có thể cho thấy nhiều pid cùng chờ database lock, redis timeout hoặc external service. Mitigation khẩn cấp nên giảm positive feedback loop bằng cách hạ retry, rate limit endpoint đắt, tắt feature lỗi, rút ngắn dependency timeout hoặc phục vụ cache phù hợp. Scale chỉ nên thực hiện khi memory, cpu và downstream còn capacity. Mọi thay đổi cần có expected signal và rollback trigger. Sau khi ổn định, team phải tạo permanent fix, load test representative mix và cập nhật capacity model. Báo cáo incident cần phân biệt symptom, contributing factor và root cause. Pool saturation là symptom capacity. Database lock có thể là root cause. Retry storm có thể là amplifier. Thiếu alert queue có thể là detection gap. Một cấu hình mới chỉ được coi là thành công khi queue, tail latency, error và resource headroom tốt hơn qua traffic tương đương, không phải vì service restart xóa counter. Cuối cùng, hãy ghi lại release id, configuration diff, fpm start time và opcache restart counter để sự cố sau có baseline. Vận hành giỏi không phải thuộc nhiều directive, mà là biết mỗi metric trả lời câu hỏi nào, giới hạn của nó ở đâu và evidence nào có thể bác bỏ giả thuyết hiện tại.
