Adobe Commerce được thiết kế để developer mở rộng hoặc thay thế hành vi bằng module và extension point, thay vì sửa trực tiếp core hoặc package bên thứ ba. Khi project chỉnh một file trong vendor, Composer và hệ thống version vẫn cho rằng package là bản chính thức, dù behavior runtime đã khác. Thay đổi có thể biến mất sau install, bị ghi đè khi update hoặc bỏ lỡ security fix mới. Nó cũng khó xuất hiện trong pull request và khó revert có kiểm soát. Câu hỏi đầu tiên trước một customization không phải là override class nào, mà là ai sở hữu code và contract nào được phép mở rộng. Code do project sở hữu có thể refactor trực tiếp kèm test. Code upstream có extension point nên dùng extension point. Code upstream không có hook cần đánh giá adapter, patch tạm thời hoặc upstream contribution. Quy trình lựa chọn nên bắt đầu bằng requirement và phạm vi chính xác. Sau đó kiểm tra configuration, dependency injection argument, strategy pool, service contract, layout hoặc ui configuration. Nếu framework đã expose một danh sách strategy qua cấu hình, viết plugin để đổi cùng dữ liệu chỉ tạo coupling không cần thiết. Tiếp theo mới xem event, public method cho plugin, decorator hoặc preference.

Patch nằm gần cuối vì nó thay trực tiếp code không thuộc project. Thứ tự này không phải luật cứng, nhưng giúp team tránh nhảy ngay vào preference hoặc copy cả class. Cơ chế tốt nhất thường là cơ chế có blast radius nhỏ nhất, dùng contract ổn định nhất và dễ gỡ bỏ nhất khi upstream thay đổi. Composition phù hợp khi upstream phụ thuộc một interface rõ ràng. Project có thể cung cấp implementation mới hoặc decorator giữ behavior gốc rồi bổ sung policy. Ví dụ một dịch vụ kiểm tra bảo hành có thể được bọc bởi policy loại trừ sản phẩm đang bị thu hồi. Decorator chỉ xử lý rule mới và gọi service gốc cho phần còn lại. Cách này dễ unit test và không cần copy logic. Khi có nhiều policy, strategy pool hoặc composite giúp tách trách nhiệm thay vì tạo một class lớn chứa nhiều condition. Configuration quyết định danh sách và thứ tự strategy. Đây là thiết kế có thể thay thế, phù hợp với nguyên tắc dependency inversion và thường ít conflict hơn can thiệp trực tiếp execution flow. Plugin phù hợp khi cần thay đổi behavior của public method mà không thay toàn bộ class. Before plugin có thể normalize argument.

After plugin điều chỉnh result khi method gốc vẫn cần chạy. Around plugin chỉ nên dùng khi thật sự cần quyết định có gọi method gốc hay không hoặc bao quanh flow. Around làm chain và stack trace phức tạp hơn, đồng thời có thể cắt plugin phía sau nếu không gọi proceed. Khi review plugin, cần xem target có phải business boundary phù hợp không, signature có ổn định không, area có quá rộng không và method có nằm trên hot path không. Plugin một utility method được gọi rất thường xuyên có thể ảnh hưởng performance toàn site. Observer phù hợp khi module cần phản ứng với business event và publisher không cần biết subscriber. Observer nên nhỏ, gọi service riêng, không phụ thuộc thứ tự chạy và được khai báo đúng area. Nó không phù hợp nếu requirement cần sửa trực tiếp return value hoặc argument của một method. Nghe một event quá chung chỉ vì không tìm thấy hook chính xác có thể làm logic chạy ở nhiều flow ngoài dự kiến. Nếu business rule bắt buộc cho mọi entry point, rule nên nằm trong service layer dùng chung. Observer có thể thực hiện side effect như audit hoặc notification sau khi state phù hợp đã được tạo.

Preference thay implementation mà object manager sử dụng cho một interface hoặc class. Nó phù hợp khi cần cung cấp implementation hoàn chỉnh cho contract và không có decorator hoặc strategy hook tốt hơn. Rủi ro lớn là chỉ một preference cuối cùng thắng cho cùng type trong một area. Hai module cùng preference sẽ conflict theo merge order. Copy class upstream rồi preference vào custom class còn tạo maintenance burden vì constructor, private state và public behavior có thể đổi sau upgrade. Interface preference thường rõ dependency inversion hơn concrete class preference. Preference không nên được dùng chỉ vì developer chưa quen plugin. Inheritance chỉ an toàn khi class được thiết kế để extend. Protected extension method rõ ràng, dependency dựa trên abstraction và contract ổn định là dấu hiệu tốt. Private property dày đặc, private helper, constructor thay đổi thường xuyên và class không thuộc public api là dấu hiệu xấu. Copy toàn bộ class để sửa một condition là một fork ẩn. Team phải tự merge mọi bug fix và security fix upstream về sau. Nếu tạm thời buộc phải copy, cần ghi upstream version, giữ diff nhỏ, thêm regression test và tạo kế hoạch loại bỏ. Namespace khác không làm mất trách nhiệm maintain fork.

Patch là file mô tả thay đổi vào code upstream và được áp lại trong build. Patch có thể hợp lý khi có bug rõ, không có extension point, fix nhỏ và cần giải pháp trước release chính thức. Nó không phù hợp để xây business feature lớn hoặc thay đổi sâu nhiều file. Mỗi patch cần package và version scope, nguồn gốc, owner, test, lý do tồn tại và điều kiện remove. Khi upstream đã sửa, patch cũ có thể conflict hoặc đảo ngược behavior mới. Patch được commit trong project không có nghĩa code mục tiêu trở thành project owned. Upgrade vẫn cần review patch context và necessity. Không phải public method PHP nào cũng là public api ổn định. Service contract, interface trong namespace api và extension point được tài liệu hóa thường có cam kết tốt hơn. Customization phụ thuộc reflection, private property, internal SQL hoặc thứ tự call không được contract hóa có rủi ro cao. Nếu buộc phải phụ thuộc implementation nội bộ, Composer constraint và test phải phản ánh mức coupling đó. Khi package update, cần kiểm tra target method còn tồn tại, signature có đổi, plugin chain có khác và behavior gốc mới có làm customization dư thừa không.

Area scope giúp giảm blast radius. Một plugin chỉ phục vụ storefront không nhất thiết chạy trong admin, cron hoặc consumer. Tuy nhiên business invariant quan trọng không được đặt ở area quá hẹp làm REST hoặc GraphQL bỏ qua rule. Presentation behavior có thể scope theo frontend. Business service dùng chung nên bảo vệ invariant cho mọi entry point. Khi debug conflict, cần xác định class runtime thật, preference cuối, plugin chain, sort order, observer và patch đã áp. Debug trên vendor directory bị sửa thủ công không tạo kết quả đáng tin cậy. Hãy tái hiện từ lock file sạch và pipeline chuẩn. Third party module cần được xem như một upstream package có lifecycle riêng. Trước khi override, hãy đọc tài liệu, release note, support policy, public hook và compatibility matrix. Một lỗi tưởng phải patch có thể đã có configuration hoặc extension point. Nếu là bug chung, gửi reproduction và test case cho vendor giúp giảm workaround dài hạn. Pin version có thể cần thiết khi customization phụ thuộc behavior nội bộ, nhưng pin mãi không thay thế upgrade plan. Module vendor thường thay contract nhanh hơn public service contract của Adobe, vì vậy regression test càng quan trọng. Một customization tốt phải có exit strategy.

Lưu requirement gốc, package bị ảnh hưởng, extension mechanism, upstream issue, regression test, owner và điều kiện remove. Feature flag có thể giúp tắt behavior nhưng không thay cleanup plan. Trong mỗi upgrade, team cần inventory mọi plugin, preference, copied class và patch. Xác nhận customization còn cần không, extension point có thay đổi không và upstream đã cung cấp fix chưa. Những thay đổi có giá trị chung nên được đề xuất upstream. Khi fix được maintain trong package chính, project giảm đáng kể chi phí merge và rủi ro security. Best practice là không sửa trực tiếp core hoặc vendor, ưu tiên configuration và composition, dùng plugin ở public business boundary, giữ observer nhỏ và đúng area, hạn chế preference rộng, tránh copy class và coi patch là giải pháp có lifecycle. Mọi customization cần test, owner và upgrade review. Anti pattern gồm sửa file production, commit vendor để giữ một thay đổi, reflection vào private method, around plugin không gọi proceed, observer global không cần thiết và giữ patch sau khi upstream đã fix. Mục tiêu không phải tránh mọi customization, mà là thay đổi behavior theo cách có phạm vi rõ, tương thích module khác và có thể gỡ bỏ.
