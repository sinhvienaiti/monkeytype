Layout trong Adobe Commerce mô tả cách các phần của trang được tổ chức và render. Nó không phải css và cũng không phải business logic. Layout quyết định page dùng wireframe nào, container nào chứa block nào, block dùng class và template gì, element đứng trước hay sau sibling nào. Css quyết định hình thức, còn template tạo markup của block. Một request storefront đi qua route và controller, result page thu thập layout handles, framework tìm file từ module và theme, merge instruction, tạo blocks và containers rồi render html. Vì một trang nhận contribution từ nhiều module và theme, nhìn một file không đủ để hiểu output cuối. Backend developer cần hiểu cơ chế này vì module thường cung cấp block, view model, configuration và cache behavior. Một dòng xml đặt sai trong default layout có thể tạo object trên mọi page hoặc làm toàn storefront mất full page cache. Tư duy đúng là xác định scope, ownership và dependency trước khi thêm block. Ví dụ section chứng nhận sản phẩm chỉ thuộc product page thì nên dùng product handle, không đặt global chỉ vì dễ nhìn thấy.

Adobe phân biệt page layout, page configuration và generic layout. Page layout tạo wireframe như một cột hoặc hai cột và chủ yếu chứa containers. Page configuration chọn wireframe, định nghĩa head metadata, blocks, containers và nội dung chi tiết của page. Generic layout mô tả fragment hoặc response đặc biệt như html snippet. Chọn sai loại file làm structure khó bảo trì. Layout handle là tên của một tập instruction. Page type handle thường tương ứng full action name. Specific handle áp dụng cho entity hoặc page cụ thể. Arbitrary handle được handle khác include để tái sử dụng instruction. Một product page có thể nhận default handle, action handle, product type handle, entity handle và handle do extension thêm. Vì vậy block bị mất có thể do một handle khác move hoặc remove parent. Developer nên truy ngược toàn bộ handle chain thay vì chỉ sửa file có tên giống url. Handle cũng là contract nội bộ. Đổi inheritance hoặc name lõi có thể làm extension khác không còn được include. Specific handle cũng hữu ích khi một cms page hoặc một product cần presentation riêng, nhưng lạm dụng file theo từng entity làm theme khó quản lý. Nên ưu tiên rule ổn định và chỉ dùng specific handle cho ngoại lệ có owner rõ.

Functional layout nên nằm trong module khi chức năng phải hoạt động với nhiều theme. Module chứng nhận có thể cung cấp block, view model, template mặc định và layout thêm section vào product page. Theme quyết định presentation cụ thể như di chuyển section vào sidebar hoặc đổi page layout. Không sửa file trong vendor hoặc theme lõi vì composer update ghi đè và Git không quản lý rõ customization. Theme inheritance cho phép theme con chỉ chứa delta. Copy toàn bộ file từ parent làm future update bị che và upgrade khó. Merge order gồm contribution từ modules theo component order, extending files từ theme ancestors, override tương ứng và delta của current theme. Không nên hiểu đơn giản là dòng cuối luôn thắng, vì operation có semantics khác nhau. Module có thể thêm child, theme move child và extension khác remove destination. Kết quả phụ thuộc graph instruction. Override thay file source, còn extend merge thêm delta. Vì vậy extend là lựa chọn mặc định và override chỉ dùng khi cơ chế merge không thể cancel action, argument hoặc handle inclusion cần thay.

Block và container có vai trò khác nhau. Block là view element có php class, có thể nhận dependency, dùng template và render content. Container tổ chức structure, chứa children và có thể wrap chúng bằng html tag hoặc class, nhưng không có block class để tạo business output. Name định danh element trong generated page và cần unique. Alias chỉ có ý nghĩa trong scope parent, thường được parent template dùng để lấy child. Đổi name hoặc alias lõi có thể làm reference, move và child rendering của module khác hỏng. Khi thêm block, cần chọn parent tồn tại trên mọi theme target. Một container có ở Luma chưa chắc có ở custom theme. Block không nên trở thành service locator. Dependency được inject vào block hoặc view model, template không gọi Object Manager, repository hoặc resource model. Constructor cũng không nên thực hiện query nặng vì block có thể được tạo ngay cả khi không render theo cách developer tưởng. Container không render gì nếu không có child, nên việc thêm wrapper rỗng chưa tạo output. Khi parent template lấy child theo alias, di chuyển block sang parent khác cần kiểm tra alias mới và thứ tự render của parent đó.

Reference block và reference container cập nhật element đã tồn tại. Reference không phải cách đáng tin để tạo target khi name sai hoặc target không có trên handle hiện tại. Cần dùng đúng reference theo loại element. Có thể đổi argument, template, remove hoặc display trên target. Argument name phải được block hoặc template dùng, nếu không chỉ tạo data vô nghĩa. Remove và display thường bị nhầm. Remove loại element khỏi layout; remove container kéo theo children. Display false tắt render nhưng Adobe nêu php classes vẫn được load và object vẫn có thể được thao tác. Vì vậy display false không chắc giảm cost của block nặng. Dùng remove khi element không cần tồn tại, dùng display khi muốn tạm ẩn nhưng giữ structure. Node remove trong phần head là cơ chế khác để gỡ static resource, không dùng để xóa block. Debug phải phân biệt hai loại instruction thay vì search từ remove rồi kết luận chung. Nếu block bị module khác remove rồi một theme cố display lại, kết quả còn phụ thuộc merge instruction. Review cần tìm cả giá trị remove true và remove false, không chỉ declaration đầu tiên của element.

Move đổi parent và vị trí của element. Element và destination phải tồn tại trong merged layout. Sau move, alias context có thể thay đổi vì alias thuộc parent. Nếu destination bị remove bởi instruction khác, element được move vào đó cũng biến mất. Move không sửa data. Nếu block hiển thị sai giá hoặc sai scope, di chuyển nó chỉ che triệu chứng. Before và after sắp xếp siblings trong cùng parent. Chúng không tự chuyển element sang parent của target. Target không tồn tại có thể làm element rơi vào vị trí mặc định. Dấu gạch ngang dùng để đưa element về đầu hoặc cuối, nhưng nhiều element cùng yêu cầu vị trí tuyệt đối làm order khó dự đoán. Nên anchor theo sibling ổn định và test mọi theme. Layout order là dom order, ảnh hưởng accessibility, seo và keyboard navigation. Không nên đảo visual order bằng css nếu semantics của dom vẫn sai. Khi page thay đổi theo config, sibling anchor có thể biến mất, nên test cả feature bật và tắt. Khi nhiều extension cùng move một element, contribution load sau có thể quyết định destination cuối. Đây là lý do module nên tránh move element lõi nếu không sở hữu presentation và theme nên chịu trách nhiệm về vị trí cuối cùng.

Arguments truyền string, boolean, object, array hoặc type khác vào block. View model là lựa chọn tốt để cung cấp presentation data cho template mà không làm block phình lớn. View model nên stateless hoặc an toàn trong request. Adobe mô tả object argument được shared mặc định; shared false chỉ dùng khi thực sự cần instance riêng, không dùng để che mutable state. Render flow có thể chạy lại và không có transaction semantics phù hợp. Nếu base layout gọi method không thể cancel bằng extending file, override có thể được cân nhắc, nhưng cần ghi rõ lý do và review khi upgrade. Argument object còn tạo dependency thông qua Object Manager, nên class phải thuộc module enable và constructor không có vòng phụ thuộc. Một typo trong class name có thể chỉ xuất hiện khi page handle được render, không phải lúc compile mọi flow.
