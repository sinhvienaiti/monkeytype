Message queue trong Adobe Commerce tách publisher và consumer theo thời gian. Publisher đưa message vào transport rồi kết thúc phần việc của mình, còn consumer xử lý sau. Điều này hữu ích với carrier sync, erp integration, email, document processing và bulk operation. Tuy nhiên, request publish thành công chỉ chứng minh message được chấp nhận, không chứng minh business đã hoàn thành. Queue có thể đang backlog, consumer có thể dừng hoặc handler có thể fail. Vì vậy api và ui phải phân biệt accepted với completed. Queue phù hợp khi business chấp nhận eventual consistency và operation có thể retry độc lập. Nếu caller cần kết quả tức thời để quyết định transaction, synchronous service có thể đúng hơn. Queue không làm tổng thời gian luôn nhanh hơn, nó chuyển latency ra khỏi request chính. Thiết kế tốt cần trạng thái operation, monitoring và cách người dùng biết kết quả cuối. Khi học message queue, không chỉ nhớ bốn file xml mà phải hiểu toàn bộ lifecycle từ publish, route, store, consume, side effect tới acknowledge. Điểm mấu chốt là trạng thái bất đồng bộ phải trở thành một phần rõ ràng của thiết kế nghiệp vụ.

Luồng tổng thể gồm publisher, topic, exchange, binding, queue, consumer và handler. Topic là tên contract mà publisher gửi, chẳng hạn shipment tracking sync. Exchange nhận message và dùng binding để route. Binding nối topic pattern với destination queue. Queue giữ message cho tới khi consumer đọc. Consumer là process, còn handler chứa business logic. Một topic có thể được route tới nhiều queue để notification, analytics và audit xử lý độc lập. Mỗi queue có acknowledgment và backlog riêng. Nhiều topic cũng có thể vào một queue qua wildcard, nhưng handler phải hiểu mọi schema đi vào. Tách queue theo consumer concern giúp scale, retry và failure isolation. Gộp mọi topic vào một queue làm external service chậm có thể chặn task critical khác. Quá nhiều queue lại tăng broker metadata và vận hành. Kiến trúc cần cân bằng domain boundary, throughput profile và ownership. Ví dụ, queue gửi thông báo không nên dùng chung với queue cập nhật trạng thái giao hàng, vì mức độ quan trọng và chiến lược retry của chúng khác nhau. Khi chia đúng ranh giới, một sự cố ở dịch vụ phân tích không làm chậm luồng fulfillment chính.

Communication xml khai báo topic, message type hoặc service schema và khai báo handler. Topic name nên là chuỗi phân tách bằng dấu chấm từ tổng quát tới cụ thể. Name phải unique và không dùng wildcard ở phần declaration. Request phù hợp với type đơn giản. Schema trỏ tới service interface method và mô tả structure rõ hơn array. Với synchronous topic còn có response type, vì caller chờ kết quả. Asynchronous topic không cần response. Message contract nên nhỏ, typed và versioned. Có thể chỉ gửi shipment id, operation id và schema version. Gửi toàn bộ model serialize làm coupling chặt với database shape, payload lớn và dễ lộ dữ liệu nhạy cảm. Queue có thể còn message cũ khi code mới deploy, nên consumer cần compatibility window. Snapshot payload và identifier payload có semantics khác nhau. Snapshot giữ input cũ, identifier cho consumer đọc state mới. Team phải chọn rõ ràng. Một contract tốt cũng xác định trường bắt buộc, trường tùy chọn và cách xử lý message đến từ phiên bản cũ. Nếu consumer không hiểu version mới, nó phải fail có kiểm soát thay vì âm thầm bỏ dữ liệu. Điều này giúp deployment nhiều node an toàn hơn khi code cũ và code mới cùng tồn tại trong thời gian chuyển tiếp.

Publisher dùng PublisherInterface và topic string để gửi message. Publisher config quyết định topic đi connection và exchange nào. Nếu database transaction rollback sau khi message đã publish, consumer có thể đọc entity chưa tồn tại hoặc state chưa commit. Hướng an toàn là publish sau commit hoặc dùng outbox. Outbox lưu event trong cùng transaction với business entity rồi worker publish sau. Broker unavailable cũng cần policy rõ. Có flow phải fail request, có flow ghi outbox và retry, còn side task không quan trọng mới có thể được bỏ qua theo business decision. Không swallow publish exception mà không có recovery. Operation id nên đi cùng message để trace và idempotency. Publisher chỉ nên biết topic contract, không chứa logic topology. Connection explicit tăng control nhưng làm module coupling deployment. Automatic resolution giúp cùng package chạy trên nhiều môi trường. Outbox còn tạo một nơi quan sát rõ ràng cho các event chưa được publish. Worker có thể retry theo batch, ghi số lần thử và cảnh báo khi một bản ghi tồn tại quá lâu. Cách này đổi một lỗi khó thấy trong request thành một workflow có trạng thái và có thể khôi phục.

Queue publisher xml map topic tới connection và exchange. Connection có thể là amqp, stomp hoặc database, hoặc được framework resolve từ env configuration. Chỉ một publisher enabled cho mỗi topic. Nếu nhiều connection cùng enable, behavior không hợp lệ hoặc khó dự đoán. RabbitMQ thường dùng exchange magento trong configuration mặc định. ActiveMQ Artemis có queue semantics riêng theo stomp. Module portable thường bỏ explicit connection và để deployment chọn broker. Khi hệ thống có nhiều broker hoặc một topic phải đi connection riêng, explicit mapping có lý do. Publisher, topology và consumer phải dùng connection tương thích. Publish qua amqp nhưng queue chỉ được khai báo ở database sẽ làm message và consumer không gặp nhau. Debug cần kiểm tra merged config, không chỉ từng file source. Khi review cấu hình, cần kiểm tra cả cấu hình sau khi merge vì module khác có thể disable hoặc thay publisher. Một file riêng nhìn đúng chưa chứng minh runtime đang dùng mapping đó. Công cụ debug phải cho thấy topic cuối cùng đang đi qua connection và exchange nào.

Queue topology xml định nghĩa exchange, binding và destination queue. Exchange type được Adobe mô tả là topic. Binding có id unique, topic pattern và queue destination. Asterisk khớp một segment, còn pound khớp nhiều segment. Pattern vendor shipment pound có thể nhận nhiều operation shipment. Wildcard giúp route linh hoạt nhưng pattern quá rộng như pound nhận mọi topic và có thể đưa schema lạ vào handler. Một topic có thể bind tới nhiều queue để nhiều concern xử lý độc lập. Exchange durable mặc định giúp tồn tại qua broker restart, còn auto delete và internal có semantics riêng. Broker arguments như alternate exchange chỉ nên dùng khi hiểu broker và platform support. Không copy argument RabbitMQ sang ActiveMQ hoặc database adapter mà giả định tương đương. Topology là graph, một sai tên ở exchange, binding hoặc queue đủ làm message không tới consumer. Tên queue nên phản ánh trách nhiệm của consumer thay vì chỉ lặp lại topic. Điều này giúp dashboard, quyền broker và runbook incident dễ hiểu. Khi đổi topology, cần đánh giá message còn nằm trong queue cũ và kế hoạch drain trước khi xóa destination.

Queue consumer xml nối consumer name với queue và handler. Name dùng để start process và quan sát. Consumer instance mặc định là framework consumer, nhưng có batch consumer hoặc implementation khác cho use case cụ thể. Max messages giới hạn số message trước khi process exit, giúp recycle memory. Max idle time và sleep chỉ được xử lý trong điều kiện Adobe mô tả khi consumer chạy với max messages. Only spawn when message available được consumers runner kiểm tra để tránh bootstrap process khi queue trống. Consumers wait for messages là setting global khác. Khi false, process đã spawn sẽ exit nếu không có message. Hai setting cùng giảm resource nhưng ở boundary khác nhau. Queue ít traffic có thể dùng only spawn và idle exit. Queue throughput cao thường cần worker luôn sẵn sàng để giảm startup latency. Capacity phải dựa arrival rate, processing rate và latency target. Không nên dùng max messages như một con số sao chép giữa mọi consumer. Handler có memory profile, thời gian xử lý và mức tải khác nhau. Cần đo resident memory, restart cost và queue age để chọn giá trị hợp lý, rồi kiểm tra lại sau mỗi thay đổi lớn của payload hoặc dependency.

Handler có thể được khai báo trong communication xml hoặc trực tiếp trong consumer config. Với default consumer, handler trong consumer config được ưu tiên và communication handler bị bỏ qua. Đây là lỗi debug phổ biến. Developer sửa class trong communication nhưng runtime vẫn gọi handler cũ ở queue consumer. Nếu có custom consumer instance, implementation đó quyết định cách dùng handler. Best practice là chọn một nguồn rõ cho mỗi use case, tránh khai báo hai handler khác nhau mà không document. Merged configuration và log startup có thể xác nhận class thật được gọi. Handler nên là service nhỏ gọi domain logic, không chứa một method khổng lồ với database, http client, retry và logging trộn lẫn. Unit test kiểm tra business behavior, integration test kiểm tra decode và queue wiring. Nếu cần nhiều handler cho cùng topic, cách rõ ràng hơn thường là route tới nhiều queue, mỗi queue có consumer riêng. Cách đó cho phép retry, scale và quan sát độc lập. Gọi nhiều side effect trong một handler duy nhất khiến một bước lỗi có thể kéo toàn bộ message vào retry và lặp lại những bước đã thành công.

Connection resolution lấy deployment config trong env file. Khi không khai báo explicit, framework chọn amqp nếu RabbitMQ được cấu hình, chọn stomp nếu ActiveMQ Artemis được cấu hình, nếu không thì dùng database adapter. Khi nhiều external connection cùng có, default connection hoặc mapping riêng cần rõ. Extension không nên hard code broker nếu không có yêu cầu kiến trúc. RabbitMQ dùng amqp và phù hợp production phổ biến. ActiveMQ Artemis dùng stomp và cần anycast cho point to point theo tài liệu Adobe. Database adapter lưu message trong các bảng queue và dùng cron consumer. Adobe nêu adapter này không scalable và khuyên external broker cho production khi có thể. Database queue cạnh tranh connection, disk và query với checkout, indexer và admin. Local tiện không có nghĩa production phù hợp. Khi dùng database adapter trong môi trường phát triển, test vẫn phải bao phủ broker thật trước production vì semantics về acknowledgment, redelivery, durability và permission không hoàn toàn giống nhau. Một flow chạy đúng trên database chưa chứng minh topology và credential của RabbitMQ hoặc ActiveMQ đã đúng.

Credential broker nằm trong deployment config và không được commit vào Git. Secret manager hoặc platform tooling nên cấp host, user, password, virtual host và tls option. Broker user cần least privilege trên virtual host, exchange và queue cần thiết. Credential rotation phải xét long running consumer giữ connection cũ. Deploy secret mới nhưng không restart process có thể làm một số worker tiếp tục connection cũ tới khi broker đóng. Network nên private và firewall giới hạn source. Monitoring cần connection failure, authentication error và reconnect rate. Không log connection string có password. Khi nhiều environment dùng broker khác nhau, code package giữ nguyên còn env config thay đổi. Đây là lợi ích của logical topology tách khỏi deployment connection. Ngoài credential, cần quản lý certificate, thời hạn hết hạn và hostname verification nếu dùng tls. Việc rotate secret phải có runbook gồm cập nhật secret, restart consumer theo đợt, kiểm tra connection mới và giữ khả năng rollback. Không nên restart toàn bộ worker cùng lúc nếu backlog lớn. Mỗi lần rotate cần được ghi audit để truy vết sự cố.

Handler phải idempotent vì message có thể được giao lại. Carrier api call thành công nhưng process chết trước acknowledge sẽ làm broker redeliver. Operation id hoặc business unique key ngăn tạo side effect lần hai. Handler cần phân loại permanent invalid message, transient network error, business conflict và infrastructure failure. Retry vô hạn một payload sai làm poison message chặn throughput. External call phải có timeout. Database update cần transaction, nhưng external service không nằm trong cùng transaction, nên state machine, outbox hoặc reconciliation thường cần thiết. Log topic, operation id và entity id an toàn, không log token hoặc toàn payload. Một handler treo làm processing rate về không dù consumer process vẫn tồn tại. Health check phải nhìn throughput và queue age, không chỉ pid. Idempotency key cần được lưu bền vững ở nơi tất cả consumer instance cùng nhìn thấy. Biến trong memory không đủ vì process có thể restart hoặc message được xử lý bởi node khác. Bản ghi deduplication cũng cần retention policy để không tăng vô hạn, nhưng không được xóa sớm hơn cửa sổ redelivery thực tế.

Store context quan trọng với scope config, currency, locale và website mapping. Adobe có cơ chế đưa store id vào message header của asynchronous request và restore store context ở consumer. Handler không nên luôn dùng default store nếu operation thuộc store cụ thể. Publisher hoặc framework phải set trusted context, không tin một store id tùy ý để bỏ qua authorization. Test nên publish từ nhiều store view và chứng minh consumer đọc đúng config. Tạo store mới còn liên quan poison pill vì long running process có thể giữ scope tree cũ. Store context và in memory lifecycle phải được xem cùng nhau. Một message có store id đúng nhưng consumer chưa biết store mới vẫn có thể fail hoặc fallback sai. Multi store integration cần log store id và website id an toàn trong trace. Nếu business config cần được chụp tại thời điểm publish, message nên mang snapshot tối thiểu đã được xác thực. Nếu phải dùng trạng thái mới nhất, consumer đọc lại dữ liệu và chấp nhận kết quả có thể khác thời điểm request. Hai lựa chọn này phải được ghi rõ trong contract và test acceptance.

Asynchronous và Bulk rest api được xây trên message queue framework. Webapi async có thể tự generate communication và publisher config từ service routes, đồng thời cung cấp topology và consumer chung cho operation async. Vì vậy không nên duplicate bốn file custom nếu đang dùng generated flow. Async operations all consumer xử lý message framework. Connection được resolve từ env. Bulk request tạo nhiều task, mỗi task có status riêng. Accepted bulk request không có nghĩa mọi item hoàn thành. Nếu một item fail, caller cần đọc operation status. Generated configuration vẫn có thể được extension reader điều chỉnh, nhưng developer phải hiểu sort order và compatibility. Custom topic phù hợp cho domain messaging riêng; async rest phù hợp khi muốn đưa service contract rest vào queue. Hai cơ chế liên quan nhưng không hoàn toàn giống nhau. Bulk processing cần backpressure. Nếu producer tạo task nhanh hơn consumer xử lý trong thời gian dài, queue age sẽ tăng dù hệ thống chưa báo exception. Có thể giới hạn kích thước batch, điều tiết producer, tăng consumer có kiểm soát hoặc phân tách queue theo mức ưu tiên.

Git review phải xem bốn file queue như một graph. Communication đúng nhưng thiếu publisher, binding hoặc consumer vẫn không tạo flow hoàn chỉnh. Có thể tách commit thành contract, publisher, topology, consumer handler và test. Topic rename là breaking change với publisher, binding và message tồn trong queue. Migration có thể dual publish hoặc dual bind trong thời gian giới hạn, drain queue cũ rồi retire. Message schema rollout nên deploy consumer đọc được cả cũ và mới trước, sau đó publisher gửi schema mới. Rollback code phải xử lý message mới còn backlog. Contract test nên so sánh schema được publish với schema consumer chấp nhận. Việc đổi tên field mà không có compatibility plan có thể làm backlog cũ trở thành poison message ngay sau deployment.

Nếu dashboard không dẫn tới bước điều tra cụ thể, nó chỉ tạo thêm tiếng ồn cho đội vận hành. Việc ưu tiên alert phải dựa trên mức ảnh hưởng nghiệp vụ.
