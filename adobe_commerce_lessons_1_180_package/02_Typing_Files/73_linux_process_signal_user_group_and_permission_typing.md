Linux không chạy một tệp theo nghĩa tĩnh mà tạo một process có pid, parent, credential, environment, current directory, umask, file descriptor và resource limit riêng. Cùng một binary php có thể xuất hiện dưới dạng master của php fpm, nhiều worker web, một lệnh cli, một cron runner và nhiều consumer. Vì vậy hai command dùng cùng source vẫn có thể tạo kết quả khác khi được start bởi parent khác. Child thường thừa hưởng environment, umask, descriptor và limit từ parent, còn thao tác exec thay program image nhưng giữ pid. Process tree là bằng chứng đầu tiên để biết worker do master, shell, cron hay supervisor tạo. Foreground process gắn với terminal foreground group, trong khi một job có dấu và chỉ được đưa ra background của shell hiện tại. Nó chưa trở thành service đáng tin vì có thể phụ thuộc terminal, không có restart policy và không có health check. Session và process group còn quyết định signal được gửi tới một process hay cả nhóm. Daemon production cần identity, log, graceful stop, resource limit và supervisor rõ ràng. Khi process ở trạng thái sleeping, không nên tự động coi nó bị treo. Nó có thể đang chờ socket, lock, child hoặc io. Cần xem state, wait channel, elapsed time và các process cùng chờ resource. Một child đã exit nhưng parent chưa wait trở thành zombie. Zombie không còn chạy code nên gửi thêm signal không giải quyết được; parent phải reap child. Orphan lại là child còn sống sau khi parent kết thúc và có thể được reparent. Hai khái niệm này khác nhau và dẫn tới cách xử lý khác nhau. Khi thu thập bằng chứng, nên chụp cả command line, parent chain, start time và namespace của process. Một pid giống nhau trong host và container có thể chỉ là ánh xạ khác nhau, nên không được kết luận dựa trên một con số rời rạc. Process tree sau deploy còn giúp phát hiện worker cũ vẫn giữ code hoặc configuration trước release.

Signal là control primitive bất đồng bộ, không phải message business. Lệnh kill mặc định thường gửi sigterm chứ không gửi sigkill, vì vậy tên command dễ làm người mới hiểu sai. Sigterm cho process cơ hội ngừng nhận work mới, hoàn tất hoặc rollback transaction, đóng connection và flush log. Sigkill do kernel cưỡng chế và không thể được process catch hoặc ignore. Quy trình dừng an toàn nên gửi signal graceful, chờ trong timeout có giới hạn, quan sát process tree rồi mới escalate. Forced kill dùng quá sớm có thể làm consumer bị redelivery, tạo side effect trùng nếu business operation không idempotent, hoặc che lỗi wrapper không forward signal. Một shell wrapper tạo child phải trap signal, chuyển signal tới child và wait để lấy exit status. Dù vậy script ngắn vẫn không thay thế supervisor vì còn thiếu restart, backoff, user, group, limit và log policy. Kill bằng signal không còn chỉ phụ thuộc pid. Kernel kiểm tra credential của sender và target, còn pid có thể được reuse sau khi process cũ kết thúc. Một pid file cũ vì thế cần được xác minh bằng executable, start time hoặc service manager. Kill với signal không có payload có thể dùng để kiểm tra tồn tại và permission, nhưng vẫn có race vì process có thể exit ngay sau kiểm tra. Khi process không dừng, cần xem signal pending, blocked, ignored hoặc caught, rồi xác định nó đang chờ io, lock hay child. Kill chín không phải công cụ chẩn đoán nguyên nhân. Một quy trình escalation tốt phải ghi thời điểm gửi từng signal, số process còn sống và work đang chạy. Điều này giúp phân biệt process thật sự không phản hồi với process đang hoàn tất tác vụ hợp lệ. Nếu phải dùng sigkill, incident report cần nêu lý do, phạm vi side effect có thể xảy ra và bước kiểm tra dữ liệu sau đó.

Permission của linux bắt đầu từ identity của process chứ không bắt đầu từ tên người đang nhìn terminal. Process có real, effective và saved user id, primary group và supplementary group. Permission check thông thường dựa nhiều vào effective credential và group list. Một user vừa được thêm vào shared group nhưng session cũ chưa được tạo lại có thể vẫn thiếu group đó. Mỗi file hoặc directory có owner, group và mode cho user, group và other. Read, write và execute trên file khác ý nghĩa trên directory. Directory cần execute để traverse, read để liệt kê tên và write kết hợp execute để tạo, xóa hoặc rename entry. Vì thế file cuối writable chưa đủ nếu một parent directory thiếu execute. Setgid trên directory giúp file mới inherit group của parent, rất hữu ích khi file system owner và web server user dùng shared group. Tuy nhiên setgid không tự làm file mới group writable vì umask còn loại permission. Umask được child thừa hưởng từ parent và không bị exec reset, nên cron, supervisor, shell và php fpm có thể tạo file khác mode dù chạy cùng code. Access control list và read only mount còn là các lớp khác. Dấu cộng ở mode gợi ý cần xem acl, còn mount read only không thể được sửa bằng chmod. Capability có thể tách một số quyền root, nhưng không nên cấp capability rộng như một cách né thiết kế least privilege. Root chạy được command chỉ chứng minh root vượt nhiều check, không chứng minh permission model đúng. Permission test nên được thực hiện bằng đúng identity của service thay vì root hoặc tài khoản quản trị. Có thể dùng một file tạm trong đúng directory để kiểm tra create, rename và delete, rồi dọn sạch ngay. Cách này cho thấy quyền thực tế trên toàn path và tránh kết luận sai từ một lệnh ls chỉ hiển thị mode của entry cuối.

Adobe commerce khuyến nghị mô hình hai user khi vận hành private server: file system owner chạy lệnh cli và cron, còn web server user chạy storefront và admin, hai bên chia sẻ một group cần thiết. Trong developer hoặc default mode, các vùng như var, generated, pub static, pub media và app etc cần writable theo mô hình đã chọn. Production giảm write access cho code và artifact sau deployment để tăng an toàn. Lỗi phổ biến xuất hiện khi một engineer chạy compile hoặc cache command bằng root. Command đầu tiên thành công nhưng để lại file root owned, sau đó cron và php fpm không thể ghi. Chạy lại bằng sudo chỉ tạo thêm artifact sai owner. Cách debug đúng là ghi exact path và operation, tìm pid thực hiện, xem effective user và group, kiểm tra từng component của path, mode, acl, umask và mount. Công cụ namei giúp thấy permission của từng directory, còn stat cho uid, gid và mode bằng số. Nếu cli pass nhưng web fail, cần so identity, supplementary group, umask, environment, php configuration và container mapping. Chmod recursive bảy bảy bảy là anti pattern vì mở write cho mọi user, che sai owner, không giải quyết read only mount và không bảo đảm file mới đúng mode. Permanent fix phải sửa identity pipeline, shared group, setgid và umask, sau đó clean và rebuild artifact. Trên cloud infrastructure, source artifact được mount read only ngoài các mount được hỗ trợ, nên generation phải chạy ở đúng build hoặc deploy phase thay vì cố mở quyền runtime. Khi chuyển từ developer sang production mode, team cần xác định rõ bước nào tạo artifact và bước nào chỉ đọc artifact. Nếu runtime vẫn cần ghi vào code tree, đó thường là dấu hiệu pipeline chưa hoàn tất hoặc extension đang viết sai vị trí. Quyền đúng phải được tái tạo tự động sau mỗi deploy, không phụ thuộc một lệnh chown thủ công của cá nhân.

File descriptor là số trong mỗi process tham chiếu file, pipe, socket hoặc object io đang mở. Php fpm worker cần descriptor cho client, upstream, log và file; consumer cần broker, database và log connection. Sau khi một pathname bị unlink, process vẫn có thể giữ descriptor tới inode, vì vậy disk chưa được giải phóng dù du không thấy file. Lsof với deleted open file giúp xác minh, rồi daemon nên reopen log hoặc restart graceful theo procedure. Resource limit cho open file có soft và hard value, được child thừa hưởng từ parent và giữ qua exec. Thay limit trong shell đăng nhập không tự thay service đã được supervisor start. Error too many open files có thể do limit thấp so với concurrency hợp lệ hoặc do descriptor leak. Việc chỉ nâng limit thường chỉ trì hoãn thời điểm descriptor leak làm dịch vụ ngừng nhận kết nối. Cần theo dõi count theo pid, phân loại target, so với request hoặc message count và worker age. Nếu count tăng liên tục, tìm connection hoặc file không đóng. Worker recycling có thể giảm impact của leak nhưng là mitigation, không phải permanent fix. Descriptor còn có close on exec để tránh child thừa hưởng resource không cần. Một child giữ đầu pipe hoặc socket ngoài ý muốn có thể làm parent chờ mãi. Khi điều tra deploy treo hoặc process không exit, xem danh sách descriptor và process tree thường cho bằng chứng mạnh hơn việc chỉ đọc một dòng timeout. Log rotation cũng phải phối hợp với descriptor lifecycle. Rename file log không buộc process mở file mới, còn copy truncate có tradeoff về io và mất dữ liệu trong race. Cách phù hợp phụ thuộc daemon có hỗ trợ reopen signal hay graceful restart không. Monitoring nên so dung lượng filesystem với tổng file nhìn thấy để phát hiện phần chênh lệch do file đã xóa nhưng còn mở.

Php fpm master quản lý worker web, còn cron và consumer dùng php cli process có lifecycle khác. Khi lỗi chỉ xảy ra ở web, cùng source chưa đủ để kết luận application code khác; worker có thể chạy user, group, umask, environment và php ini khác cli. Cron của adobe commerce phải chạy bằng file system owner vì nhiều chức năng như index, email, rule và consumer runner phụ thuộc nó. Trên cloud infrastructure, adobe lưu ý chỉ một cron job có thể chạy tại một thời điểm trên web instance, nên long running task nên được chia thành queued work nhỏ hoặc chuyển sang worker. Consumer có thể được start bằng cron hoặc external process manager. Cron thường tạo worker xử lý một số message rồi exit, trong khi supervisor giữ worker dài hạn và restart sau crash. Cấu hình chờ message phù hợp với worker lâu dài, còn max messages cho phép recycle process. Không nên vô tình dùng cả cron runner và supervisor cho cùng consumer nếu chưa tính concurrency và idempotency. Supervisor phải pin command, working directory, user, group, environment, umask, open file limit, graceful signal, stop timeout, restart backoff và log. Start consumer bằng dấu và trong ssh shell không có các control đó. Khi terminal đóng, process có thể nhận hangup hoặc sống thành orphan nhưng vẫn không được supervision. Service đáng tin cần version verification sau deploy, queue lag, restart reason và bounded shutdown. Sau mỗi thay đổi supervisor, cần xác minh process thực tế nhận đúng user, group, umask và limit chứ không chỉ đọc file cấu hình. Một service có thể chưa reload hoặc vẫn giữ worker cũ. Bằng chứng nên gồm pid mới, start time, command line, effective credential, open file limit và một smoke test ghi vào đúng writable directory của adobe commerce.

Một deploy an toàn phải điều khiển lifecycle của worker thay vì chỉ thay file. Trước khi đổi artifact, supervisor ngừng nhận work mới hoặc dừng consumer theo procedure, cho message đang xử lý hoàn tất trong timeout và xác minh process exit. Sau deploy, migration và cache procedure chạy bằng đúng file system owner, rồi worker mới được start và kiểm tra version. Nếu forced kill xảy ra giữa transaction, broker có thể redeliver message nên handler cần idempotency. Khi deploy timeout trong bước stop, có thể wrapper không forward sigterm, worker bị chặn ở external io không có timeout, hoặc child còn sống sau parent. Tăng stop timeout chỉ hợp lý khi evidence cho thấy transaction hợp lệ cần thêm thời gian. Nếu process tạo zombie, lỗi nằm ở parent không wait. Nếu consumer biến mất sau logout, lỗi nằm ở cách start không có supervisor. Nếu disk không giảm sau log deletion, process có thể giữ descriptor. Nếu generated permission denied, lỗi có thể do root owned artifact hoặc group inheritance. Mỗi symptom cần exact evidence riêng. Technical lead phải phân biệt mitigation và permanent fix: restart worker khác sửa crash, chown file hiện có khác sửa pipeline identity, tăng descriptor limit khác đóng leak, forced kill khác sửa graceful shutdown. Runbook tốt ghi pid, parent, credential, signal, path permission, limit và log thay vì một chuỗi lệnh quyền cao không giải thích. Rollback code không tự quay lại message đã xử lý hoặc transaction external đã phát sinh. Vì vậy kế hoạch deploy worker cần gắn version của payload, compatibility window và cách xử lý message đang nằm trong queue. Nếu hai version chạy đồng thời trong thời gian drain, schema và contract phải tương thích ngược. Đây là lý do lifecycle process là một phần của release design, không chỉ của vận hành.

Cách review ở mức expert là kiểm tra ranh giới privilege và lifecycle trước khi hỏi command có chạy hay không. Web process và consumer không nên chạy root. Shared group chỉ chứa identity cần thiết, env php không world readable, code production read only và writable path được giới hạn. Supervisor không nên đọc secret từ file mà application có thể sửa. Log điều tra không được copy toàn bộ environment vì có thể chứa credential. Process count và permission còn ảnh hưởng performance. Quá ít php fpm worker tạo queue request, quá nhiều worker gây memory pressure và bão connection database. Quá nhiều consumer làm broker hoặc database contention, còn open file limit thấp chặn socket mới. Recursive chown trên tree lớn có thể kéo dài deploy. Capacity phải dựa trên workload và downstream limit, không chỉ số core. Một checklist tốt hỏi process do ai start, pid và parent nào, signal nào đã gửi, child có được forward signal không, effective group có đúng không, từng directory có traverse được không, umask tạo file mới ra sao, mount có read only không, descriptor count tăng thế nào và limit đến từ supervisor nào. Sau khi sửa, deployment gate nên kiểm tra unexpected owner, writable code path và worker version. Mục tiêu cuối cùng không phải làm permission error biến mất trong một lần, mà tạo hệ thống least privilege, graceful, observable và tái tạo được qua mỗi deploy. Review còn phải kiểm tra khả năng audit. Mọi lệnh sửa owner, mode, limit hoặc supervisor nên nằm trong automation có version và được peer review. Thao tác khẩn cấp cần được ghi lại rồi chuyển thành permanent change trong repository. Khi cùng lỗi tái diễn sau mỗi release, nguyên nhân gần như chắc chắn nằm ở pipeline hoặc ownership model chứ không nằm ở một file riêng lẻ.
