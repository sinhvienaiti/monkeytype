Redis hoặc valkey trong adobe commerce không phải một hộp cache duy nhất. Default cache, full page cache và session có mục đích khác nhau. Cache ứng dụng có thể tái tạo từ database hoặc configuration. Full page cache có thể được rebuild từ request. Session chứa trạng thái customer hoặc admin đang hoạt động, nên mất key có thể gây logout, mất form state hoặc gián đoạn checkout. Nếu ba workload dùng chung một process và cùng memory policy, campaign tạo nhiều page cache có thể đẩy session ra ngoài dù backend vẫn trả ping nhanh. Logical database number chỉ tách namespace trong cùng process. Nó không tách cpu, memory, persistence, failover hoặc eviction. Instance riêng tạo isolation mạnh hơn. Prefix ngăn key collision giữa project và environment, nhưng đổi prefix trong deployment giống như chuyển sang keyspace mới. Cache sẽ cold start và session có thể logout hàng loạt. Vì vậy prefix là compatibility setting. Trước khi tối ưu, hãy xác định phiên bản commerce hỗ trợ redis hay valkey và option cli nào hợp lệ. Tài liệu mới dùng valkey cho nhánh mới, còn dự án cũ có thể vẫn dùng redis. Không đổi tên backend chỉ vì tài liệu mới hơn mà bỏ qua system requirements. Cấu hình thật cần được đọc từ artifact đã deploy, relationship và environment variable, không chỉ từ file local. Senior review bắt đầu bằng sơ đồ workload, key prefix, database, instance, memory limit và failure tolerance. Họ hỏi dữ liệu nào có thể mất, dữ liệu nào phải fail write thay vì bị eviction, và cold start sẽ dồn tải vào mysql hay origin ra sao. Một cấu hình tốt không chỉ có kết nối thành công. Nó ngăn cache pressure làm hỏng session, có alert trước khi memory đầy và có runbook failover cùng rollback prefix.

Expiration và eviction thường bị nhầm vì cả hai đều làm key biến mất. Expiration là contract theo ttl. Key hết hạn được dọn theo chu kỳ hoặc khi truy cập, nên memory không nhất thiết giảm đúng tại giây hết hạn. Eviction xảy ra khi memory chạm giới hạn và server phải giải phóng chỗ theo policy. Một session có ttl dài vẫn có thể bị eviction sớm nếu policy cho phép xóa mọi key. Cache thuần có thể chấp nhận chính sách dựa trên recency hoặc frequency, nhưng session thường cần policy tránh xóa tùy ý và alert trước write failure. No eviction không làm hệ thống tự an toàn; khi đầy, write có thể fail và application phải xử lý. Memory planning phải tính dataset, object overhead, allocator fragmentation, client buffer, replication buffer và persistence. Used memory khác rss. Fragmentation ratio cao có thể do allocator và pattern cấp phát, không tự động chứng minh leak. Restart giảm rss tạm thời nhưng tạo cold cache hoặc mất session tùy persistence, vì vậy không phải giải pháp đầu. Maxmemory cần headroom, không đặt bằng toàn bộ ram. Cache hit rate cũng cần context. Hit cao có thể do vài key nóng, trong khi miss trên product projection đắt vẫn làm page chậm. Hit thấp sau deploy hoặc purge có thể bình thường. Hãy đọc hit, miss, eviction, expired key, command latency và application timing theo cùng timeline. Nếu cache key thiếu store hoặc customer group, hit rate cao nhưng dữ liệu sai. Correctness quan trọng hơn tỷ lệ đẹp. Khi memory tăng, sample size và type an toàn, không chạy keys wildcard trên production. Scan có giới hạn và tool được phê duyệt giúp tránh chặn event loop. Dashboard tốt cho thấy memory headroom, eviction rate, fragmentation, largest sampled value và tốc độ tăng theo release hoặc campaign.

Session locking bảo vệ trường hợp nhiều request cùng cookie đọc một state rồi ghi đè nhau. Một request cập nhật cart, request khác cập nhật customer section, nếu cả hai đọc cùng phiên bản và ghi cuối cùng thắng thì update có thể mất. Lock serialize critical section của cùng session. Đổi lại, request thứ hai phải chờ request đầu. Nếu request đầu gọi external api, query chậm hoặc stream response trong lúc giữ lock, nhiều ajax cùng customer sẽ xếp hàng dù redis latency rất thấp. Điều tra cần trace thời điểm acquire và release session, không chỉ xem slow log server. Disable locking có thể giảm queue nhưng tạo race, nên phải có concurrency test và thiết kế state khác. Một số dữ liệu có thể dùng operation atomic hoặc tách khỏi session; không nên tắt lock toàn cục chỉ để che request dài. Logout ngẫu nhiên có nhiều nguyên nhân. Session key có thể bị eviction, ttl sai, prefix đổi, failover mất write mới, cookie domain lệch hoặc application không ghi session do lỗi. Evidence gồm session id từ cookie, key tồn tại, ttl, memory, eviction counter, failover timeline và log write. Không đưa payload session nhạy cảm vào log. Nếu failover dùng replica asynchronous, write mới có thể chưa replicate và bị mất khi promote. Điều đó khác eviction nhưng symptom giống nhau. Retry kết nối cần thận trọng vì command đã được server xử lý nhưng response mất có thể tạo kết quả mơ hồ với operation không idempotent. Session store cần capacity, policy và high availability phù hợp hơn cache. Một runbook tốt có cách phân biệt một user, một node, toàn environment và một thời điểm failover. Nó không bắt đầu bằng clear cache hoặc kéo dài ttl. Sau fix, test nhiều request cùng cookie, failover giả lập và memory pressure để chứng minh state vẫn nhất quán.

Cache stampede xuất hiện khi nhiều request cùng miss một key đắt và đồng thời rebuild. Nó thường xảy ra sau purge all, deploy làm đổi prefix, ttl đồng loạt hết hoặc failover mất cache. Database và php fpm có thể quá tải trong vài giây dù cache service không lỗi. Biện pháp đầu là giảm đồng thời rebuild. Lock hoặc request coalescing cho một worker tạo value, worker khác chờ hoặc dùng stale. Lock phải có ttl và owner token để worker chết không giữ vĩnh viễn. Release lock chỉ khi token còn đúng, tránh xóa lock của worker mới. Stale cache cho phép trả value cũ trong cửa sổ khi refresh hoặc backend lỗi. Nó phù hợp với content chấp nhận cũ ngắn hạn, không phù hợp với authorization, payment hoặc inventory invariant cần current state. Jitter ttl phân tán thời điểm hết hạn. Prewarm có kiểm soát giúp key quan trọng nhưng prewarm toàn catalog có thể tự tạo load storm. Adobe commerce cache tags giúp invalidation theo entity, nhưng extension gắn quá nhiều tag hoặc clean scope rộng có thể tạo invalidation storm. Full page cache ở varnish hoặc fastly là layer khác với redis cache. Purge edge không nhất thiết xóa application cache và ngược lại. Khi page chậm sau cache clean, hãy theo dõi miss rate theo layer, origin request, database query và worker saturation. Không kết luận redis stampede chỉ vì cpu mysql tăng. Một cache key sai scope còn nguy hiểm hơn stampede vì trả dữ liệu customer hoặc store không đúng. Review cache design cần key composition, ttl, tag, rebuild cost, stale policy và permission boundary. Test phải tạo nhiều request đồng thời vào một key chưa có, đo số lần builder thật chạy và hành vi khi builder fail. Hệ thống tốt giới hạn rebuild, giữ latency có kiểm soát và không trả stale ngoài business window.

Serialization, compression và large value quyết định cả memory lẫn latency. Commerce biến object hoặc array thành byte trước khi lưu. Nếu serializer hoặc class contract thay đổi, value cũ có thể không đọc được sau rolling deployment. Cache có thể được flush chủ đích, nhưng session không thể tùy tiện mất. Schema của session value cần backward compatibility hoặc deployment phải chấp nhận logout. Compression giảm network và dataset cho value lớn, nhưng tốn cpu và thời gian nén giải nén. Threshold thấp làm key nhỏ bị nén vô ích. Threshold cao bỏ lỡ value lớn. Cần đo distribution, ratio và percentile latency. Large value gây copy, network, allocator và deletion cost. Một command trên collection rất lớn có thể chiếm event loop đủ lâu để mọi client chậm. Slow log và latency monitor giúp tìm command, nhưng slow log không bao gồm mọi network wait. Client output buffer lớn có thể dùng memory đáng kể khi consumer chậm. Fragmentation cao sau churn có thể cần lazy free hoặc defragmentation theo service support, không nên tự sửa config cloud ngoài quyền. L2 cache trên web node giảm network tới remote backend nhưng thêm consistency boundary. Local value phải được invalidation đúng. Nếu node một giữ cache cũ trong khi node hai đã clean, symptom theo node. Correlation cần hostname hoặc pod id. Khi tối ưu compression, hãy đo php cpu, backend cpu, bytes transferred và memory saved. Không chỉ nhìn memory giảm. Khi đổi serializer, chạy compatibility test với value được tạo bởi code cũ. Senior review yêu cầu limit kích thước và không cache payload không có chiến lược invalidation. Cache là optimization, không phải nơi cất business record duy nhất. Khi review cache payload, team nên đo kích thước serialized thực tế và chi phí giải mã, vì object nhỏ trong php có thể thành value lớn sau khi chứa metadata hoặc danh sách lồng nhau. Một giới hạn rõ giúp phát hiện regression trước khi memory tăng âm thầm. Test cũng cần chứng minh dữ liệu nguồn vẫn có thể dựng lại khi cache bị mất hoàn toàn.

Monitoring redis hoặc valkey cần kết hợp server, client và application. Server cung cấp memory, rss, fragmentation, hit miss, expired, evicted, connected và blocked client, commandstats, slow log cùng latency events. Client cần pool wait, connection error, timeout, retry và bytes. Application cần cache build time, session lock wait, full page cache status và request correlation. Một latency spike server có thể do command tuyến tính, fork persistence, swap, allocator hoặc network. Ping từ một node không đại diện cho mọi web node. Chạy latency baseline gần server giúp tách intrinsic latency với network. Blocked client trong danh sách có thể là command blocking hợp lệ, không tự động là sự cố. Cần biết command và duration. Alert nên dựa trên trend và business impact, không chỉ threshold tĩnh. Eviction tăng trên cache có thể chấp nhận ở peak nhưng eviction session thì không. Memory gần max với no eviction là cảnh báo trước write failure. Hit rate giảm sau deploy cần cửa sổ warmup. Failover event phải gắn deployment marker để giải thích reconnect và session loss. Runbook thu thập info theo section thay vì dump mọi key. Không lưu secret hoặc session payload. Khi incident, xác định layer trước: edge cache, application cache, session hay local l2. Team cần truy ngược keyspace tới feature, tenant hoặc campaign tạo cardinality và đặt owner cho cleanup. Dashboard phải phân biệt memory do dataset, allocator overhead và replica backlog.

Failover và cold start là hai bài test thường bị bỏ qua. Replica có thể giúp availability nhưng replication không đồng bộ tuyệt đối. Promote sau lỗi có thể thiếu session vừa ghi. Cache thiếu key thì rebuild, nhưng hàng nghìn request cùng rebuild có thể làm mysql quá tải. Client reconnect cần timeout ngắn đủ để fail fast nhưng không gây retry storm. Circuit breaker ở application có thể bảo vệ dependency, nhưng session failure thường ảnh hưởng user trực tiếp. Khi planned maintenance, prewarm key quan trọng và rate limit traffic có thể giảm cold start. Không nên prewarm bằng cách crawl toàn catalog cùng lúc. Prefix hoặc database change cũng tạo cold start tương tự failover. Rollback config phải nhớ keyspace cũ có thể stale hoặc session đã diverge. Không chuyển qua lại nhiều lần mà không có plan. Read replica cho cache có thể giảm load, nhưng stale read và consistency phải theo adobe configuration. Session read từ replica có thể không thấy write mới nếu contract không đảm bảo. Health check chỉ ping không phát hiện command latency hoặc memory gần đầy. Synthetic check nên set, get và delete key riêng với ttl, nhưng không dùng key trùng application. Trong cloud, relationship, service version và support boundaries quyết định thao tác. Team không được chạy config nguy hiểm vì một blog chung. Rehearsal failover trên staging cần đo reconnect, error rate, session continuity và origin load. Sau failover, kiểm tra replica role, replication backlog và memory. Business phải biết logout ngắn hạn có chấp nhận không. Nếu không, architecture cần stronger session durability hoặc external strategy, không chỉ tăng retry. Failover test nên bao gồm request đang mở, request mới và worker giữ connection cũ. Một client pool không refresh topology có thể tiếp tục gửi traffic tới node không còn writable.
