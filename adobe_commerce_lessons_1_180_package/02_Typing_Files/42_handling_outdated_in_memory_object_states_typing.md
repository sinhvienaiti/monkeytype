Message queue consumer trong Adobe Commerce có thể sống lâu và xử lý nhiều message trong cùng một process. Khi process khởi động, framework tạo object và nạp configuration vào memory. Admin có thể thay configuration trong database sau đó, nhưng object đang tồn tại không tự được tạo lại. Vì vậy consumer xuất invoice sang erp có thể tiếp tục dùng profile, tax mapping hoặc retry policy cũ dù Admin đã hiển thị value mới. Đây là stale in memory object state, không nhất thiết là database sai. Http request truyền thống thường có lifecycle ngắn hơn, nên request mới có cơ hội bootstrap và đọc state mới. Consumer loop thì giữ shared service qua nhiều message. Restart process là boundary để object graph được tái tạo. Adobe cung cấp cơ chế poison pill trong message queue framework để đánh dấu rằng memory hiện tại đã cũ. Consumer kiểm tra version trước message tiếp theo, dừng có kiểm soát khi version thay đổi và chờ process manager khởi động instance mới với configuration mới. Việc nhận ra lifecycle này là bước đầu để debug đúng.

Cần phân biệt stale memory với nhiều loại dữ liệu cũ khác. Stale configuration cache làm cả request mới đọc value cũ cho tới khi cache được invalid. Stale full page cache làm storefront html cũ nhưng không liên quan trực tiếp consumer object. Database replica lag có thể khiến một node chưa thấy commit mới. Stale message nghĩa payload đã chứa snapshot cũ từ lúc publish, nên restart consumer cũng không đổi payload. Stale code xảy ra khi deploy xong nhưng long running process chưa restart. Mỗi loại cần một cách xử lý khác. Flush toàn bộ Redis không bảo đảm object trong process đổi, và còn gây tải lại hệ thống. Restart consumer không sửa message đã publish với mapping cũ. Quy trình debug nên hỏi database hiện có gì, request web mới đọc gì, consumer log đang dùng gì, process bắt đầu lúc nào và payload chứa snapshot hay identifier. Phân loại đúng giúp tránh dùng cache clean hoặc reindex như một phản xạ chung cho mọi triệu chứng dữ liệu cũ. Một bằng chứng nhỏ như process start time thường loại bỏ rất nhiều giả thuyết sai.

Poison pill có ba interface chính. Put interface có method ghi một version mới vào database. Read interface lấy latest version. Compare interface kiểm tra version baseline trong memory của consumer còn là latest hay không. Database version là nguồn chung cho nhiều node và nhiều consumer instance. Nó không phải business message trong topic invoice export. Khi consumer bắt đầu callback invoker, framework đọc latest version làm baseline. Trước khi xử lý một message mới, framework so baseline với database. Nếu giống nhau, callback tiếp tục. Nếu khác nhau, consumer biết object state của process có thể đã cũ. Cách dùng version đơn giản hơn việc phải broadcast một control message tới đúng mọi consumer. Nếu nhiều config save xảy ra gần nhau, consumer không cần xử lý từng version trung gian. Nó chỉ cần biết baseline không còn latest và process phải được tái tạo. Version signal không chứa configuration value, nên process mới vẫn phải đọc config và cache đúng. Baseline này cũng giúp log giải thích vì sao process thoát mà không coi đó là crash.

Theo flow Adobe mô tả, consumer dequeue message rồi compare poison pill version trước khi gọi business callback. Nếu version đã cũ, message vừa lấy được reject và process exit với code thành công. Message không nên bị mất chỉ vì process cần restart. Process manager hoặc consumers runner sẽ khởi động consumer mới, process mới đọc version và configuration mới rồi xử lý message. Boundary này nằm trước callback của message tiếp theo. Poison pill không undo message đã xử lý xong trước đó và không interrupt một callback đang chạy giữa chừng. Nếu callback kéo dài nhiều phút, configuration có thể đổi trong khi business operation đang thực hiện. Module cần policy rõ là hoàn thành message với snapshot lúc bắt đầu hay re read critical state tại safe checkpoint. Không nên đổi strategy giữa một transaction tùy tiện. Handler vẫn phải idempotent vì crash, network error hoặc acknowledge failure có thể làm broker redeliver message ngoài tình huống poison pill. Process manager cần hiểu exit này là tín hiệu recycle bình thường, không phải lỗi cần backoff dài.

Custom module nên gọi put khi một thay đổi làm long running consumer cần reload state đã snapshot. Ví dụ đổi erp profile active, mapping strategy, website tree hoặc credential được client object đọc khi khởi tạo. Không nên gọi put cho mỗi order, invoice hoặc entity save, vì consumer sẽ restart liên tục. Thứ tự rất quan trọng. Version bump phải xảy ra sau khi thay đổi đã persist thành công và cache lifecycle phù hợp được xử lý. Nếu bump trước commit, consumer có thể restart ngay, đọc database cũ rồi tiếp tục với một version đã được coi là mới. Nếu transaction rollback, version và business state càng lệch. Production implementation cần xem after commit boundary, không chỉ thứ tự dòng trong một method nếu resource dùng transaction bên ngoài. Audit log nên nối config change với version bump để incident có timeline rõ. Nếu save flow có nhiều entry point, tất cả cần dùng chung service để không bỏ sót signal.

Scope tree, store resolver và mapping theo website có thể đã được build trong memory. Consumer đa store cần nhận biết scope mới khi xử lý message.
