Extension attribute trong Adobe Commerce là cơ chế mở rộng một data interface đã có mà không sửa trực tiếp interface lõi. Điều quan trọng nhất là không nhầm contract với nơi lưu dữ liệu. Khai báo extension attribute tạo ra getter, setter và object mở rộng để entity có thể mang thêm dữ liệu qua service contract. Nó không tự tạo bảng, không tự load dữ liệu, không tự save và cũng không tự làm field xuất hiện đúng trong mọi api. Khi thiết kế một fulfillment profile cho sản phẩm, developer phải trả lời ba câu hỏi riêng. Dữ liệu nằm ở đâu và liên kết với product bằng khóa nào. Service contract biểu diễn dữ liệu bằng scalar, complex object hay array. Consumer nhận dữ liệu qua php, rest, soap hay graphql. Nếu chỉ giải quyết một lớp, hệ thống có thể compile thành công nhưng response luôn rỗng, hoặc api trả object trong memory nhưng database không hề thay đổi. Mô hình đúng là persistence cung cấp dữ liệu thật, repository gắn dữ liệu đó vào extension object, rồi transport serialize theo contract và authorization hiện tại. Cách phân lớp này giúp debug chính xác hơn vì mỗi triệu chứng được truy về đúng boundary thay vì kết luận chung rằng extension attribute không hoạt động.

Trước khi khai báo extension attribute, cần kiểm tra interface mục tiêu có hỗ trợ extensible data pattern hay không. Interface thường kế thừa extensible data interface và có hai method để lấy và đặt extension attributes. Không nên giả định mọi model đều có khả năng này, vì service contract và model concrete không phải cùng một khái niệm. Module bên ngoài không được thêm method trực tiếp vào interface lõi trong vendor, vì cách đó tạo thay đổi khó nâng cấp và có thể phá consumer khác. Sau khi xác định interface phù hợp, cần chọn code duy nhất và type ổn định. Scalar phù hợp cho integer, boolean hoặc string đơn giản. Complex interface phù hợp khi dữ liệu có nhiều field và cần contract rõ. Array có thể chứa scalar hoặc object, nhưng cần cân nhắc payload size và cách load danh sách. Thay đổi type sau khi release có thể là breaking change đối với php caller, generated client và api payload. Vì vậy, thiết kế extension attribute phải được review như public contract, không phải một field nội bộ có thể đổi tùy ý. Một quyết định nhỏ trong xml có thể trở thành dependency lâu dài của integration và module khác.

Tệp extension attributes xml chỉ mô tả interface nào được mở rộng, code của field và type dữ liệu. Sau khi metadata được merge, code generation tạo extension interface, implementation và factory tương ứng. Nếu production báo method mới không tồn tại trong khi local developer mode vẫn chạy, cần kiểm tra build pipeline thay vì sửa generated file bằng tay. Local có thể generate on demand, còn production thường phụ thuộc artifact đã compile. Các nguyên nhân phổ biến gồm xml trỏ sai interface, schema xml không hợp lệ, module chưa enable, generated code cũ hoặc dependency injection compilation chưa chạy lại. Generated code là kết quả của metadata, vì vậy sửa trực tiếp output chỉ che lỗi và sẽ bị ghi đè trong lần deploy sau. Quy trình tốt phải validate xml, compile trong chế độ gần production và chạy test contract trong ci. Git release cũng phải chứa đủ declaration, interface complex type, implementation, persistence và test. Nếu cherry pick chỉ lấy plugin nhưng bỏ xml hoặc data interface, branch có thể compile ở một môi trường đã có artifact cũ nhưng fail khi cài mới từ đầu.

Một extension object có thể là null nếu entity chưa khởi tạo nó. Plugin load dữ liệu mà gọi setter trực tiếp trên null sẽ gây lỗi. Pattern phổ biến là dùng after plugin trên method lấy extension attributes của entity cụ thể. Plugin trả object hiện có nếu đã tồn tại, hoặc dùng generated factory để tạo object mới khi result là null. Điểm quan trọng hơn là không bao giờ tạo object mới một cách mù quáng rồi replace object hiện tại. Nhiều module có thể cùng mở rộng product interface. Object hiện tại có thể đã chứa stock data, field của third party hoặc dữ liệu do plugin trước đó gắn vào. Nếu module fulfillment tạo object mới và chỉ set field của mình, các field khác có thể biến mất khỏi response. Quy tắc an toàn là lấy object hiện có, tạo mới chỉ khi thật sự null, set field mình sở hữu và gắn lại entity. Plugin cũng không nên được áp dụng quá rộng cho mọi extensible interface, vì generated extension type của từng entity khác nhau. Cần chọn đúng concrete class hoặc extension point và test khi nhiều module cùng hoạt động.

Để load một entity, Adobe minh họa after plugin trên repository get. Repository chính trả product, plugin lấy product id, gọi repository phụ để đọc fulfillment profile, sau đó gắn profile vào extension object. Cách này dễ hiểu nhưng vẫn cần policy khi dữ liệu phụ không tồn tại. Nếu profile là optional, có thể trả null hoặc object mặc định không persist. Nếu profile bắt buộc cho một product type, service có thể trả domain exception hoặc fallback an toàn. Không nên dùng exception kỹ thuật của database làm business response. Plugin cũng phải bảo toàn extension object hiện có và không mutate dữ liệu ngoài ownership. Khi debug field luôn null, cần kiểm tra repository method thực sự được gọi. Một số flow dùng get by id, get list hoặc data provider riêng, nên plugin trên một method không bao phủ toàn bộ hệ thống. Test php repository, rest single entity và admin flow riêng biệt. Việc một controller trực tiếp load model có dữ liệu không chứng minh service contract đã được populate. Extension attribute chỉ đáng tin khi mọi entry point đã được xác định rõ và dùng cùng một nguồn dữ liệu hợp lệ.

Load danh sách là nơi dễ xuất hiện lỗi n cộng một query. Một implementation đơn giản lấy product list rồi gọi repository profile cho từng product. Nếu page có nhiều sản phẩm, số query tăng tuyến tính và api chậm theo page size. Cách tốt hơn là thu thập toàn bộ product id, gọi một query lấy profile theo danh sách id, lập map theo product id rồi gắn dữ liệu trong memory. Nếu profile có danh sách source code ở bảng con, có thể cần thêm một batch query thứ hai thay vì query cho từng profile. Batch loader phải xử lý empty list, duplicate id, missing profile và giới hạn số parameter của database. Cũng cần đo memory khi complex object lớn. Page size nhỏ trên local không đại diện cho integration dùng page size lớn. Query profiler hoặc New Relic có thể cho thấy cùng một statement lặp theo entity id. Khi GraphQL resolver trả field cho nhiều product, nguyên tắc batching vẫn giống repository get list. Resolver từng leaf gọi service riêng sẽ tạo cùng vấn đề n cộng một query ở một transport khác. Developer cấp expert phải nhận ra pattern chứ không chỉ sửa một endpoint cụ thể.

Join trong extension attributes xml có thể thêm field từ bảng ngoài vào collection và hỗ trợ filter. Tuy nhiên, join không tự triển khai save, validation, transaction hay GraphQL. Join phù hợp khi quan hệ có cardinality rõ và field cần tham gia search. Nếu join một bảng có column trùng tên với main table, filter như created at có thể bị ambiguous. Search request hoặc collection processor cần qualify field đúng. Nếu join quan hệ một nhiều như danh sách source code, mỗi product có thể xuất hiện nhiều row, làm total count sai, pagination sai và entity lặp. Khi đó batch loading hoặc aggregate query an toàn hơn. Không nên self join bảng entity chỉ để expose một field đã có sẵn, vì cách đó tăng độ phức tạp mà không tạo giá trị. Trước khi chọn join, cần xác định mục tiêu là filter, sort hay chỉ enrich response. Nếu chỉ enrich data sau khi collection đã được phân trang, batch loader thường đơn giản và ít ảnh hưởng count hơn. Nếu cần filter thật, cần thiết kế index, alias field và cardinality từ đầu, đồng thời test query sql thực tế.

Khai báo extension attribute không làm dữ liệu tự persist khi repository save. Module phải lấy extension object từ input entity, validate profile và ghi vào bảng mình sở hữu. Adobe có ví dụ after save plugin, trong đó product được save trước rồi dữ liệu phụ được lưu. Pattern này có thể phù hợp nếu profile là dữ liệu phụ và business chấp nhận xử lý lỗi riêng. Nhưng nếu product save thành công còn profile save thất bại, hệ thống rơi vào trạng thái không đồng nhất. Caller có thể nhận exception trong khi product name đã thay đổi. Retry có thể save product lần nữa. Nếu profile là điều kiện bắt buộc để fulfillment đúng, cần transaction boundary mạnh hơn, chẳng hạn domain service phối hợp cả hai repository hoặc implementation sở hữu transaction rõ. Không nên bọc around plugin và giả định nested transaction sẽ làm mọi thứ atomic, vì repository lõi có thể commit ở boundary khác. Trước khi chọn pattern, cần xác định business invariant, thứ tự commit, retry policy và forward recovery. Atomic, eventual consistency và best effort là ba lựa chọn khác nhau, không phải các tên gọi có thể dùng thay thế.

Save logic phải có tính idempotent. Khi cùng payload được gửi lại do timeout hoặc retry, bảng profile không được tạo duplicate và bảng source link không được nhân bản. Upsert theo product id, unique constraint và replace strategy có kiểm soát thường an toàn hơn insert mù quáng. Validation cần chia thành shape, reference và state. Lead time phải là số không âm. Handling group phải thuộc tập cho phép. Source code phải tồn tại và product hoặc business unit phải có quyền dùng source đó. Product đang trong workflow khóa có thể không được chỉnh profile. Validation không nên chỉ nằm ở admin form, vì rest, import, queue consumer và php caller có thể bỏ qua ui. Domain service dùng chung phải bảo vệ invariant. Khi response save trả đúng object input, vẫn chưa chứng minh database đã persist. Integration test phải reload bằng repository mới hoặc query xác minh. Test cũng cần mô phỏng child save fail để xem main entity có bị thay đổi ngoài mong muốn hay không. Constraint ở database và log idempotency giúp chứng minh retry không tạo side effect mới.

Entity Manager extension actions là một extension point khác được Adobe nhắc tới. Cách này đưa extension lifecycle gần operation của entity hơn và có thể giảm số plugin repository rời rạc. Tuy nhiên, không phải mọi entity dùng Entity Manager giống nhau. Developer phải đọc source implementation của entity đang mở rộng, xác định operation pipeline và action name thực tế. Cấu hình sai có thể không chạy mà khó nhận biết nếu chỉ test một flow. Extension action không nên được chọn chỉ vì nghe có vẻ sạch hơn plugin. Nó phù hợp khi lifecycle entity và operation pipeline rõ ràng, đội hiểu cách debug và transaction behavior đáp ứng yêu cầu. Nếu entity hiện tại có repository custom không dùng pipeline đó, plugin hoặc domain service có thể dễ kiểm soát hơn. Expert decision phải dựa trên source thật, không dựa trên pattern được dùng ở một entity khác rồi áp dụng máy móc. Trước khi chọn, cần đọc source và viết integration test cho operation thật.

REST và SOAP có thể serialize extension attributes khi service contract trả extensible data object. Payload thường có một phần extension attributes chứa scalar hoặc complex object. Một điểm quan trọng trong tài liệu Adobe là một số search api không trả detailed attributes đầy đủ như endpoint single entity, dù generated documentation có thể khiến developer hiểu ngược lại. Nếu field biến mất với một role nhưng php object đã có dữ liệu, hãy kiểm tra resource filtering trước khi bỏ permission. Việc xóa ACL để làm test chạy có thể tạo lỗ hổng production. Custom attribute và extension attribute cũng không dùng chung mọi cơ chế field restriction, nên không nên áp một kết luận cho cả hai loại dữ liệu.

GraphQL không nên được suy luận từ REST. PHP extension attribute declaration không tự bảo đảm storefront GraphQL có field tương ứng. Module cần extend schema, định nghĩa type và cung cấp resolver. Multiple modules cùng mở rộng một interface là tình huống bình thường. Các declaration được merge và generated extension interface chứa nhiều field. Concurrency cần được phân tích khi nhiều admin hoặc integration cùng chỉnh profile. Nếu hai người load cùng version, người thứ nhất sửa lead time, người thứ hai sửa handling group rồi save object cũ, last write wins có thể làm mất thay đổi đầu tiên. Repository save không tự hiểu merge nghiệp vụ. Có thể dùng version field, updated timestamp check hoặc compare and swap để phát hiện stale write. Khi conflict, service trả domain error và yêu cầu reload thay vì im lặng ghi đè. Unique constraint bảo vệ một profile cho mỗi product, nhưng không ngăn lost update. Với danh sách source code, replace toàn bộ list dễ ghi đè thay đổi đồng thời hơn add hoặc remove command có version. Lựa chọn phụ thuộc workflow. Nếu profile được chỉnh hiếm và chỉ một role thao tác, optimistic concurrency có thể đủ. Nếu integration ERP cập nhật liên tục, cần idempotency key, source ownership và reconciliation. Cấp expert phải phân biệt duplicate creation, lost update và stale read, vì mỗi lỗi cần constraint hoặc strategy khác nhau.

Performance review phải đo cả read, write và serialization. Single entity thêm một query có thể chấp nhận, nhưng product list thêm một query cho mỗi item thì không. Log nên ghi entity id, operation và kết quả kỹ thuật, nhưng không ghi dữ liệu nhạy cảm. Query profiler giúp phát hiện n cộng một. Integration test giúp phân biệt lỗi metadata với lỗi persistence. Đi theo boundary làm giảm việc xóa cache, compile lại hoặc sửa plugin ngẫu nhiên mà không có bằng chứng. Mỗi bước nên ghi lại bằng chứng để người khác có thể lặp lại kết luận.

Một tình huống điển hình là product search endpoint chậm sau khi thêm profile. Query trace cho thấy một statement lặp lại theo product id. Nguyên nhân là after get list gọi repository phụ trong vòng lặp. Cách sửa là batch load và map kết quả. Tình huống khác là stock data biến mất sau release. Plugin fulfillment đã tạo product extension object mới, vô tình xóa field module inventory. Cách sửa là merge vào object hiện có. Một trường hợp khó hơn là product save báo lỗi, nhưng name đã đổi còn profile chưa đổi. Main repository đã commit trước khi after plugin save child thất bại. Đội phải quyết định forward fix, domain transaction hoặc eventual consistency, không thể chỉ retry mù quáng. Nếu rest get đúng còn search thiếu, cần kiểm tra get list và detailed response. Nếu GraphQL category chậm theo số product, cần batch resolver. Nếu pagination lặp product, join một nhiều đã làm nhân row. Các tình huống này cho thấy cùng một extension attribute chạm contract, database, api, performance và transaction. Sau khi sửa, cần đo lại cùng page size và cùng context để xác nhận nguyên nhân gốc.

Testing cần bao phủ fresh install, production compilation và nhiều entry point. Unit test xác nhận ensure extension object giữ nguyên object có sẵn và tạo mới khi null. Batch loader map đúng id, xử lý empty list và missing profile. Integration test gọi repository get, get list, save rồi reload từ database. Test query count hoặc profiler assertion giúp ngăn n cộng một quay lại. Api functional test kiểm tra rest single, rest search, role có quyền, role không quyền và payload invalid. GraphQL test kiểm tra schema, batch behavior, store context và authorization. Concurrency test mô phỏng hai update cùng version nếu business cần. Failure test ép repository phụ throw exception để quan sát trạng thái main entity. Deployment test compile từ artifact sạch thay vì dựa generated code cũ. Khi schema của bảng profile thay đổi, migration test phải nâng từ version trước. Một bộ test chỉ gọi getter trên object mock không chứng minh solution hoạt động xuyên suốt từ storage tới api. Test trên dữ liệu gần production giúp phát hiện giới hạn mà fixture nhỏ không thể hiện.

Khi review solution, hãy bắt đầu bằng business invariant. Fulfillment profile có optional không, ai được sửa, checkout có phụ thuộc không và dữ liệu cần consistent đến mức nào. Sau đó kiểm tra contract có type ổn định, persistence owner rõ và source table có constraint phù hợp. Review load single và list, đặc biệt query count. Review save, transaction, retry, concurrency và response reload. Kiểm tra rest, graphql và permission riêng. Kiểm tra nhiều module cùng mở rộng product interface và build production từ sạch. Cuối cùng nối release với Git và system. Pull request phải chứa xml, generated contract source, table declaration, repository, plugin hoặc extension action, test và hướng deploy. Revert code không tự revert dữ liệu profile. Monitoring phải cho thấy latency và error sau rollout. Một extension attribute đạt mức expert không chỉ xuất hiện trong payload, mà phải đúng contract, đúng dữ liệu, đúng quyền, có hiệu năng ổn định và có thể debug khi nhiều layer cùng tham gia. Checklist này nên trở thành tiêu chí bắt buộc trong pull request và release note.
