Service contract là ranh giới ổn định giữa module sở hữu nghiệp vụ và các consumer. Trong adobe commerce, interface dưới api và data interface dưới api data thường được coi là public contract, nhưng vị trí file không tự bảo đảm thiết kế tốt. Một contract tốt dùng vocabulary nghiệp vụ, che persistence và không trả model concrete, collection hoặc resource connection. Hãy bắt đầu từ use case. Ví dụ approve request cần request id, actor, policy và outcome rõ. Repository có thể load và save aggregate, còn approve service điều phối transition, authorization, transaction và event. Nếu nhét approve vào repository chỉ vì repository đã có entity, persistence abstraction trở thành service khổng lồ. Nếu caller lấy model rồi tự set status và save, invariant bị phân tán. Data interface chỉ mang dữ liệu cần qua boundary. Nó không nên lazy load theo session hoặc chứa behavior phụ thuộc infrastructure. Error contract cũng quan trọng. Consumer cần phân biệt not found, invalid input, forbidden và conflict state thay vì nhận raw database exception. Public method signature ổn nhưng đổi meaning, exception hoặc serialization vẫn là breaking change. Vì vậy compatibility review phải xét behavior, không chỉ php compile. Contract owner cần biết consumer nào gọi qua rest, graphql, cron, queue hoặc module php. Mỗi context có transaction và authorization khác. Một boundary tốt cho phép implementation thay đổi bằng dependency injection mà consumer không biết storage hoặc framework internals. Nó cũng tạo chỗ viết contract test chạy với implementation thật và implementation thay thế. Trong architecture review, hãy vẽ consumer trực tiếp của contract và consumer gián tiếp qua web api. Một field tưởng private có thể đã được mobile app dùng. Migration plan nên có adapter, deprecation log và usage metric để biết khi nào bỏ endpoint cũ. Public boundary chỉ đáng tin khi thay đổi được phát hiện trước production.

Repository pattern thường bị lạm dụng thành cổng gọi mọi thứ. Repository phù hợp get, save, delete và get list của aggregate theo data contract. Business command như cancel, approve, recalculate hoặc assign thường có invariant và side effect riêng, nên đặt ở management hoặc application service. Search criteria giúp consumer filter, sort và paging mà không phụ thuộc collection concrete, nhưng generic query cũng cần guardrail. Không nên mở mọi field private hoặc cho phép page size vô hạn. Field mapping, store scope, authorization và default sort phải rõ. Khi get list trả extension attribute, implementation cần batch hydrate. Plugin load từng attribute theo từng entity tạo query n cộng một và biến contract hợp lệ thành performance failure. Performance là một phần compatibility vì consumer có thể đang dùng list hàng nghìn item. Data interface không tự persistence. Extension attribute declaration chỉ mở rộng contract; repository hoặc extension code phải populate và save. Khi thêm attribute mới, hãy kiểm tra rest serialization, graphql resolver, list performance và partial data. Không nên thêm method trực tiếp vào public interface chỉ để một extension dùng, vì mọi custom implementation phải cập nhật. Một interface bổ sung nhỏ hoặc extension attribute có thể an toàn hơn. Review repository phải xem transaction. Gọi save ba lần không tự tạo atomic use case. Application service phải quản transaction local hoặc dùng resource transaction đúng. Đồng thời không nên giữ transaction mở khi gọi network dài, vì lock duration tăng và rollback không hoàn tác external side effect. Batch repository cũng cần xác định consistency. Nếu list được đọc trong lúc data thay đổi, paging theo offset có thể bỏ hoặc lặp row. Stable sort và cursor phù hợp hơn cho export lớn. Contract phải nói snapshot có được hứa không. Domain boundary xác định ownership và invariant, không nhất thiết trùng database table. Company credit có thể đọc order và payment data nhưng rule cấp hạn mức thuộc một owner. Module khác nên gọi service để yêu cầu reserve hoặc release credit, không update table trực tiếp. Nếu integration external dùng vocabulary khác, anti corruption layer chuyển request và response sang model nội bộ. Domain code không nên phụ thuộc array vendor, status code http hoặc client concrete. Adapter map timeout, authentication và error thành port nội bộ. Điều này giúp thay endpoint mà không đổi rule. Service layer điều phối use case, còn domain object hoặc policy giữ invariant có thể test độc lập. Không dồn mọi rule vào service thủ tục dài. Authorization cần đặt theo context. Một repository được dùng trong cron không thể luôn dựa vào current customer session. Application boundary có thể nhận actor id hoặc security context rõ. Web api resource mapping vẫn cần service kiểm tra business scope nếu caller có quyền tổng quát nhưng entity thuộc tenant khác. Validation cũng có tầng. Format email là input validation, transition từ approved về pending là domain validation, unique database constraint là guard cuối. Cùng một service nên được reuse bởi admin, api và queue để tránh rule lệch. Khi asynchronous command đi qua queue, response không còn đồng bộ; service có thể tạo operation record và event. Contract phải mô tả eventual outcome, idempotency và error visibility. Không dùng event để thay mọi request response chỉ vì muốn giảm dependency. Domain service không nên nhận object manager, request global hoặc session chỉ để lấy context. Dependency rõ giúp cli, queue và test dùng cùng rule. Policy object có thể nhận actor và aggregate để quyết định. Khi một rule cần data từ boundary khác, gọi port hoặc read model được sở hữu, không join trực tiếp table private rồi biến schema thành dependency ngầm.

Backward compatibility của service contract rộng hơn version number. Đổi parameter order, type, return data, exception hoặc nullability đều có thể phá consumer. Thêm method vào interface cũng phá class tùy chỉnh implement interface đó. Đổi default filter hoặc sort có thể phá integration dù signature giữ nguyên. Đổi extension attribute từ absent sang empty hoặc đổi field meaning ảnh hưởng serialized payload. Review cần inventory consumer, deprecation window và migration note. Ký hiệu api tạo kỳ vọng ổn định; private implementation vẫn có thể bị extension dùng trái phép nhưng không nên vì thế biến tất cả thành public. Khi cần thay contract lớn, tạo interface mới, adapter từ cũ sang mới và deprecate theo release. Contract test nên chạy cùng fixture và assert cả success, validation, authorization, conflict cùng performance budget. Một consumer driven test có thể phát hiện field bị mất hoặc exception đổi. Semantic version chỉ có ý nghĩa khi policy được tuân thủ. Trong module composer riêng, constraint giúp solver nhưng không chứng minh runtime compatibility. Release review cần source diff, api diff và integration test. Đừng dùng preference toàn cục để thay service implementation mà không kiểm tra mọi caller. Decorator hoặc plugin có phạm vi có thể thêm behavior, nhưng vẫn phải giữ postcondition và exception contract. Nếu implementation mới gọi service cũ và tạo recursion, dependency graph phải được kiểm tra. Boundary tốt cho phép thay storage từ table cũ sang projection mới trong khi consumer không đổi. Compatibility gate nên so cả api schema và behavior fixture. Một change có thể giữ field nhưng đổi unit, timezone hoặc scope. Hãy lưu example request và expected response cho các consumer quan trọng. Khi deprecate, log caller an toàn và đặt deadline. Không xóa contract chỉ vì code search nội bộ không thấy, vì external consumer không nằm trong repository.

Transaction boundary là nơi service contract gặp distributed system. Một approve operation có thể update request, reserve credit, ghi audit và publish event. Các mutation local cần atomic trong một transaction nếu invariant yêu cầu. Publish trực tiếp tới broker trong transaction database tạo dual write: database có thể commit nhưng publish fail hoặc ngược lại. Transactional outbox lưu event cùng transaction rồi relay sau. Consumer event phải idempotent. Nếu service gọi payment hoặc erp, không giữ database lock suốt network call. Dùng state machine như pending, processing, confirmed, failed hoặc unknown. Unknown cần reconciliation vì timeout không chứng minh external operation thất bại. Error contract phải biểu diễn outcome chưa rõ thay vì trả generic failure rồi caller retry mù. Repository save không nên tự publish hidden side effect nếu consumer không biết, vì transaction ordering và test khó. Domain event có thể được thu thập rồi dispatch sau commit. Observer chạy đồng bộ trong cùng request có failure semantics khác queue event. Contract documentation cần nói operation synchronous hay asynchronous, idempotency key, retry policy và consistency window. Batch service cũng cần partial failure contract. Trả boolean cho một trăm item không cho biết item nào thất bại. Result object có success, error code và retryability giúp caller quyết định. Mục tiêu không phải làm mọi thứ atomic toàn cầu, mà làm local invariant chắc và distributed outcome có thể phục hồi. Outbox event từ service cần được tạo từ state đã commit hoặc cùng local transaction, không phát fact trước khi invariant chắc. Nếu operation async, result contract nên trả operation id và cách query status. Caller không được hiểu accepted là completed. Một timeout khi query status cũng không nên làm command được gửi lại bằng identity mới. Khi local transaction thất bại, outbox record cũng phải rollback. Khi commit thành công, relay có thể publish nhiều lần và consumer chịu duplicate. Contract của service nên nói fact nào được phát sau success và operation status nào caller có thể query.
