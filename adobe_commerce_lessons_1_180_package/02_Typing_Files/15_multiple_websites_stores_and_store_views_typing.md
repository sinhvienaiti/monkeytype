Một Adobe Commerce instance có thể vận hành nhiều website, store và store view từ cùng codebase cùng Admin. Ba tầng không chỉ là cách nhóm màn hình quản trị. Chúng tạo ranh giới khác nhau cho checkout, catalog structure, language, configuration và business policy. Website là container cấp cao. Store nằm trong website và gắn với root category. Store view nằm trong store và thường dùng cho localization hoặc presentation. Thiết kế đúng phải bắt đầu từ business boundary. Hai domain không tự động có nghĩa cần hai website, nhưng hai brand có payment, shipping, customer account và checkout độc lập thường nên được tách thành website riêng.

Website phù hợp khi cần domain hoặc brand độc lập, checkout riêng, payment và delivery policy khác, customer account boundary khác hoặc catalog price theo website. Customer account có thể được chia sẻ toàn cục hoặc theo website, nên quyết định này phải được đưa ra trước khi có dữ liệu thật. Nếu account không chia sẻ, cùng một email có thể tồn tại theo rule của từng website. Website không chỉ là một URL. Nó là scope cho nhiều cấu hình sales, customer, tax và currency. Dùng một website cho hai legal entity cần checkout độc lập sẽ làm configuration và data ownership khó kiểm soát.

Store nằm trong website và chủ yếu xác định catalog tree thông qua root category. Nhiều store trong cùng website có thể dùng root category khác nhưng vẫn chia sẻ website checkout boundary. Store phù hợp khi cùng business và checkout nhưng cần main navigation hoặc product assortment khác. Nếu chỉ cần dịch ngôn ngữ hoặc đổi label, store view thường đủ. Tạo store riêng cho mỗi language làm hierarchy, category và index phức tạp hơn mà không tạo giá trị business. Product có thể được assign vào category thuộc nhiều root tree, nhưng vẫn phải có website assignment phù hợp.

Store view là tầng presentation thường dùng cho language, locale, theme, CMS content, product name và description theo scope. Store view không tạo payment hoặc checkout độc lập. Name của store view là label hiển thị, còn code là identifier kỹ thuật có thể được dùng trong web server, environment config và integration. Đổi name thường ít rủi ro. Đổi code cần inventory mọi nơi tham chiếu. Disable store view cũng cần redirect, canonical, sitemap và customer bookmark plan. Không nên chỉ tắt rồi để URL cũ trả lỗi.

Scope xác định nơi configuration hoặc data value có hiệu lực. Global áp dụng toàn instance. Website áp dụng cho website hiện tại. Store quan trọng với root category và catalog structure. Store view áp dụng cho presentation cụ thể. Mỗi field có scope riêng do module khai báo, nên không được giả định mọi setting đều override ở store view. Configuration fallback xảy ra khi child scope không có value riêng. Commerce đọc parent hoặc default value. Một record rỗng có thể khác với không có record. Environment variable hoặc locked configuration cũng có thể thắng database value. Debug phải xác định store runtime, field scope, database row, config cache và environment override.

Giả sử doanh nghiệp có brand Alpha và Beta. Mỗi brand có domain, checkout, payment, shipping và customer account riêng. Mỗi brand có tiếng Việt và tiếng Anh. Thiết kế phù hợp là hai website, mỗi website có một store và hai store view. Website tách business boundary. Store giữ root category của brand. Store view xử lý language. Thiết kế một website với bốn store view không thể hiện đúng checkout và customer isolation. Ngược lại, nếu hai language dùng cùng brand và checkout, tạo hai website chỉ vì ngôn ngữ là over design.

Product entity được dùng chung trong instance nhưng có website assignment và attribute value theo scope. SKU thường global. Name hoặc description có thể khác theo store view. Một số price data có website scope tùy configuration. Product nằm trong category nhưng chưa assign website vẫn có thể không bán được tại website đó. Integration cần truyền store code hoặc scope phù hợp để đọc localized value. Global attribute thay đổi ảnh hưởng mọi website. Multisite giúp quản trị tập trung nhưng yêu cầu hiểu field nào global, website hay store view.

Inventory không được quản lý theo store view. Với Multi Source Inventory, stock, source và sales channel xác định availability. Store view ngôn ngữ không nên tạo inventory pool riêng. Cart, session và checkout chủ yếu theo website boundary. Khi switch store hoặc store view, cần kiểm tra product assignment, currency, URL rewrite, session cookie và customer sharing. Cookie domain hoặc path sai có thể làm mất login, mất cart hoặc tạo collision giữa subdomain. Những vấn đề này không được giải quyết chỉ bằng Admin hierarchy.

Request cần được bootstrap vào đúng website hoặc store view. Run type cho biết chạy website hay store, còn run code là identifier tương ứng. Nginx, Apache hoặc cloud route map hostname hay path tới hai giá trị này. Base URL phải được set đúng scope. Sai mapping có thể làm domain Alpha hiện content Beta, redirect loop hoặc static asset dùng domain khác. Unique domain cần DNS, TLS và CDN configuration. Shared domain theo path cần rewrite chính xác. URL strategy nên được quyết định trước launch vì thay đổi sau đó liên quan redirect, canonical, sitemap, cookie và analytics.

Trên Adobe Commerce on cloud infrastructure, multisite còn cần route configuration, domain setup, Fastly, base URL và variable mapping theo cloud guide. Không copy nguyên local virtual host vào cloud mà bỏ qua route architecture. Adobe cảnh báo catalog data tăng khi có nhiều website và store, làm indexing lâu hơn và non cached page chậm hơn. Mỗi scope mới có thể tăng product value, price dimension, URL rewrite, search index và permission data. Trước khi tạo store view mới, cần đánh giá business value, index size, deployment time và cache warm.

Custom code phải tránh hard coded store id. Identifier có thể khác giữa local, staging và production. Cron không có storefront request context, nên service cần nhận store hoặc website rõ khi đọc config, render email, tạo URL hoặc load localized product. Queue message nên mang scope identifier thay vì dựa vào current store ngầm định. Store emulation phải được dừng bằng finally để context không rò sang item tiếp theo. Custom cache key cần chứa store hoặc website dimension nếu output thay đổi theo scope, nhưng không nên thêm dimension không cần thiết làm cache fragmentation.

Debug multisite bắt đầu từ hostname, route, run type, run code và base URL. Sau đó kiểm tra store, root category, product website assignment, attribute scope, config fallback, cache và index. Nếu cron gửi email sai language, kiểm tra store id trong job và emulation. Nếu price hoặc content lẫn giữa brand, kiểm tra custom cache key và website context. Nếu indexer chậm sau khi thêm store view, đo URL rewrite, search data và store scoped attribute. Multisite không chỉ là cấu hình Admin. Nó là kiến trúc xuyên qua web server, cache, indexer, integration, cron và dữ liệu.

Best practice là dùng website cho business boundary, store cho root category và store view cho language hoặc presentation. Quyết định customer sharing, domain, catalog, price, currency, tax, payment và shipping trước khi tạo hierarchy. Không hard code store id. Truyền scope rõ trong service, cron, queue và api. Test guest, logged in, cart, checkout, REST, GraphQL, email và redirect ở mọi website. Monitor indexing cùng non cached latency khi tăng scope. Một hierarchy đơn giản nhưng đúng business thường tốt hơn nhiều store view được tạo chỉ vì tiện cấu hình ngắn hạn.
