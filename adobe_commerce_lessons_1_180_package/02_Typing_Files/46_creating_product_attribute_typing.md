Product attribute trong Adobe Commerce là một quyết định data model, không chỉ là thêm field vào Admin. Eav attribute phù hợp khi dữ liệu thuộc product, có value đơn giản hoặc option, cần quản lý theo attribute set, scope, import, search hoặc rule. Dữ liệu có nhiều record, history, permission hoặc lifecycle riêng thường phù hợp bảng riêng hơn. Ví dụ chu kỳ hiệu chuẩn là một số nguyên gắn với thiết bị, nên có thể là product attribute. Lịch sử nhiều lần hiệu chuẩn lại nên là bảng riêng vì mỗi product có nhiều record và audit riêng. Attribute code trở thành contract lâu dài trong database metadata, csv import, rest payload, graphql metadata, search index và integration. Rename code không phải thay label mà là migration. Custom attribute là subset của eav attribute do merchant hoặc module thêm, khác với built in attributes như name, price hoặc status. User defined thường nên bật cho attribute tùy chỉnh. Không nên giả system attribute chỉ để field trông giống core, vì ownership và upgrade expectation khác nhau.  Quyết định này còn ảnh hưởng search engine, cache, deployment và khả năng nâng cấp, nên cần được ghi trong tài liệu thiết kế chứ không chỉ nằm trong một data patch.

Backend type quyết định family storage. Varchar phù hợp chuỗi ngắn, int phù hợp số nguyên, boolean hoặc option id, decimal phù hợp số thập phân, text phù hợp nội dung dài hoặc multiselect, datetime phù hợp ngày giờ. Static cần cột trong entity table và không phải tối ưu mặc định cho custom attribute. Frontend input quyết định control trong Admin như text, textarea, select, multiselect, boolean hoặc date. Type và input phải tương thích. Select thường lưu option id, boolean lưu số, multiselect lưu danh sách option và cần backend model phù hợp. Chọn varchar cho số có thể làm sorting theo chuỗi và range filter sai semantics. Đổi type sau production là migration rủi ro vì value cũ và search mapping có thể không tương thích. Source model cung cấp options, backend model xử lý validation hoặc serialization, frontend model liên quan rendering ở một số context. Không trộn trách nhiệm bằng cách cho source model save data hoặc backend model gọi external service trong product save.  Nếu business chưa chắc value tương lai là số nguyên hay decimal, cần làm rõ domain trước khi release. Một lựa chọn storage vội vàng sẽ tạo migration tốn kém hơn nhiều so với thêm vài ngày phân tích ban đầu.

Scope global dùng một value toàn hệ thống, phù hợp dữ liệu kỹ thuật như chu kỳ hiệu chuẩn. Website scope cho phép khác giữa websites khi business thật sự cần. Store view scope phù hợp content hoặc localization. Scope không phải visibility. Một attribute có global scope vẫn có thể ẩn khỏi storefront, còn visible attribute có thể store scope. Đổi scope sau production cần policy cho value cũ và overrides. Global sang store có thể dùng default value làm fallback hoặc copy ra từng store, nhưng hai lựa chọn có semantics khác. Store sang global cần quyết định chọn value nào và xử lý conflicts. Integration phải gửi store code đúng. Import ở default scope có thể vô tình ghi đè expectation của store override. Search index và cache cũng cần rebuild hoặc invalidation. Không chỉ update metadata rồi xem task hoàn thành. Multi store test phải đọc và save ở nhiều store view, không chỉ default scope.  Khi scope website được chọn, test phải bao phủ nhiều websites có store views khác nhau và xác nhận fallback đúng. Không nên dùng website scope chỉ vì muốn merchant nhìn thấy thêm tùy chọn trong Admin.

Adobe Commerce dùng data patch để tạo product attribute bằng code. Patch implement data patch interface, dùng module data setup và eav setup để add attribute. Framework ghi patch đã apply trong bảng patch list và không chạy lại chỉ vì developer sửa method apply. Vì vậy patch class và namespace là migration identity. Sau khi patch đã chạy trên staging hoặc production, mọi thay đổi phải đi bằng patch mới. Sửa patch cũ tạo drift, vì fresh install nhận metadata mới còn environment cũ giữ metadata cũ dù cùng commit. Dependencies cần khai báo khi patch dựa vào attribute set hoặc dữ liệu do patch khác tạo. Alias cần dùng nếu class buộc phải rename để framework nhận identity cũ. Setup upgrade phải chạy trong deployment pipeline có một migration writer, không để mọi node tự chạy patch khi start. Backfill hàng triệu products không nên nhồi vào attribute creation patch. Tách batch migration có progress, retry và observability.  Pipeline cũng cần so sánh fresh install với upgrade database cũ để chắc chắn cả hai tạo cùng metadata. Đây là cách phát hiện drift do patch bị sửa hoặc dependency chưa khai báo.

Required, default, unique và apply to đều có hậu quả production. Required attribute mới có thể làm product cũ không save vì chưa có value. Hướng an toàn là tạo optional, backfill, validate rồi mới tăng business validation trong patch sau. Default metadata không nhất thiết tạo row value cho mọi product cũ. Code phải hiểu fallback. Unique attribute tạo validation cost và race khi nhiều import process chạy. Nó không thay database table với unique constraint mạnh cho business entity phức tạp. Apply to giới hạn product types. Chu kỳ hiệu chuẩn có thể chỉ phù hợp simple và virtual, trong khi bundle hoặc gift card không có nghĩa. Visible điều khiển Admin metadata, visible on front liên quan một số frontend rendering nhưng không làm headless storefront tự thấy field. Used in product listing làm attribute được load rộng hơn, vì vậy chỉ bật khi category hoặc product list thật sự cần.  Những flags này còn ảnh hưởng product form metadata và integration expectations. Mỗi option trong patch nên có lý do business hoặc comment thiết kế, thay vì copy nguyên một array từ blog hoặc module khác.

Searchable, filterable, filterable in search, comparable, used for sort và used for promo rules cần use case rõ. Bật mọi flag không làm attribute hữu ích hơn, nó làm index và collection nặng hơn. Attribute có hàng chục nghìn unique values không phù hợp layered navigation vì facet lớn và ux tệ. Backend type và input ảnh hưởng search mapping. Đổi text sang numeric hoặc thay filterability có thể cần reindex và index recreation tùy engine. Select, multiselect, boolean và price có behavior filter khác nhau. Sort theo option label, text hoặc number có semantics khác. Promotion rule dùng attribute làm condition khiến value change liên quan rule evaluation. Search weight chỉ có ý nghĩa khi field searchable và business đã đo relevance. Trước production, staging cần đo index size, reindex time, query latency và facet response. Không quyết định bằng catalog nhỏ trên local.  Nếu merchant có quyền tự quản lý attribute sets, module cần tài liệu hoặc automation rõ để attribute không biến mất trên product mới. Một cron sửa sets liên tục thường không phải giải pháp tốt vì có thể chống lại quyết định quản trị hợp lệ.

Attribute set và group quyết định product form organization. Catalog thực tế có thể có nhiều sets do merchant tạo. Patch chỉ gán attribute vào default set làm field không xuất hiện cho products thuộc set khác. Team phải chọn gán vào set module sở hữu, mọi set hiện có hoặc để merchant gán thủ công. Gán mọi existing set không xử lý set được tạo sau. Cần process rõ cho future sets. Group name có thể bị merchant rename, nên deterministic setup có thể dùng group id hoặc module owned group. Attribute metadata tồn tại nhưng không có trong set vẫn có thể được api xử lý theo một số flow, khiến Admin và integration nhìn khác nhau. Debug field không hiện cần kiểm tra set, group, visible, apply to và ui modifier. Không chỉ clean cache. Attribute assignment là business presentation contract và phải được test trên từng product type quan trọng.  Khi options đến từ hệ thống ngoài, đồng bộ cần giữ mapping table và xử lý rename, disable, merge hoặc split option. Xóa rồi tạo lại làm option id đổi và phá product values đang tham chiếu.

Select và multiselect lưu option id, không nên coi label là storage identity. Option id khác giữa local, staging và production vì database sequence khác. Integration hard code id sẽ gửi sai value. Cần stable business code và mapping, hoặc resolve metadata theo environment. Label có thể dịch theo store và bị rename. Hai options có label giống nhau gây ambiguity trong import. Xóa option khi products còn lưu id tạo orphan semantic. Cần migrate product values, rule conditions và integrations trước. Multiselect thường lưu chuỗi option ids, nên direct sql like query dễ match sai. Nếu business cần relation query mạnh, ordering, metadata riêng hoặc nhiều records, bảng many to many có thể tốt hơn multiselect. Backend array model xử lý ui value, nhưng không biến storage thành relational model. Source model cũng không nên gọi dịch vụ chậm mỗi lần product form load.  Validation error cần chỉ ra attribute code, sku, scope và value đã được làm sạch để đội vận hành sửa dữ liệu. Không log toàn payload nếu import chứa thông tin nội bộ hoặc dữ liệu từ partner.

Validation phải có ở server. Frontend class trong Admin chỉ giúp feedback nhanh và có thể bị bỏ qua bởi rest, graphql, import hoặc code nội bộ. Chu kỳ hiệu chuẩn cần integer dương, range hợp lý và có thể chỉ áp dụng cho một số product types. Conditional required không nên được biểu diễn bằng metadata required cho toàn entity nếu chỉ một category cần. Service hoặc validation component phải giữ invariant. Import validation cần batch friendly và error message có row context. Backend model không nên làm query nặng cho từng product. Api validation cần trả error rõ mà không lộ internal detail. Concurrent updates và unique value cần transaction hoặc database support phù hợp. Test phải bao phủ Admin save, repository save, rest update, import và bulk flow. Một field hợp lệ trong form không chứng minh mọi write path an toàn.  Client cũng cần phân biệt attribute không có value với attribute không được load do fields filter hoặc store scope. Hai trường hợp có response giống nhau nhưng nguyên nhân và hướng xử lý khác.

Product service contract hỗ trợ custom attributes. Rest payload thường đặt field tùy chỉnh trong custom attributes theo code và value, không tự tạo top level property như built in field. Store code trên route ảnh hưởng scope khi đọc và save. Client phải phân biệt default value và store override. Type representation trong json có thể cần xác nhận theo version, vì custom attribute value đôi khi được serialize khác expectation strict của client. Product api authorization vẫn áp dụng, nhưng custom eav attribute không tự có field level acl giống extension attribute resource restriction. Bulk update cần chunk, retry và reindex plan. Hàng trăm nghìn product updates có thể tạo index backlog và cache churn. Operation accepted không nghĩa storefront đã cập nhật. Monitoring phải xem import status, indexer state và queue nếu dùng async bulk.  Với storefront dùng code generation, top level typed field có thể dễ dùng hơn generic array, nhưng đổi lại module phải duy trì schema, resolver, cache và backward compatibility lâu dài.  Quyết định phải dựa vào số lượng attributes, nhu cầu filter và mức ổn định của contract, không chỉ sự tiện lợi của một client hiện tại.

Graphql exposure cần được kiểm tra riêng. Tạo eav attribute không đảm bảo schema có top level field cùng code. Adobe Commerce hiện có generic custom attribute và metadata contracts cho nhiều use cases. Nếu storefront cần typed field ổn định hoặc object tính toán, module có thể mở rộng schema. Output exposure không đồng nghĩa products query filter hoặc sort được. Attribute metadata, search index và query implementation phải hỗ trợ. Core GraphQL, Catalog Service và Adobe Commerce as a Cloud Service có capability khác nhau, nên không áp một tài liệu endpoint cho mọi platform. Cache còn cần test. Product save theo repository thường phát lifecycle phù hợp, nhưng direct database integration có thể làm query cache hoặc full page cache stale. Client cache như Apollo cũng có thể giữ value cũ dù network response đã đúng.  Import rehearsal trên dữ liệu gần production cần đo thời gian, error rate và index backlog. Một file chạy nhanh trên vài nghìn sản phẩm không dự báo được lock, disk hoặc queue pressure ở catalog lớn.  Nếu import thay đổi search relevant fields, kế hoạch còn phải tính thời điểm reindex và khả năng storefront phục vụ index cũ trong lúc batch đang chạy.

Import và export biến attribute code thành external contract. Csv column name, option format và store view phải được tài liệu hóa. Empty string, null, missing column và explicit delete không giống nhau. Default scope row có thể tạo fallback, còn store row tạo override. Import file thiếu scope design dễ xóa localization hoặc giữ stale override. Select label có thể khác theo locale, nên stable code mapping đáng tin hơn. Backfill attribute mới có thể để null và compute fallback, hoặc ghi value cho catalog cũ. Backfill lớn cần batch, checkpoint, retry và query theo primary key. Export cũng cần data classification. Technical specification có thể public, nhưng supplier code, margin class hoặc internal compliance flag không nên gửi cho mọi partner. Integration contract phải chỉ expose fields cần thiết.  Sau khi bật cache user defined attributes, cần theo dõi Redis hoặc Valkey memory và network traffic. Tối ưu số query không được đổi thành cache footprint vượt khả năng hạ tầng.  Eav metadata cache và product page cache là hai layer khác nhau. Clean layer này không đảm bảo layer kia tự cập nhật nếu invalidation path custom bị thiếu.

Attribute metadata, indexer và cache tạo một lifecycle liên kết. Eav configuration được cache. Adobe mô tả system attributes được preload và có option cache user defined attributes, giúp giảm database requests nhưng tăng cache network size. Khi searchable, filterable, sort hoặc promo flags thay đổi, indexers liên quan cần được xác định và thời gian rebuild phải được đo. Used in product listing làm collection load field rộng hơn. Direct sql update bỏ qua repository events, index invalidation và cache tags, nên database đúng nhưng category page hoặc graphql vẫn cũ. Reindex không tự sửa cache key sai, và cache clean không thay reindex. Debug phải xem metadata cache, indexer state, search document, product response và edge cache riêng. Attribute cardinality cao còn ảnh hưởng search memory và aggregation latency.  Trong giai đoạn dual read, metrics nên đếm số value khác nhau giữa attribute cũ và mới. Chỉ so tổng số rows không phát hiện mapping sai hoặc value bị truncate.  Migration cũng cần kiểm tra negative value, empty value, store override và product type không được áp dụng. Những edge cases thường chiếm phần lớn lỗi sau rollout.

Thay đổi attribute đã có data cần migration nhiều bước. Đổi label thường ít rủi ro storage nhưng ảnh hưởng Admin và mapping dựa label. Đổi text sang select cần tạo options và map every existing text value sang option id. Đổi varchar sang int tại chỗ dễ làm data và search mapping hỏng. Hướng an toàn là tạo attribute mới, dual read hoặc fallback, backfill theo batch, so sánh counts, chuyển writers và readers rồi retire attribute cũ. Đổi scope cần copy hoặc collapse overrides theo policy. Xóa attribute là destructive và phải kiểm tra configurable product, rules, search, api clients, import files, reports và extensions. Không xóa chỉ vì code không còn reference trực tiếp. Data có thể vẫn là merchant asset hoặc integration dependency.  Uninstall documentation cần nói rõ data nào được giữ, data nào bị xóa và cách export trước khi cleanup. Merchant không nên phát hiện policy destructive sau khi lệnh đã chạy.  Nếu module được bán cho nhiều merchant, cleanup có thể là command riêng yêu cầu confirmation và tạo backup report, thay vì tự động chạy trong uninstall hook.

Revert patch cần được xem như uninstall data policy. Adobe không cung cấp workflow bình thường để revert riêng một data patch; revert thường chạy trong module uninstall khi patch implement interface phù hợp. Remove attribute trong revert xóa metadata và values. Nếu merchant uninstall tạm thời hoặc reinstall, business data có thể mất. Module khác hoặc merchant có thể đã dùng attribute ngoài mục đích ban đầu. Nhiều extension production chọn không tự xóa data, hoặc cung cấp cleanup command explicit. Quyết định phải được tài liệu hóa. Test package cần clean install, upgrade và uninstall trên database có data. Backup không thay policy, nhưng restore rehearsal cần có nếu cleanup destructive. Code review phải nhìn method revert với mức nghiêm trọng tương đương drop table.  Schema migration và code deployment nên có owner riêng nhưng cùng một release checklist. Nếu database step thành công còn code rollback, system phải vẫn đọc được metadata mới mà không lỗi.  Health check sau migration nên kiểm tra attribute metadata, sample products, Admin form, api response và index status trước khi mở traffic đầy đủ.

Git review cần kiểm tra attribute code collision, backend type, scope, required, default, apply to, search flags, set assignment, revert và api exposure. Patch đã release là immutable. Thay đổi tiếp theo là patch mới với dependency rõ. Pipeline cần install module trên database sạch, upgrade từ version trước và xác nhận patch list. Deployment nhiều node phải chạy setup upgrade trước traffic theo strategy thống nhất. Nếu code reader chạy trước migration, attribute chưa tồn tại có thể gây lỗi hoặc empty behavior. Rolling release cần backward compatible code hoặc atomic switch. Search reindex và cache warming phải nằm trong runbook. Attribute inventory nên ghi code, owner, purpose, scope, source, index flags, integrations và deprecation state. Đây là tài liệu hệ thống giúp tránh duplicate attributes và quyết định sai trong upgrade.  Khi root cause chưa rõ, hãy chụp effective attribute metadata, sample rows theo store, indexer status và request response trước khi clean cache. Evidence này giúp phân biệt data drift với cache stale.  Khi issue chỉ xảy ra trên một store, so sánh row default với row store view và kiểm tra save context. Không nên kết luận patch lỗi chỉ vì default scope vẫn đúng.

Các incident phổ biến gồm required attribute làm product cũ không save, field chỉ hiện ở default set, option id sai giữa environments, search index fail sau đổi type và store override bị import xóa. Patch sửa nhưng production không đổi vì patch list đã ghi applied. Layered navigation có hàng chục nghìn options vì high cardinality attribute bị bật filterable. Module uninstall xóa attribute và merchant data do revert destructive. Used in listing trên quá nhiều fields làm memory product collection tăng. Graphql đúng nhưng category stale vì direct sql bỏ qua invalidation. Mỗi incident cần evidence ở metadata, value table, set assignment, index, cache và integration. Không xóa patch list hoặc flush mọi cache để thử. Những thao tác đó có thể làm state khó khôi phục và không giải quyết data model sai.  Incident review nên bổ sung automated check để ngăn tái diễn, chẳng hạn cảnh báo applied patch bị chỉnh sửa, filterable attribute có cardinality quá cao hoặc attribute mới chưa được gán vào required sets.  Root cause document cần ghi rõ vì sao test trước đó không bắt được lỗi, data volume nào làm behavior thay đổi và threshold nào sẽ được monitoring từ nay.

Hãy lập migration mới mà không sửa patch cũ và chứng minh rollback không làm mất merchant data.
