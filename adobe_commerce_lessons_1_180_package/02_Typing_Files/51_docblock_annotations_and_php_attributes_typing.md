Metadata trong integration test của Adobe Commerce mô tả context mà test framework phải chuẩn bị trước khi assertion chạy. Commerce không chỉ có database. Nó còn có object manager, dependency injection theo area, session, current store, request, cache, configuration, indexer và component registration. Nếu test chỉ chứa code gọi service mà không khai báo context, framework có thể chạy trong trạng thái khác production. Metadata giúp framework biết có cần application isolation, database transaction, data fixture, area, cache hoặc config tạm thời hay không. Có thể hình dung metadata là bản kế hoạch lifecycle của test. Framework đọc kế hoạch, tạo ranh giới isolation, áp dụng fixture, chọn area, đặt cache và config, rồi mới chạy method. Sau test, framework khôi phục state. Khi metadata sai, test có thể fail vì setup không đúng. Nguy hiểm hơn, test có thể pass trong context không giống entry point thật. Ví dụ plugin chỉ khai báo ở frontend sẽ không được chứng minh nếu test chạy global. Vì vậy metadata không phải comment trang trí. Nó là một phần của behavior mà test đang kiểm tra.

Docblock annotation là cách legacy đặt metadata trong comment phía trên class hoặc method. Framework parse các dòng bắt đầu bằng tên annotation rồi chuyển string thành instruction. Cơ chế này xuất hiện từ trước khi php có native attributes và vẫn có trong nhiều test core hoặc custom cũ. Ưu điểm của nó là dễ thêm vào code legacy và đã được framework hỗ trợ lâu. Hạn chế là annotation chỉ là text. IDE khó kiểm type, static analysis ít phát hiện argument sai, refactor tên class không an toàn và lỗi chính tả có thể chỉ xuất hiện khi test chạy. Parameter phức tạp cũng khó đọc vì mọi thứ nằm trong một dòng string. Adobe hiện không khuyến nghị dùng docblock annotations cho test mới khi php attributes đã khả dụng. Tuy nhiên developer vẫn cần hiểu annotation để bảo trì release branch cũ, đọc test core và migration test suite. Không nên xóa hoặc chuyển hàng loạt chỉ vì style. Migration metadata có thể đổi lifecycle, nên phải giữ behavior và chạy regression đầy đủ. Khi đọc test cũ, cần kiểm cả annotation ở class và method vì context có thể được khai báo xa assertion và làm behavior khó nhận ra.

Php attribute là metadata native của ngôn ngữ. Nó dùng class thật, constructor thật và argument có type. IDE có thể tìm symbol, gợi ý parameter và hỗ trợ refactor. Static analysis cũng có nhiều cơ hội phát hiện lỗi sớm hơn. Attribute đặc biệt quan trọng với parameterized data fixture vì test có thể truyền array data, alias, scope và count rõ ràng. Named argument giúp người đọc thấy ý nghĩa mà không phải nhớ thứ tự string. Tuy vậy attribute không tự bảo đảm test đúng. Developer vẫn có thể chọn sai area, bật isolation không cần thiết hoặc đặt config sai scope. Attribute chỉ làm contract rõ hơn. Test mới nên dùng attributes. Test legacy có thể giữ annotations nếu pull request nhỏ và migration làm tăng rủi ro. Khi team quyết định migration, nên thực hiện theo module hoặc nhóm annotation, không trộn tùy ý hai style trong cùng method. Mục tiêu là tăng clarity và type safety mà không làm mất coverage hoặc thay đổi runtime context vô tình. Mỗi migration nên ưu tiên clarity, dùng named argument khi giúp reviewer hiểu scope hoặc trạng thái thay vì chỉ rút ngắn số dòng.

Thứ tự framework áp dụng metadata rất quan trọng. Application isolation được xử lý trước database isolation. Sau đó framework có thể chạy fixture trước transaction đặc biệt, data fixture thông thường, indexer dimension mode, component registration, application area, cache và configuration. Trình tự này phản ánh dependency giữa các context. Ví dụ một store fixture phải tạo store trước khi config fixture đặt giá trị theo store đó. Nếu developer tự set config trong setup method trước khi fixture store tồn tại, config có thể gắn sai scope hoặc fail. Isolation được chuẩn bị sớm để tạo ranh giới cho data và memory. Area được chọn sau fixture theo lifecycle framework, còn cache và config hoàn thiện precondition trước assertion. Khi debug, hãy xác định failure xuất hiện ở bước nào. Không nên trộn setup thủ công chỉ vì chưa hiểu order. Framework đã có metadata để quản lý lifecycle. Một test Expert không chỉ khai báo đúng attribute, mà còn giải thích được vì sao attribute đó phải xuất hiện và state nào cần tồn tại trước state nào.

Application isolation xử lý state trong memory và application lifecycle. Commerce có session, request, response, current store, registry, shared object và static cache của custom code. Database rollback không làm những state này biến mất. Nếu một test đăng nhập customer hoặc thay current store, test sau có thể nhận state cũ nếu application không được reinitialize. Application isolation phù hợp với controller, session, area, store emulation hoặc shared singleton bị mutate. Tuy nhiên nó có cost vì framework phải khởi tạo lại nhiều thành phần. Không nên bật cho toàn suite như một biện pháp chữa flaky test chung chung. Repository test chỉ tạo và load entity thường không cần mức isolation đó. Nếu test pass riêng nhưng fail sau một test session, hãy nghi memory state leak. Thu thập current store, area, object identity và static cache trước khi thay test order. Annotation legacy có thể bật application isolation bằng string enabled, còn test hiện đại dùng attribute boolean rõ hơn. Quyết định vẫn phải dựa trên state thật sự bị thay đổi. Một test session tốt còn cần assert state đã được phục hồi, không chỉ assert hành vi trong chính method hiện tại.

Database isolation xử lý persistence trong database transaction. Framework có thể rollback insert, update và delete sau test, giúp test chạy lặp mà không để lại row. Khi data fixture hiện đại được dùng, database isolation được bật mặc định theo tài liệu hiện hành. Điều này không có nghĩa mọi side effect đều biến mất. File trên filesystem, message đã publish tới broker, document trong search engine, cache ngoài transaction và request external service không được rollback bởi database. Nếu test tạo những state này, fixture hoặc test phải có cleanup riêng. Database isolation cũng không sửa application state trong memory. Vì vậy app isolation và db isolation giải quyết hai lớp khác nhau. Không bật hoặc tắt chúng theo thói quen. Hãy vẽ state map của test rồi chọn đúng ranh giới. Khi test cần kiểm transaction boundary thật, data fixture before transaction có thể cần thiết, nhưng nó làm cleanup khó hơn và phải có rollback explicit. Đây là công cụ đặc biệt, không phải default setup. Khi side effect nằm ngoài database, test phải có cleanup có thể quan sát và không được dựa vào lần chạy sạch tiếp theo để che state còn sót.

Application area quyết định nhiều behavior trong Adobe Commerce. Dependency injection có thể được merge theo frontend, admin, rest, soap, graphql hoặc cron context. Plugin và observer có thể chỉ tồn tại trong một area. Session implementation, request object và route behavior cũng khác. Test phải chọn area giống production entry point. Nếu service được gọi từ storefront, frontend area thường là context cần kiểm. Nếu module chỉ can thiệp admin, test cần admin area. Một strategy tốt là có positive test ở area đúng và negative test ở area khác để chứng minh extension không tác động ngoài phạm vi. Không nên set area trực tiếp trong setup khi framework có metadata phù hợp, vì manual state có thể conflict với lifecycle và gây lỗi area đã được set. Nếu test báo plugin không chạy, trước khi sửa di configuration hãy kiểm area. Annotation legacy dùng magento app area, còn test mới dùng attribute class. Ý nghĩa kiến trúc không đổi, nhưng attribute giúp IDE và refactor tốt hơn. Nếu cùng service được gọi từ nhiều entry point, nên có scenario riêng cho từng area quan trọng thay vì chọn một area thuận tiện rồi suy rộng kết quả.

Configuration fixture đặt config tạm thời rồi khôi phục sau test. Nó phù hợp với feature flag, website override, store display mode, integration option hoặc default value. Test nên dùng configuration metadata thay vì mock config reader nếu mục tiêu là kiểm scope resolution thật. Một scenario tốt có thể kiểm default, website override, store override, fallback và missing config. Tài liệu attribute hiện hành mô tả config ở method level, vì vậy không nên giả định có thể đặt một baseline class level cho mọi test. Config cũng tương tác với cache. Nếu test thay config nhưng object đã đọc giá trị cũ từ cache hoặc shared object, assertion có thể sai. Framework order áp dụng config sau fixture giúp store hoặc website fixture tồn tại trước khi config theo scope được set. Khi config không revert, kiểm test có chạy đúng integration framework, scope type, scope value và cache state. Không sửa singleton bằng reflection rồi quên restore. Metadata làm precondition rõ và giúp reviewer hiểu test đang chạy với cấu hình nào. Test cũng nên reload config qua public reader hoặc service thật để chứng minh framework đã áp dụng scope, không chỉ kiểm row trong bảng config.

Cache metadata cho phép test bật hoặc tắt cache type trong phạm vi xác định. Nhiều team tắt toàn bộ cache để test dễ pass, nhưng production chạy với cache enabled. Cách đó che lỗi cache key, invalidation và stale data. Test liên quan configuration, block output, repository cache hoặc custom cache type cần ít nhất một scenario với cache hoạt động. Test nên tạo state, đọc output, thay source data rồi chứng minh invalidation hoặc key variation cho kết quả mới. Không clean toàn bộ cache ngay trước assertion vì thao tác đó có thể che lỗi. Cache state phải được khai báo rõ để test không phụ thuộc cache còn lại từ lần chạy trước. Annotation legacy có magento cache, còn attributes hiện đại dùng class tương ứng của target version. Constructor cụ thể cần được đối chiếu source vì framework có thể thay đổi. Ý quan trọng là cache là một phần behavior, không chỉ vấn đề tốc độ. Test metadata cần phản ánh chính sách cache production mà module phải hoạt động cùng. Khi kiểm invalidation, cần quan sát output trước và sau thay đổi source để chứng minh cache policy thật sự hoạt động trong lifecycle test.

Indexer dimension mode là context ít được chú ý nhưng quan trọng với price, customer group, website hoặc shared catalog. Một indexer có thể tạo output khác theo dimension mode. Test pass ở default mode không chứng minh production mode khác cũng đúng. Metadata dimension cho phép test đặt mode cần kiểm. Scenario nên tạo source data, chạy indexer và assert output ở từng dimension quan trọng. Không hardcode tên mode từ tài liệu khác version mà không kiểm source target branch. Khi CI và production dùng mode khác, test có thể tạo cảm giác an toàn sai. Component registration metadata cũng có vai trò riêng. Nó đăng ký component fixture tạm và unregister sau test, phù hợp với test module discovery, di configuration hoặc route khi component xuất hiện. Component cần registration file đúng và path phải hoạt động trên filesystem case sensitive. Test pass local trên mac nhưng fail linux có thể do path hoặc chữ hoa thường. Metadata chỉ hiệu quả khi environment parity được bảo đảm. Với custom indexer, test nên ghi rõ dimension nào ảnh hưởng key và output để failure không bị hiểu nhầm là lỗi dữ liệu fixture.

Class level và method level metadata không phải lúc nào cũng merge giống nhau. Một class có area chung có thể khai báo baseline nếu framework hỗ trợ. Nhưng method có fixture riêng có thể làm class fixture bị bỏ qua cho method đó. Config attribute hiện hành được mô tả dùng ở method level. Developer phải đọc contract từng attribute, không suy rộng từ một attribute sang tất cả. Nếu test class chứa nhiều scenario khác nhau, method metadata thường dễ đọc hơn vì precondition nằm cạnh assertion. Class metadata có thể giảm duplication nhưng dễ tạo hidden context. Khi reviewer đọc một method giữa file dài, họ có thể không thấy area hoặc isolation đặt ở đầu class. Tên test và documentation cần giúp nhận biết. Debug alias missing hoặc config không tồn tại phải kiểm cả class và method precedence. Không chữa bằng copy mọi metadata vào mọi method mà không hiểu lifecycle. Mục tiêu là context rõ, tối thiểu và đúng. Khi baseline class làm method khó hiểu, tách test class theo context thường tốt hơn việc thêm nhiều override chồng chéo.

Data fixture metadata đã được học sâu ở bài trước, nhưng trong chuỗi lifecycle cần nhớ rằng fixture chạy sau isolation và trước area, cache, config. Fixture hiện đại dùng php attributes, còn annotation legacy chỉ làm việc với file hoặc method cũ. Data fixture before transaction chạy sớm hơn và cần rollback riêng. Fixture không nên dựa vào arbitrary application state vì app isolation có thể reset state. Khi test cần store fixture và config theo store, framework order giúp tạo store trước config.
