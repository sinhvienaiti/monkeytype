Một hệ thống linux không cấp cho process một khối ram vật lý bằng đúng con số mà ứng dụng yêu cầu. Process nhìn thấy một không gian địa chỉ ảo, còn kernel ánh xạ từng page ảo tới page vật lý khi dữ liệu thật sự được truy cập. Vì vậy virtual size lớn có thể chỉ phản ánh vùng đã reserve, file đã map hoặc address range chưa được touch. Resident set mới gần với số page đang nằm trong ram, nhưng resident set vẫn có thể tính cùng shared library hoặc shared page cho nhiều process. Proportional set chia chi phí shared page cho các process đang dùng nên thường hữu ích hơn khi lập ngân sách cho một pool php. Anonymous memory thường đến từ heap, stack và dữ liệu private, còn file backed memory có thể đọc lại từ file. Page cache giữ nội dung file đã đọc để lần sau không phải truy cập storage chậm. Cache lớn không tự động là memory leak, vì clean cache có thể được reclaim khi workload cần memory. Một ảnh chụp có cột free thấp vì thế chưa chứng minh server thiếu ram. Engineer cần xem available, resident footprint, pressure, reclaim, fault và latency theo cùng timeline. Minor fault có thể được giải quyết mà không cần đọc storage, trong khi major fault thường liên quan i o và có thể làm request chậm. Một process cũng có thể free object nhưng resident set không giảm ngay vì allocator giữ arena để tái sử dụng. Đây là allocator retention, khác với leak nơi reference không cần thiết vẫn sống và footprint tăng theo công việc. Điều tra đúng phải đo nhiều lần dưới workload lặp lại, nhận biết pid đã restart và tách private page khỏi shared page. Khi các khái niệm này được hiểu đúng, team không còn nhân virtual size với số worker hoặc xem mọi cache là lãng phí. Team có thể giải thích memory bằng mapping, resident page, ownership và khả năng reclaim, rồi mới quyết định giới hạn hoặc capacity.

Linux chủ động dùng ram chưa cần cho anonymous workload để làm page cache, vì ram trống không tạo giá trị cho hệ thống. Khi php đọc class, generated code hoặc metadata, page cache có thể phục vụ lần đọc sau mà không cần i o. Khi application cần thêm memory, kernel có thể bỏ clean file page và đọc lại chúng sau. Dirty page khó reclaim hơn vì content mới phải được write back xuống storage trước. Nếu storage chậm hoặc log burst tạo nhiều dirty page, request có thể bị throttle dù tổng ram nhìn vẫn còn. Lệnh free tổng hợp nhiều trường từ proc, nhưng engineer nên nhìn available thay vì chỉ nhìn free. Available là ước lượng memory có thể cấp mà không gây swap quá mức, không phải lời hứa tuyệt đối. Pressure thật cần evidence như available thấp kéo dài, direct reclaim, major fault, swap activity, memory pressure stall và latency tăng. Pressure stall information cho biết task đã bị stall vì thiếu resource trong bao nhiêu phần thời gian. Trường some nghĩa ít nhất một task bị ảnh hưởng, còn full cho thấy mọi task không idle trong scope cùng bị stall. Hai hệ thống đều có thể dùng chín mươi phần trăm ram, nhưng hệ thống thứ nhất có cache reclaimable và pressure gần bằng không, trong khi hệ thống thứ hai liên tục reclaim và làm request chờ. Chỉ phần trăm used không tách được hai trạng thái này. Engineer cũng phải xem timeline vì counter tích lũy từ boot có thể lớn dù incident đã qua. Một snapshot vmstat đầu tiên thường là trung bình dài hạn, nên cần các dòng interval tiếp theo. Cách làm an toàn là ghi memory tổng, pressure, swap in, swap out, process resident và cgroup event trong cùng cửa sổ. Không nên drop cache để làm con số free đẹp hơn, vì thao tác đó xóa working set hữu ích và có thể tạo cold i o. Mục tiêu của điều tra là chứng minh workload đang chịu pressure hay chỉ đang sử dụng ram hiệu quả.

Swap là backing store cho anonymous page không cần resident ngay, nhưng swap không có tốc độ tương đương ram. Một hệ thống có thể đưa page ít dùng ra swap để giữ ram cho working set hoạt động và page cache. Vì vậy swap used lớn không tự động là lỗi. Những page cũ có thể nằm trong swap rất lâu mà không được đọc lại, trong khi swap in và swap out gần bằng không và latency vẫn ổn định. Thrashing là trạng thái khác, nơi working set lớn hơn memory khả dụng nên kernel liên tục đẩy page ra rồi kéo chúng trở lại. Khi đó swap activity, major fault, storage i o và pressure tăng cùng nhau, còn throughput business giảm. Cpu có thể không cao vì task đang chờ page thay vì chạy code. Engineer phải nhìn activity theo giây và impact, không chỉ nhìn tổng dung lượng swap. Swappiness ảnh hưởng cân bằng reclaim anonymous page với file page, nhưng nó không phải công tắc đơn giản để bật hoặc tắt swap. Một giá trị cực đoan có thể giữ anonymous page quá lâu hoặc làm mất page cache hữu ích. Trên môi trường cloud được quản lý, team không nên tự tạo swapfile hoặc thay kernel setting ngoài boundary hỗ trợ. Swap cũng không sửa memory leak, batch không bounded hoặc pool có quá nhiều worker. Nó có thể cho thêm thời gian trước oom trong một burst ngắn, nhưng một workload thiếu capacity thường xuyên sẽ chỉ chậm hơn trước khi thất bại. Zswap nếu có thể nén page trong ram trước khi ghi ra swap device, nhưng nó vẫn dùng cpu và memory. Mọi quyết định tuning cần hypothesis, benchmark và rollback. Khi thấy swap, câu hỏi cần đặt là page nào đang di chuyển, tốc độ di chuyển bao nhiêu, request bị stall ra sao và nguyên nhân nào làm working set vượt budget. Chỉ sau khi trả lời các câu hỏi đó mới có thể chọn giảm concurrency, chia batch, sửa leak, tăng ram hoặc điều chỉnh architecture.

Memory leak và allocator retention thường tạo biểu hiện giống nhau trong một ảnh chụp, nhưng cách sửa khác nhau. Leak xảy ra khi dữ liệu không còn cần vẫn reachable hoặc component tiếp tục giữ reference. Allocator retention xảy ra khi application đã free object nhưng allocator giữ page để phục vụ lần cấp phát sau. Một php worker vừa xử lý export lớn có thể giữ resident set cao mà không tiếp tục tăng. Nếu worker xử lý các request tương tự và footprint ổn định quanh high water mark, retention có thể là lời giải thích hợp lý. Nếu footprint tăng gần tuyến tính theo số request hoặc message và không trở về baseline sau idle, leak trở nên đáng nghi hơn. Process reuse của php fpm và queue consumer giúp tránh startup cost, nhưng cũng cho state sống lâu hơn. Static cache, client buffer, exception chain hoặc service singleton có thể giữ object qua nhiều message. Team nên đo memory theo request count, loại message và payload size thay vì chỉ theo thời gian. Profile trong staging cần dùng dữ liệu giống production và phải bảo vệ dữ liệu nhạy cảm trong heap dump. Recycle worker sau một số request hoặc message có thể contain incident và làm allocator được giải phóng khi process exit. Tuy nhiên recycle không phải permanent fix nếu code vẫn giữ reference hoặc query vẫn load toàn bộ collection. Một batch tốt chỉ select field cần thiết, xử lý một phần hữu hạn, commit progress và release reference trước phần tiếp theo. Nó cũng phải restart được mà không tạo duplicate side effect. Với php fpm, số child tối đa là memory multiplier vì nhiều request có thể cùng đạt peak. Capacity không nên được tính bằng ram chia cho php memory limit, vì limit là trần accounting của từng script chứ không phải footprint đo được. Team cần dùng phân phối resident hoặc proportional memory, chừa phần cho opcache, master process, kernel và job nền, rồi load test queueing. Cách tiếp cận này biến việc restart định kỳ từ mẹo che lỗi thành một lớp containment có chủ đích trong khi root cause được sửa.

Out of memory có nhiều boundary nên dòng killed không đủ để kết luận. Php có thể tự dừng script khi chạm memory limit và ghi fatal error allowed memory size exhausted. Kernel có thể gửi signal kill khi toàn host không reclaim đủ memory. Một cgroup cũng có thể đi vào oom khi workload chạm hard limit riêng, ngay cả khi host còn ram. Ngoài ra operator, supervisor hoặc timeout cũng có thể gửi cùng signal. Evidence đúng phải nối exit status, timestamp, kernel hoặc cgroup event, victim pid và workload. Trong cgroup version hai, memory current cho biết usage hiện tại, memory high tạo throttle và direct reclaim, còn memory max là hard boundary. File memory events đếm số lần vượt high, chạm max, đi vào oom và có process bị oom killer kill. Counter là tích lũy nên monitoring cần xem delta. Global oom yêu cầu điều tra toàn host, swap, reclaim và kernel log, còn cgroup oom tập trung vào limit và process trong scope. Oom killer dùng heuristic và adjustment score để chọn victim, không đơn giản luôn kill process lớn nhất. Bảo vệ tùy tiện nhiều service bằng điểm âm cực đoan có thể khiến host khó phục hồi. Exit code một trăm ba mươi bảy thường phù hợp với signal kill trong container convention, nhưng vẫn không chứng minh oom nếu thiếu log. Trên managed cloud, engineer có thể không đọc được dmesg nên cần giữ platform activity, service metric, memory event và mở support với timeline rõ. Mitigation có thể là dừng duplicate job, giảm concurrency hoặc recycle một worker, nhưng permanent fix phải giải quyết producer hoặc resource boundary. Không nên tăng php limit trước khi biết lỗi thuộc php hay kernel, vì limit lớn hơn có thể làm một script sống lâu hơn rồi đẩy cả cgroup vào oom. Một incident report tốt phải nêu rõ boundary nào hết memory, cơ chế nào phát hiện, process nào bị ảnh hưởng và test nào chứng minh bản sửa.

Adobe commerce tạo nhiều loại peak memory khác nhau nên một cấu hình chung không đủ cho mọi process. Php fpm phục vụ nhiều request đồng thời, trong khi setup upgrade, reindex hoặc import thường là một process cli lớn. Cron có thể overlap nếu job chạy lâu hơn schedule, còn consumer sống lâu có thể tích lũy state qua message. Adobe đã ghi nhận setup upgrade trên commerce cloud có thể vượt memory limit cli mặc định trong một số phiên bản và hướng dẫn tăng cấu hình php rồi redeploy. Tuy nhiên team vẫn cần xác định module hoặc data patch tạo peak, vì một patch load toàn bộ collection có thể tiếp tục tăng theo catalog. Adobe cũng ghi nhận reindex ở một số environment có thể chỉ hiện killed khi data cardinality và concurrency làm process thiếu memory. Engineer phải ghi indexer, số store, customer group, product và job đang chạy song song. Chạy lại nhiều full reindex cùng lúc thường làm incident nặng hơn. Với fpm, số child tối đa phải dựa trên footprint đã đo và headroom, không dựa duy nhất vào memory limit. Opcache là shared memory nên không nên cộng toàn bộ cho mỗi child, nhưng nó vẫn nằm trong budget của service. Max requests có thể respawn child để contain leak từ library bên thứ ba, song giá trị quá thấp tạo churn và warmup cost. Consumer nên có giới hạn message hoặc lifetime phù hợp, nhưng handler vẫn phải release state và idempotent. Deployment còn có peak riêng khi compile, static build, setup upgrade và cache warm chạy gần nhau. Nếu deploy chia cùng boundary với web, peak tạm thời có thể throttle hoặc kill storefront worker. Runbook cần biết phase nào chạy process nào, cron có bị giảm không và rollback có cần lặp lại job lớn không. Cách quản trị expert là xây concurrency map cho web, cli, cron, consumer và deploy, sau đó kiểm tra peak tổng trên dữ liệu production like trước khi release.

Opensearch, redis và mysql đều dùng memory làm cache hoặc working area, nhưng mỗi service có semantics khác nhau. Opensearch có java heap cho object, cache và query execution, đồng thời còn dùng off heap memory, thread stack, memory mapping và page cache. Guidance thường bắt đầu với heap khoảng một nửa memory khả dụng để chừa phần còn lại cho operating system, nhưng con số phải được kiểm chứng bằng garbage collection, breaker, query và shard. Đặt heap bằng toàn bộ ram có thể làm node mất page cache và gặp pressure ngoài heap. Quá nhiều shard nhỏ, aggregation cardinality cao hoặc fielddata sai mapping có thể làm heap tăng dù document count không lớn. Redis có maxmemory và eviction policy riêng. Used memory phản ánh allocator theo accounting của redis, còn resident memory có thể lớn hơn vì fragmentation, client buffer hoặc copy on write. Evicted key tăng có thể chỉ làm cache miss, nhưng nếu key là session thì shopper có thể mất state. Vì thế cache và session cần boundary phù hợp, không flush toàn bộ service như phản xạ. Peak, uptime, eviction, hit rate và fragmentation phải được đọc cùng timeline. Mysql innodb buffer pool chủ động giữ table và index page để giảm disk i o. Process resident lớn có thể là design tốt nếu host không pressure. Hạ buffer pool quá mạnh có thể làm query chậm, khiến php request sống lâu hơn và tổng worker memory tăng. Database còn có per connection và per query buffer nên max connection cao không đồng nghĩa mọi buffer đã cấp, nhưng active concurrency có thể tạo peak. Team phải lập budget theo service, phân biệt global cache, private allocation và burst, rồi đo end to end latency. Tăng một cache hoặc heap có thể cải thiện local metric nhưng lấy memory của layer khác. Permanent fix có thể là sửa mapping, shard, ttl, key model, query, connection hoặc data access, không phải chỉ tăng limit.

Technical lead nên yêu cầu mọi incident memory có timeline, boundary và bằng chứng pressure. Snapshot cần chứa available memory, pressure stall, swap activity, cgroup event, process resident hoặc proportional footprint và metric service liên quan. Evidence phải được scrub vì command line, environment, core dump hoặc heap profile có thể chứa token, session và dữ liệu khách hàng. Alert không nên chỉ dựa trên phần trăm used. Opensearch cần heap, garbage collection, breaker, rejection, shard và segment. Mysql cần buffer pool, active connection, temporary memory và latency. Capacity model phải gồm traffic, catalog cardinality, admin export, cron, consumer, deployment peak và sale event. Báo cáo phải tách biện pháp giảm tác động tức thời khỏi thay đổi loại bỏ nguyên nhân lâu dài. Giảm worker có thể bảo vệ host nhưng tăng queue; tăng memory limit có thể cho job hợp lệ chạy xong nhưng cũng tăng blast radius; restart có thể giải phóng allocator nhưng không sửa leak. Review sau incident nên thêm test với dữ liệu production like, headroom và rollback. Team cũng cần tránh các thao tác làm metric đẹp nhưng phá working set như drop cache, disable swap tùy tiện hoặc flush redis. Mục tiêu không phải giữ ram free, mà là duy trì working set đúng trong ram, reclaim có kiểm soát và workload không bị stall. Khi memory được quản lý như một budget nhiều lớp, adobe commerce có thể xử lý request, reindex, deploy và queue mà không dựa vào phỏng đoán. Báo cáo cuối cùng phải chỉ ra metric nào trở về baseline, peak mới thấp hơn bao nhiêu, latency có ổn định không và correctness của session, order, index cùng cache đã được xác nhận.
