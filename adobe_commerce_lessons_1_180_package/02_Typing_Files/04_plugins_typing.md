Chỉ chuyển exception khi plugin chịu trách nhiệm rõ ràng cho error policy đó.

Khi plugin không chạy, bước đầu tiên là xác nhận observed method thật sự được gọi. Flow có thể dùng một class khác, một implementation khác hoặc một method khác có tên gần giống. Tiếp theo, kiểm tra target có thể intercept hay không. Method phải public, không final, không static và không phải constructor. Class không được final và object không thuộc nhóm noninterceptable. Sau đó, kiểm tra object có được tạo qua object manager hay không. Nếu legacy helper dùng new, plugin sẽ bị bypass. Tiếp theo là kiểm tra tệp dependency injection, observed type, plugin class, area và disabled node. Command dev di info hỗ trợ xem preference, constructor parameters và plugins của một class. Debugger có thể cho biết actual class là interceptor hay class gốc. Nếu cấu hình đúng nhưng behavior vẫn cũ, cần kiểm tra generated code và metadata. Trong production, thay đổi dependency injection phải đi qua compilation và deployment process phù hợp, không xóa generated directory tùy tiện khi site đang phục vụ traffic. Khi plugin chạy sai thứ tự hoặc conflict, cần xem toàn bộ chain. Một before plugin nhận input đã được plugin trước thay đổi.

Một after plugin nhận result đã qua các phần trước của chain, không nhất thiết là raw result của method gốc. Nếu một plugin thay toàn bộ array thay vì enrich result, field của module khác có thể mất. Nếu around plugin return sớm, plugin phía sau biến mất mà không có exception. Cách debug hiệu quả là ghi log có kiểm soát tại boundary, đặt breakpoint trước và sau callable, xem sort order và tạm disable từng plugin trong môi trường test. Không nên thêm static flag để che plugin chạy hai lần trước khi biết nguyên nhân. Logic có thể được khai báo hai lần, method có thể được caller gọi hai lần, plugin có thể nằm trên cả interface và class, hoặc queue có thể retry. Call stack và integration test sẽ cho câu trả lời đáng tin cậy hơn suy đoán. Kiểm thử plugin cần nhiều lớp. Unit test business service chứa logic chính trước, vì service này dễ kiểm soát input và output. Unit test before plugin xác nhận normalization và thứ tự arguments. Unit test after plugin xác nhận result đúng type, không mất field và arguments được chuyển vào service đúng.

Unit test around plugin mock callable để kiểm tra branch bình thường gọi đúng một lần và branch dừng không gọi. Tuy nhiên, unit test plugin class không chứng minh tệp dependency injection đúng. Integration test phải lấy observed type qua object manager rồi gọi method thật. Test này xác nhận plugin được đăng ký, area đúng, interceptor hoạt động và disable configuration có hiệu lực. Với plugin vào core hoặc third party method, contract test sau upgrade cần phát hiện signature đổi, return type đổi, optional argument mới hoặc method bị deprecated. Một bộ test tốt không chỉ chứng minh plugin chạy, mà còn chứng minh plugin không phá contract và không tác động entry point ngoài phạm vi. Một tình huống thường gặp là rule hoạt động trên storefront truyền thống nhưng không hoạt động trong headless client. Nguyên nhân thường không phải graphql bỏ qua business logic một cách ngẫu nhiên, mà plugin được khai báo trong frontend area. Khi request đi vào graphql area, cấu hình đó không được nạp. Nếu rule là business validation, giải pháp tốt hơn là đặt nó trong service dùng chung hoặc plugin global trên contract phù hợp. Một tình huống khác là plugin đã được disable nhưng vẫn chạy.

Cần kiểm tra plugin name, observed type, area, format namespace và generated metadata. Chỉ clean cache không phải lúc nào cũng đủ sau thay đổi dependency injection. Một tình huống nữa là import trở nên chậm sau khi cài module. Plugin thực hiện một query nhỏ cho mỗi sản phẩm, nhưng hàng chục nghìn lần gọi làm tổng thời gian tăng lớn. Profiler phải đo call count và query count, không chỉ duration của một lời gọi đơn lẻ. Một tình huống nguy hiểm là original method save thành công nhưng after plugin gọi service phụ rồi throw exception. Api trả failure, client retry và tạo thêm audit record hoặc thực hiện operation lần nữa. Cần kiểm tra transaction boundary, idempotency và outbox thay vì chỉ catch exception. Một tình huống khác xuất hiện khi module mới thêm preference cho interface. Plugin khai báo trên interface vẫn chạy với implementation mới, nhưng result semantics có thể khác. Dev di info và actual class giúp xác định sự thay đổi. Trong consumer dài hạn, plugin giữ mutable property có thể dùng lại company id từ message trước. Giải pháp là giữ plugin stateless và restart consumer sau deployment khi cần. Những tình huống này cho thấy plugin conflict không chỉ là hai module dùng cùng method.

Conflict còn đến từ lifecycle, transaction, area, implementation replacement và process reuse. Best practice quan trọng nhất là dùng plugin với phạm vi nhỏ và mục đích rõ. Chọn public method ổn định, bám đúng contract và area. Dùng before để thay input, after để thay output, và chỉ dùng around khi cần quyết định có tiếp tục chain hay không. Giữ chữ ký tương thích, đặc biệt với nullable và optional argument. Preserve result contract và không xóa dữ liệu thuộc ownership của module khác. Giữ plugin mỏng, stateless và gọi service chuyên trách. Đo performance trên tổng call count. Không gọi hệ thống ngoài đồng bộ trên hot path nếu không cần. Dùng idempotency cho side effect có thể retry. Debug bằng actual class, merged dependency injection, plugin chain và generated interceptor. Test cả unit và integration. Khi thiết kế bắt đầu phụ thuộc vào nhiều plugin nối tiếp theo workflow phức tạp, hãy dừng lại và chuyển orchestration sang application service explicit. Plugin tốt làm customization nhỏ trở nên tách biệt và nâng cấp dễ hơn. Plugin bị lạm dụng biến hành vi hệ thống thành một chuỗi ẩn mà không ai nhìn thấy đầy đủ. Tóm lại, plugin trong adobe commerce là cơ chế interception dành cho public method.

Nó hoạt động vì object manager có thể trả generated interceptor và plugin list điều phối các phần before, around, method gốc và after. Before thay arguments bằng null hoặc mảng đúng thứ tự. After nhận result rồi trả result đúng contract, đồng thời có thể đọc arguments. Around kiểm soát callable và có thể dừng chain, nên cần dùng hạn chế. Plugin không áp dụng cho final, non public, static, constructor, virtual type target và một số object đặc biệt. Sort order chỉ là một phần của execution flow, vì loại plugin method quyết định cấu trúc lồng nhau. Global và area specific configuration có thể mở rộng hoặc disable plugin. Plugin trên interface có phạm vi rộng và cần test nhiều entry point. Thiết kế an toàn yêu cầu plugin mỏng, stateless, có service riêng, giữ signature chính xác, hiểu transaction và được integration test qua object manager. Khi gặp lỗi, hãy kiểm tra method thật, actual class, area, cấu hình merge, signature, generated code và around plugin phía trước trước khi kết luận framework không hoạt động.
