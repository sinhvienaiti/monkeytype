Khi một ứng dụng báo không còn chỗ ghi, kỹ sư cần tách tên file khỏi object thật trong filesystem. Directory giữ entry ánh xạ một tên tới inode, còn inode giữ metadata và tham chiếu tới block dữ liệu. Một object có thể có nhiều hard link nên xóa một tên chưa chắc xóa data. Một process cũng có thể giữ descriptor sau khi link cuối bị bỏ, vì vậy file biến mất khỏi lệnh liệt kê nhưng block vẫn bị tính. Inode number chỉ có ý nghĩa trong phạm vi device, nên device id và inode mới là cặp nhận dạng hữu ích. Kích thước logic cũng không luôn bằng dung lượng cấp phát. Sparse file có thể nhìn rất lớn nhưng dùng ít block, còn hàng triệu file nhỏ có thể tiêu tốn nhiều inode, block metadata và thời gian lookup. Vì vậy điều tra phải đo ít nhất bốn thứ riêng: byte capacity, inode capacity, inventory pathname và open descriptor. Lệnh đọc filesystem cho biết tổng block đã cấp, trong khi công cụ đi cây directory chỉ cộng object mà nó nhìn thấy. Hai kết quả lệch nhau không phải bằng chứng đủ để kết luận lỗi kernel. Process có thể nhìn mount namespace khác, user chạy scan có thể thiếu quyền, một mount mới có thể che data cũ, hoặc archive đã bị unlink nhưng daemon vẫn ghi. Kỹ sư nên ghi exact path bị lỗi, thời điểm, process tạo lỗi và mount chứa path trước khi thu thập số. Sau đó mới so block, inode, quota, directory usage và tốc độ tăng. Cách suy luận này ngăn phản xạ xóa file lớn không liên quan. Nó cũng giúp phân biệt incident cần giải phóng khẩn cấp với lỗi thiết kế tạo file không giới hạn. Một file log hai mươi gigabyte thường là byte pressure, còn hàng triệu session hoặc cache file có thể là inode pressure. Hai trường hợp cần cleanup và permanent fix khác nhau. Mục tiêu cuối cùng là biết object nào tồn tại, ai còn tham chiếu nó, nó nằm trên filesystem nào và lifecycle nào đáng lẽ phải thu hồi nó.

Cây directory duy nhất mà người dùng nhìn thấy có thể ghép nhiều filesystem ở các mount point khác nhau. Hai path nằm cạnh nhau trong source tree vẫn có thể dùng device, quota, read only flag và sharing model khác nhau. Một process trong container còn có thể thấy mount table khác shell trên host vì mount namespace cô lập view. Bởi vậy câu hỏi đầu tiên không phải directory này lớn bao nhiêu mà là path này thuộc mount nào theo góc nhìn process lỗi. Công cụ tìm mount nên trả target, source, filesystem type và option thay vì runbook parse một dòng output không ổn định. Device id của hai directory còn giúp dự đoán rename có nằm trong cùng filesystem hay không. Local disk thường có latency và failure mode khác network shared storage. Shared mount cho nhiều node nhìn data chung nhưng có thể tốn metadata round trip và chịu quota chung. Temporary filesystem có thể dùng memory và swap, nên file lớn trong đó ảnh hưởng memory pressure thay vì chỉ block disk. Read only artifact bảo vệ code nhưng buộc runtime ghi vào vùng được cấp riêng. Trên adobe commerce cloud, các directory như var, pub media, pub static và app etc được mount writable theo cấu hình, trong khi phần artifact khác không phải nơi extension tùy ý ghi. Directory tmp trên production và staging cluster là local theo từng node. Điều này phù hợp cho buffer chỉ sống trong một request, nhưng không phù hợp nếu node khác sẽ xử lý queue message và cần cùng file. Workflow nhiều node phải đưa state vào shared mount hoặc external storage trước khi phát message. Một mount point cũng có thể che content từng tồn tại trong directory bên dưới. Khi đó scan directory hiện tại không thấy data cũ nhưng root filesystem vẫn dùng block. Không được unmount tùy tiện để tìm data trong production. Cần maintenance procedure, xác minh dependency và backup. Kỹ sư giỏi luôn vẽ storage map gồm sharing, durability, quota, owner và cleanup owner cho từng writable path trước khi sửa application.

Cập nhật file an toàn cần phân biệt việc ghi content với việc publish tên cuối. Nếu writer mở final path rồi ghi dần, reader có thể tải file thiếu dòng, đọc json chưa hoàn tất hoặc cache một artifact hỏng. Mẫu tốt là tạo temporary file bằng api exclusive trong chính directory đích, ghi toàn bộ content, kiểm tra lỗi, đặt owner và mode, xác minh checksum rồi rename sang tên cuối. Khi source và target ở cùng mounted filesystem, rename có thể thay target theo một namespace operation atomic, nên lookup mới thấy version trước hoặc version sau thay vì khoảng trống giữa hai trạng thái. Tuy nhiên atomic visibility không tự đồng nghĩa dữ liệu bền vững sau power loss. File data và directory entry có thể cần flush riêng theo mức mất mát business chấp nhận. Fsync cho mọi request cũng không phải đáp án chung vì latency và blast radius có thể lớn. Quyết định durability phải thuộc component thật sự cần nó. Cross mount là boundary quan trọng. Temporary file ở tmp và target ở shared media có thể thuộc device khác, khiến rename trả lỗi cross device. Một command move có thể âm thầm fallback sang copy rồi unlink. Khi đó operation kéo dài và reader có thể quan sát target đang được copy nếu tool ghi trực tiếp final name. Cách an toàn là copy vào một temporary name trên target mount, validate lại rồi rename tại target. Temporary name predictable bằng pid hoặc timestamp có thể tạo race và symlink attack trong directory nhiều user ghi. Api tạo file exclusive hoặc công cụ tạo tên ngẫu nhiên an toàn phải được dùng cùng directory permission phù hợp. Cleanup cũng cần trap hoặc state machine để file hỏng không tích tụ. Atomic rename không ngăn hai writer cùng hoàn tất rồi writer cuối ghi đè writer trước. Workflow còn cần idempotency key, version expected, lock hoặc no replace behavior. Vì vậy cụm từ atomic file update chỉ đúng khi team mô tả cả mount boundary, concurrency policy, visibility và durability.

Upload, import và export đều cần một lifecycle rõ thay vì chỉ một pathname. Upload nên đi qua receiving, validation, security scan, business acceptance, persistence và publication. Import lớn còn cần original immutable, normalized chunks, checkpoint, error report và completed state. Nếu mỗi row hoặc retry tạo một file tạm, inode có thể cạn trước khi tổng byte đáng kể. Checkpoint chỉ nằm ở tmp sẽ mất khi process hoặc node thay đổi. Export có rủi ro ngược lại vì client có thể tải trong lúc writer đang tạo. Writer nên xây file versioned trong target mount, xác minh row count và checksum, rồi publish bằng rename hoặc cập nhật metadata tới immutable version. Cleanup version cũ phải dựa trên retention và download state, không chỉ thời gian sửa file. Trong adobe commerce, var có thể chứa log, report, import, export, cache và temporary data do core hoặc custom module tạo. Mỗi subdirectory cần có component owner, tốc độ sinh file, thời gian sống tối đa, khả năng regenerate và command cleanup. Xóa toàn bộ var trên production có thể làm mất lock, report, export hoặc evidence incident. Pub media còn trộn original asset với derived cache, nên cleanup phải phân biệt data nguồn và file có thể tái tạo. Xóa media cache rộng có thể giảm disk ngay nhưng tạo burst cpu và io khi storefront regenerate. Pub static và generated code lại gắn với deployment strategy. Tree cũ, nhiều locale hoặc failed temp có thể làm tăng inode. Cleanup trong lúc node khác đang serve cần hiểu shared mount, release lifecycle và rollback. Storage design đúng biến file từ side effect vô danh thành object có state, owner, retention và evidence hoàn thành.

Log rotation không chỉ là đổi tên file theo ngày. Daemon mở một descriptor, ghi record, còn filesystem giữ inode độc lập với pathname. Rotation kiểu rename và create cần daemon reopen pathname mới. Nếu không, process tiếp tục ghi vào inode archive dù active name mới đã xuất hiện. Nếu archive bị xóa trong lúc descriptor còn mở, công cụ đi directory không thấy file nhưng filesystem vẫn giữ block. Đây là nguyên nhân điển hình khi disk usage không giảm sau lệnh rm. Kỹ sư cần tìm deleted descriptor, xác định service và dùng signal reopen hoặc graceful restart được tài liệu hỗ trợ. Forced kill không phải bước đầu vì có thể gây outage và mất cleanup khác. Copy truncate giữ inode active nên không cần reopen, nhưng nó có cửa sổ race giữa copy và truncate. Record có thể bị mất hoặc xuất hiện trùng, còn copy log lớn tạo io đáng kể. Chỉ dùng strategy này khi application không hỗ trợ reopen và business chấp nhận tradeoff. Rotation còn có state file, trigger theo time hoặc size, owner, mode, compression, retention và post rotation action. Chạy force trên config system thật chỉ để thử có thể rotate log production ngoài kế hoạch. Test nên dùng sandbox, log giả và state riêng. Compression tiết kiệm byte nhưng tiêu thụ cpu và io, vì vậy schedule không nên trùng peak traffic nếu archive lớn. Retention phải cân bằng incident window, compliance, central ingestion và quota. Không xóa local archive trước khi xác minh pipeline log ngoài đã nhận đủ dữ liệu và truy vấn được. Custom module nên giữ active filename ổn định thay vì tạo một file theo request hoặc pid. Dynamic filename làm rotation khó match và tăng inode. Log volume tăng đột biến thường là symptom của error loop, debug flag hoặc retry storm. Truncate chỉ là mitigation. Permanent fix phải sửa source, severity, sampling hoặc retry policy. Monitoring nên theo dõi byte rate, file count, oldest archive và deleted open byte, không chỉ phần trăm disk.
